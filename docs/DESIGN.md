# AI-Agent-Resolve: design

Draft v1, 2026-10-17. Slices and status are tracked in [`PLAN.md`](../PLAN.md).

## 1. What this is

AI-Agent-Resolve is a companion app for DaVinci Resolve Studio, built mainly for AI agents to use. Agents plan, measure, build and check edits. Humans supervise and review, and keep working in Resolve as usual.

It does not reimplement Resolve. Resolve remains the renderer, the timeline of record and the collaboration surface. This app adds the things Resolve lacks for agent work:

- A typed edit-plan layer that is checked against house rules before anything touches Resolve.
- A scheduler in front of the single Resolve instance.
- An offline toolchain for `.drp` files.
- A shared store of projects, events and artifacts that humans and agents both see.
- Recipes that take a job, such as a CCN long-form or a set of shorts, from brief to published files.

## 3. Architecture

```
 agents (Command Center threads, Codex, CLI)            humans
        │ MCP (streamable HTTP) / REST / CLI                │ web console: review, approve, override
        ▼                                                   ▼
 ┌──────────────────────────── aar-hub (tailnet) ─────────────────────────────┐
 │ project registry · append-only event log · work graph                      │
 │   (brief → plan → ops → artifacts → reviews)                               │
 │ leases + presence · review threads at timecode · artifact store (by hash)  │
 │ per-project facts (offsets, gains, traps) · rule profiles · recipe runner  │
 └──────────┬──────────────────────────────────────────────┬──────────────────┘
            │ hot jobs (node pulls)                        │ cold jobs (any host)
            ▼                                              ▼
 ┌──── aar-node (beside each Resolve Studio) ───┐   ┌──── workers ──────────────────┐
 │ session broker: leases, hot-op queue,        │   │ aar.drp: read / diff /        │
 │   context save + restore, presence guard     │   │   modify / create             │
 │ op library: verified ops with traps built in │   │ transcripts, laugh maps,      │
 │ job runner: checkpointed, no 60 s cap        │   │   face tracks, ffmpeg,        │
 │ path map, offline + proxy checks             │   │   captions, thumbnails        │
 └──────────┬───────────────────────────────────┘   └───────────────────────────────┘
            │ DaVinciResolveScript (local)
            ▼
   DaVinci Resolve Studio ─── Blackmagic Cloud library · Presentations · Cloud Store
```

The app is Python 3.11+ throughout, because the Resolve API and all the existing CCN tooling are Python. It is one repo with a single package, `aar`, split into `aar.drp`, `aar.node`, `aar.hub`, `aar.plan` and `aar.recipes`.

Work is either hot or cold:

- **Hot ops** need Resolve's current project or timeline: building, grading, submitting renders, exporting. They always go through the node's broker.
- **Cold ops** need nothing from Resolve: parsing DRPs, transcription, Gemini analysis, ffmpeg, planning and linting. They run in parallel on any host.

## 4. The six requirements

### R1. Read, modify and create `.drp` files

- **Read (S1).** A lossless container reader produces a typed model: project settings, bins, media clips, timelines, tracks, items, and markers where they can be decoded. It keeps the raw text spans so later edits can splice them. It uses a tolerant scanner rather than a stock XML parser, because tags like `ListMgt::LmVersionTable` break those parsers. The version header is exposed. `.drt` is covered fully. `.drb` is best effort because its internals are still unknown.
- **Diff (S2).** A semantic diff of two files shows what an agent or a human changed between versions. Objects are matched by DbId, and every byte the reader does not decode is compared raw and reported as `opaque-changed`. Its gate mode (`aar drp diff --gate`) is S8's post-write check: it passes only when every change is decoded and DbId-matched. The gate cannot see, by construction, changes that leave both the decoded model and the compared residue identical: (a) zstd framing that decompresses to the same bytes; (b) hex letter case inside a blob the reader decodes (`FrameRate`, `Resolution`, `MediaExtents`, `Time`, `Geometry`, `Clip`, marker and settings blobs); (c) whitespace between elements; and (d) XML-equivalent attribute spellings — attribute order, quote style (`'` vs `"`) and entity-versus-literal characters — which the tolerant scanner normalizes away. Limit (d) holds only for the attributes the scanner decodes, the first 4096 of an element. The attributes of an element past that cap are not decoded; they are compared as raw bytes, from the first unread attribute to the end of the start tag, so inside that truncated tail the comparison is **stricter** than in the kept part: quote style, whitespace, entity spelling, attribute order and `/>` versus `></X>` all count as changes. That fails closed (a harmless respelling there is reported, never missed), and the reader's `scan-attributes-truncated` warning already fails the gate for such an element. A repeated attribute resolves last-wins below the cap and **first-wins past it**, because nothing past the cap is decoded: a second `DbId` there is never read, so the semantic "DbId changed" line is not produced and the pair is reported as one opaque change instead. When a `DbId` appears in the unread tail the change detail says so (a byte search for the name; a false hit only adds wording). The `DbAppVer`/`DbPrjVer` stamp is compared by its raw spelling, so a spelling-only change (`17` vs `017`, or non-ASCII digits) fails the gate. A genuine stamp *value* change also **fails** the gate on a real file: the stamp sits in the header comment of every member, including ones the reader does not interpret (`Gallery.xml`, stills), whose bytes are then compared as opaque. Bumping the stamp in only `project.xml`, or only in the members the reader interprets, fails too, but as a `version-mismatch` warning (the members no longer agree and the gate refuses any file read with warnings), not as an opaque change. A file whose stamp lived only in the decoded `project.xml` would pass a stamp change; on real files the failure comes entirely from the raw members' bytes. A project `DbId` change, by contrast, is reported but **passes** the gate — it is a single decoded header field (the project is the file's singleton, paired whatever its DbId) with no opaque collateral, so it is only listed, not failed. Because a passing gate means every change was decoded and DbId-matched, not that the changes were the ones intended, S8 must additionally compare the full change list against its intended edit set before trusting a write.
- **Modify (S8).** Only a whitelist of round-trip-verified edits is allowed:
  - rename
  - relink and path mapping (Windows drive letters to Mac `/Volumes` and back)
  - markers (add, update, delete)

  Each edit is a text-span splice plus a blob re-encode. Anything outside the whitelist is refused. Two edits that were planned are **deferred, not built**:
  - **Metadata.** It cannot be verified. The reader decodes no user-editable clip metadata (comments, keywords, scene, shot, take and camera fields live in `BtMetadataLockableBlob`, which it does not decode), so the post-write gate could not vouch for an edit. A clip's name is a rename.
  - **Fader keyframes.** No keyframe writer exists. `drp_tools` has codecs and format notes only, and its notes leave the tick encoding, the track mapping and the `AdrDatabase` checksum open. The reader does not decode `FLStudioModelBA` either.

  A project read from a Resolve disk library (S25a) is never edited: it is refused as `library-project`.

  Every write must pass the S2 gate, and its full change list must equal the plan's intended edits. Three rules bound what is edited and what is accepted:
  - **Inputs that read with warnings are refused** (`input-has-warnings`), because the gate can never pass for them. In the 64-file private corpus that is 16 files, all `blob-partial`; the other 48 can be edited.
  - **The round-trip allow-list** (`aar.drp.modify.roundtrip`) is used only to compare a file with Resolve's own re-export of it, never for the writer's output. It accepts exactly **11 opaque lines** that Resolve rewrites on every export: 3 playhead values, 3 pan/tilt preset DbIds, 2 `DbSavedTime` values, 1 project age, 1 save date inside the settings blob, and **1 save stamp in the root bin's fields blob**. The project's `LastModTimeInSecs` is accepted as a decoded header change on top of those. Each rule checks the bytes, not just the name.
  - **Files are labelled `unverified`** (`<out>.aar.json`) until the sandbox round trip exists. The label is a JSON file aar recognises as its own by the stamp it writes: a `tool` of `aar <version>`, a `label` and `status` of `unverified`, and an `output` block naming this file and this label. A `<out>.aar.json` that aar did not write is refused (`foreign-sidecar`) and both files are left untouched; a label aar wrote on Windows is recognised on POSIX when its stamp holds an absolute Windows path (drive, UNC or `\`-rooted); one with a relative Windows path is still refused there, since `sub\out.drp` is also a valid POSIX name. `--force` checks the label when the run starts and again on a snapshot (a hard link, else a copy) taken just before the label is replaced. A label that is not aar's by then is refused, nothing is written, and the snapshot is kept and named in `left_behind` (kind `label-snapshot`). A kept snapshot is renamed to `.<out>.aar.json.<8 chars>.label-snapshot.json`, a name the leftovers pattern never matches, so a later run never lists it as a stale temporary file or in an `orphan-sidecar` remove list. If that rename fails (no space, or a name past the filesystem's limit: the snapshot name is the output's name plus 39 characters), the run's result is unchanged and the snapshot is kept and reported under its temporary name, which a later run does list among the leftovers. A snapshot kept by an older aar (before S8e) still has a temporary-file name (`….tmp.json`) and is still listed among the leftovers; check it against the label before deleting it. This narrows the window but cannot close it, because rename has no compare-and-swap: a label another program writes as a new file between that last check and aar's `os.replace` (microseconds) is still replaced and lost. One written in place into the old label's file shows up in a hard-linked snapshot afterwards, which is then kept rather than deleted.
  - **Placement narrows, but does not close, the no-hard-link race.** The output and its label are written to temporary files, verified, then moved into place (the label first). Without `--force` the move hard-links onto the name — atomic, failing if the name is taken — or, on FAT/exFAT where there are no hard links, claims the name with `O_CREAT|O_EXCL` and `os.replace`s the verified temporary onto its own placeholder (`os.replace`, not `os.rename`, so it also works on Windows exFAT/FAT media, where `os.rename` fails when the destination exists). The `O_CREAT|O_EXCL` claim beats an exclusive creator or a check-then-create writer: once aar holds the name, that writer's create fails. It does **not** beat a plain non-exclusive writer (`open(dest,"wb")`, `cp`, Windows `CREATE_ALWAYS`): that writer opens and truncates aar's placeholder and writes into it, and the `os.replace` then discards those bytes. For that class of writer the window runs from the exclusive create through its close to the replace. On a failed replace aar removes the name only when it is aar's own output (same device and inode, by `lstat`). It deletes nothing else, not even an empty file: an empty file there may be another writer's (created after unlinking the placeholder, or the placeholder truncated and not yet written to), and no identity aar can record tells them apart. **A failed replace therefore leaves an empty file at the name, with no label** (the label is removed again). The same happens on Windows when a sharing violation makes the replace fail. The raised error, and the CLI's JSON (exit 74), name that file in `left_behind` (kind `placeholder`) so an agent can check and delete it. When placing the output fails, aar removes the label it just placed (or, with `--force`, restores the old one). If that cleanup fails too (for example a sharing violation on the label), the placement error is still the one raised, with the cleanup failure attached as a note and the same exit code, and aar's own label left at `<out>.aar.json` is named in `left_behind` (kind `own-label`); the next run reports it as `orphan-sidecar` (`out-exists` if a file is at the output name). When it was the `--force` restore that failed, the old output is still at `--out` and its correct label survives only in the snapshot: that snapshot is kept, never deleted, and named too (kind `label-snapshot`), to be moved back over the `own-label` file. A crash mid-move may leave aar's own partial labelled copy (an empty placeholder or the output), but never a file that was already there.

- **Create (S9).** There are two routes:
  1. Preferred: build the project with the scripting API in a sandbox, then call `ExportProject`. Resolve writes the file, so it is valid by construction.
  2. Offline: fill in a version-matched template that was exported from the target Resolve version.
- **Validation gates every write.** Each written file is imported into the sandbox library, read back through the API and compared with the intended model. If it is visual, a frame is rendered as well. A file that has not been validated is labelled `unverified` and never offered to humans.
- **Version gate.** A file is never stamped newer than the target host. Writing for an older DbPrjVer is refused unless a template for that version exists.
- **Prior art.** We port the codecs from the `drp-format` JavaScript library and from the owner's `drp_tools`. `drp_tools` supplies codecs and format notes only; it has no keyframe writer, so fader keyframes do not come from it. We do not reuse DRP-Toolkit, which is GPL.
  - **`drp-format` licence: unconfirmed.** The standalone repository `samuelgursky/drp-format` returns 404 (checked 2026-10-19). The library is vendored at `resolve-advanced/vendor/drp-format/` in `samuelgursky/davinci-resolve-mcp`. The repository's root `LICENSE` and the vendored `package.json` both say MIT, but the vendored directory has no licence file of its own and the copyright line names the repository's contributors, not the library's author. We therefore treat the licence as MIT per the host repository and unconfirmed for the directory; `tests/fixtures/drp/README.md` records the commit the four template files come from.
- **Blocked on approval.** S8 and S9 need permission to use the edit PC's empty Local Database as the sandbox. Switching databases closes the open project.

### R2. Blackmagic Cloud

- Cloud work happens only through the node (F1). The node can:
  - list cloud projects in the current library
  - load, create, import or restore a cloud project with `CloudSettings`
  - read each clip's Cloud Sync status
  - set `liveCollaborationMode`
  - check freshness with `RefreshFolders` and `GetIsFolderStale`
- **Media.** Before a build, the node checks the sync status of the project's media. It flags proxy-only sync, because in our setup proxies have no audio.
- **No direct database access.** The node never connects to the cloud library's database. That is unsupported and puts the shared library at risk.
- **Review.** Presentations have no API, so review happens in our console as a render plus timecoded notes. A human can still post a Presentation by hand. Its comments come back as timeline markers, which the node can read.
- **Limits.** The free tier allows 2 GB of storage and 20 presentations. Libraries are paid.

### R3. Collaboration between Resolve Studio users

Resolve already handles the hard parts on cloud libraries (locks, Live Save, chat, Compare Timelines). This app adds the layer above:

- **Presence and leases** across humans and agents. They are shown in the console and returned to agents in tool results, for example "bin X is held by a human since 14:02".
- **Agent branch timelines.** Agents never edit a human's timeline. An agent duplicates it to `<timeline> [agent:<id> v<n>]`, edits the copy, renders a review, and a human merges it with Compare Timelines (21.1). This rules out lock fights by design.
- **Review threads** anchored at timecode, plus approvals and handoff notes, all stored in the hub. They can be mirrored to timeline markers so humans see them inside Resolve.
- **Shared per-project facts:** sync and angle offsets, gains, template traps and path maps.
- **Remote collaborators**, Mac users included, need only Resolve Studio and access to the cloud library. The console is a web page.

### R4. Several projects at once on one machine, one user

Each Resolve instance has one current project (F3), and a second instance is unproven (F4). The plan follows from that:

- **Cold work** for any number of projects runs in parallel.
- **Hot work** is time-sliced by the broker:
  - per-project queues, batched so Resolve switches projects less often
  - leases
  - context saved and restored around every switch: project, timeline, page, playhead, Deliver settings and bin
  - a presence guard that refuses to switch while a human is working. "Working" is a heuristic: recent input, or the page or playhead has moved.
  - **Resolve 21.1 traps: never poll Deliver state.** `Project.GetCurrentRenderMode()` raises a "Main view page is changed to 11" signal on every call. Read with the rest of the context on every 0.25 s worker tick, it crashed Resolve 21.1 after about 270 reads (live 2026-11-07). `GetCurrentRenderFormatAndCodec` was not tested, so it is treated the same way. The presence poll therefore reads only the working position (`get_position`: project, timeline, page, playhead, bin, Project Manager folder and whether a render is running), at most once per `context_poll_seconds` (default 2 s, `aar node run --context-poll-seconds`, at least 0.5 s and below the presence guard's configured maximum observation age, `max_observation_age`, default 30 s). Deliver state is read only off the poll path: by the snapshot when the broker borrows the human's context, by one check before the restore and by the restore's final check (three reads per borrowed context), inside `render.build`, and once after an op in the human's project that reports changing them (`note_deliver_changed`: the gateway's Deliver setters report themselves, and `render.build`, which drives the API directly, reports a failed restore of its own). **A human's Deliver edit is kept, unless an op in the same project then reports its own Deliver change** (today only `render.build` when its own restore fails, and its snapshot preset keeps the human's edit): the poll cannot see one, so the check before the restore compares the Deliver settings with what the broker last left there (the snapshot's, unless an op reported changing them). If they differ, a human changed them while the broker held the context: the broker keeps them, restores only the position, and records `deliver_restore_skipped: human_change` with the fields (in the restore report, the `restored` event and a node-log warning).
  - **Input idle is read only in the console session.** On Windows the guard reads keyboard and mouse idle time with `GetLastInputInfo`, which sees only the calling process's session. So the node checks first that it runs in the active console session (`ProcessIdToSessionId` against `WTSGetActiveConsoleSessionId`). In session 0 (a Windows service), in any other session, with no one attached to the console, or when either call fails, it reports `input_idle_error` and refuses to switch: fail closed, because there the idle would read as huge while a human types. The node must run in the interactive user's session, as a logon task, not a service. **Known limit:** a human working over Remote Desktop has a session that is not the console session, so the node refuses to switch while they are connected. That is the safe direction; revisit it in S15b, where `aar node run` is decided.
- **Renders.** Render jobs queue per project. S14 tests whether a `-rr` render node or a `-nogui` instance can run beside the GUI on the same PC. If neither can, renders are time-sliced too.
- **Fallback.** Truly parallel hot work needs a second Resolve instance. If S14 fails on Windows, that means a second machine or VM using Studio's second activation.
- **Collisions.** The broker also fixes today's thread collisions (F10).

### R5. UI and UX designed for agents

Agents are the primary users. Humans get a thin supervision console.

- **Task-level, typed tools** rather than mirrors of the Resolve API:
  - finding and describing: `project.find`; `timeline.describe`, which returns text a model can read (tracks, items with source timecode, gaps, markers)
  - analysis: `analyze.transcript`, `analyze.laughs`, `analyze.faces`, `analyze.loudness`
  - planning: `plan.lint`, `plan.apply(dry_run)`
  - looking: `frame.grab`, `frame.contact_sheet`
  - output and checks: `render.review`, `qa.check`, `review.request`
- **One EditPlan JSON for every build.** It holds source ranges with exclusive ends, tracks, transitions, audio gains, titles and a rule profile. The plan is linted against house rules before any Resolve call. A dry run returns a diff of what would change.
- **Every result carries measured values** from deterministic tools (frame counts, LUFS, durations). Errors are structured and include a fix hint and the known trap that caused them.
- **Everything resumes.** Jobs have ids and checkpoints, and the event log lets an agent replay its state after losing context.
- **Humans get four things:** a review queue (render plus timecoded notes), approve or reject, a board of who holds what, and an emergency stop.

**Analysis workers (S13c1).** `aar.analyze` holds the cold workers behind `analyze.*`, as a library and the `aar analyze` CLI; they register no node ops yet (the job wiring comes later, per F9). `aar analyze transcript` runs faster-whisper (extra `whisper`; the CCN preset is medium.en, int8 on the CPU, beam 5, VAD with a 400 ms minimum silence, no conditioning on previous text) and writes a `Transcript` in recording time, `file time + recording_origin / fps`. It checkpoints every segment, resumes with `--resume`, drops hallucinated segments by faster-whisper's own thresholds and lists each drop in its report. Models are never downloaded: a name is looked up in the shared model directory `$AAR_MODEL_DIR` (outside the worktrees), and a missing model is an error. `aar analyze sync` (extra `analyze`, numpy) measures each file's offset against a reference with GCC-PHAT anchor windows, a consensus, and a drift fit over the overlap, and returns one status per pair: `ok`, `drift`, `low-confidence` (candidates, never a number), `no-overlap` or `failed`. `offset_s` is where the other file's first sample falls on the reference's clock, so `other.recording_origin = reference.recording_origin + offset_s × fps`. Both follow the `aar qa check` exit codes, and `aar qa check --whisper-model` uses the same adapter for `join-retranscribe`.

**Far-field transcripts (S19d).** A show recorded only by one camera's room microphones (mean about −40 dBFS) loses quiet speech in Whisper's VAD: on the S19 pilot a 90-minute show came back with exit 0 and no words for 20 minutes of continuous speech. `aar analyze transcript --normalize` (`WhisperSettings.normalize`, off by default, so outputs without it are unchanged) passes the mono mix through one fixed ffmpeg filter, `aar.analyze.audio.NORMALIZE_FILTER` = `dynaudnorm=f=250:g=15:p=0.9:m=30` (a gain per 250 ms frame, Gaussian-smoothed over 15 frames, peaks aimed at 0.9, at most 30× gain), inside the existing decode (`read_mono`, same timeout and duration cap). It changes level only: the sample count and every onset stay where they were, so word times stay in file time (tested on a synthetic file, within 20 ms). When on, the filter is in the checkpoint's settings hash, so `--resume` refuses a checkpoint made with the other setting; when off the hash is unchanged, so older checkpoints still resume. The report records `settings.normalize` and `audio_filter`. **Wordless stretches:** the report's `wordless` lists every stretch of at least `wordless_min_s` (`--wordless-min-s`, 60 s) with no kept word, the file's head and tail included, in recording and file time, with the source's level over it (RMS of the un-normalised mono mix in dBFS, from the decode already in memory or, with `--normalize`, one more bounded decode of that stretch for at most the 20 longest stretches). A level not measured, or whose decode failed (the media gone, ffmpeg failing), is null with a `level_error` (its type, or `not-measured`), and never fails the transcript: the words are in hand; after one failed decode the rest are not tried. `--wordless-min-s` is at least 1 s. The CLI prints one warning line on stderr with the total and the longest; the exit status is unchanged, because a real show has a silent house before it starts. **No words is not silence**: a stretch may hold speech the transcriber missed, or applause. `aar analyze transcript-text TRANSCRIPT --out FILE [--gap-s 0.7] [--max-chars 120] [--wordless-min-s 60] [--force]` (`aar.analyze.text.render_text`) renders a Transcript for a model choosing what to keep: one `[start-end] words` line per spoken run in the transcript's clock (recording seconds), zero-padded to one width, a new line at every gap longer than `gap_s` and before a line would pass `max_chars`, and every gap of at least `wordless_min_s` as its own `(no words transcribed)` line. Gaps are measured from the furthest end any earlier word reached, so overlapping words never open a false hole, and boundaries compare with a 1 µs tolerance. Control characters in word text are dropped. It is deterministic, validates the transcript with the plan loader (and refuses non-finite times or times past 10^7 s as `invalid-transcript`), refuses an existing output without `--force`, and refuses to write over its own input even with `--force`. Only gaps between words show there; the head and tail are in the transcript report.

**Analysis workers, part 2 (S13c2).** `aar analyze faces` writes `aar.faces/1`: OpenCV's YuNet face detector (extra `faces`, never in `dev`) on frames sampled at `--sample-fps` (default 2). The model is `--model` or `$AAR_YUNET_MODEL`, an existing file that is never downloaded; its sha256 and size go in the header with the settings, the input's size and mtime, the source and sample frame rates and the frame size. ffmpeg emits each sample at the display size, so a 90 or 270 degree rotation swaps width and height and the long side is at most `--max-side`. Sample i is the frame on screen at `i / sample_fps` (within one source frame, `time_tolerance_s`). Boxes and five landmarks are normalised to [0, 1], clamped, sorted largest first and rounded to 4 decimals. Non-finite and zero-area detections are dropped and counted, and a short final read is reported as `truncated_tail`, never parsed. It checkpoints every frame like the transcript, and a resumed run gives byte-identical output. `aar analyze laughs` writes `aar.laughs/1` and optionally a `LaughMap`. It extracts the whole file's audio to a 16 kHz FLAC, asks Gemini with the versioned prompt `LAUGH_PROMPT_V1`, saves the raw reply, and checks every laugh against the audio. **The credential** is a Gemini API key, read only from the environment (`AAR_GEMINI_API_KEY`), sent only in a request header, and never written anywhere: not argv, a URL, a log, a report, the work dir or an error message. **The paid call** needs `--allow-paid`; without it the command exits 2 before any network use, and `--from-raw` re-parses a saved reply offline. **No redirects** are followed, because urllib would copy the key to the new host, and every request must go to the API's own host. **The parser** is strict. Every dropped item is reported with its index, its reason (`bad-item`, `bare-number`, `bad-time`, `bad-level`, `unknown-kind`, `reversed` or `out-of-range`) and an excerpt. **The envelope cross-check** compares a 10 Hz RMS envelope over [start − 1, end + 2] with the median of the 8 s before it. A laugh is `confirmed` when `bump90 ≥ 6.0` dB and `frac6 ≥ 0.10`; both thresholds are tunable starting values, to be set on real material. With too little baseline or digital silence a laugh is `unchecked`, otherwise `unconfirmed`. **The onset is refined** on a 50 Hz envelope: the first 20 ms frame more than 6 dB above the baseline that stays more than 3 dB above it for 200 ms, within 1 s before to 1.5 s after Gemini's start. End-on-laugh lands on this onset. Laughs within 0.25 s merge. The map holds confirmed laughs (all of them with `--include-unconfirmed`). **Applause never enters a laugh map**; it is listed separately. A whisper model name looked up in `$AAR_MODEL_DIR` must resolve inside that directory, symlinks and `refs/main` included (`model-outside-dir`), while an explicit model path is taken as given.

#### The EditPlan (version 2)

`aar plan schema` prints the JSON Schema; `src/aar/plan/model.py` is the reference. Positions and lengths are integer frames at the plan's `fps`, and every range is half-open, `[in, out)`. The published schema is an approximate contract, and the model is authoritative at the numeric edges: a JSON number such as `24.0` as the frame rate or `1.0` as the version passes the schema's `integer` test, but the model refuses it. The same goes for the frame rate's text form: fps text padded with non-ASCII whitespace (a no-break space, say) is refused by the model but accepted by the schema, so the schema errs on the safe side.

- **Version 1 fields** (S5): `project`, `timeline`, `kind` (`longform` or `short`), `fps`, `resolution`, `profile`; `sources` (id, media, camera, shot size, recording id and origin, duration); `segments` (track, source, `src_in`/`src_out`, `record_in`, keyframed `reframe`, `gain_db`); `transitions` between neighbouring segments (video type and length, audio transition); `titles` (lower thirds are `kind: "lower-third"` with a template name, lines and a record in/out); `captions` and `caption_style`; `markers`.
- **Version 2 adds** what the S13 producers and the `plan.apply` compiler need:
  - `template`: the timeline the build starts from. The compiler branches it with `timeline.branch`, never `timeline.duplicate`, so the copy is a registered agent branch.
  - `head`: how the first segment comes in from black (video type and frames, audio fade-in frames).
  - `outro`: the clip appended where the content ends (source id, optional source range, video track, the name of the audio track that carries it, the transition into it, and optional `sting` text over its start). The outro is not a content segment. Content rules (chronological, dialogue splice, end on the laugh, cut density) see the last content segment as the end. The outro does count towards the timeline length, so `short-max-duration` includes it.
  - `audio_tracks`: per-track name, `gain_db`, `mute` and optional `bus`, in track order (A1 first), so the CCN topology can be stated: A1–A4 muted, A5 the bus, A6 the bounce. Names are unique.
  - `Source.color`: input colour space, an optional CDL (slope, offset and power as three numbers each, plus saturation) and an optional LUT name. The safety rule still holds: never set the input colour space on BRAW. The linter's `no-braw-input-color-space` rule reads the `media` text alone: it is BRAW when the path ends in `.braw`, in any case, with surrounding whitespace trimmed. A URI (`scheme://...`) loses its query and fragment first; anything else is a local path and is tested whole, so a name such as `take #3.braw` still counts. The real clip is checked at apply time.
  - `Source.frame_size` (S18): the media's **display** size `[width, height]` (after pixel aspect and rotation, not the stored pixel size), two whole numbers above zero (or any size with the display aspect, such as a face track's sampled size). Reframe `x`/`y` are shares of the source picture, and `zoom` 1.0 is the source filling the frame (the tallest crop the timeline's aspect allows). `aar plan produce` sets it (see Plan producers, framing). `plan_hash` leaves it out while unset, so older plans keep their hash.
  - `Source.start_timecode` (S18 round 4): the media's embedded start timecode as a frame count from 00:00:00:00 at the source's rate, a whole number from zero (drop-frame timecode counts the frames it labels: 01:00:00;00 at 29.97 is 107892; 01:00:00:00 is 86400 at 24 and 108000 at 29.97 non-drop). Source positions still count from the file's first frame. The FCPXML export writes each asset's `start` at it, because Resolve links a clip to its file only then. `aar plan produce` reads it from the media's `timecode` tag (video stream, then a tmcd or other stream, then the container) at the video stream's rate, else (S18a) from a `.braw`/`.mov`/`.mp4` file's tmcd track with `aar.media.quicktime`; a stub value wins, with a warning when the media disagrees. `plan_hash` leaves it out while unset.
  - `Source.start_timecode_rate` (S18 round 4, fix-check Q3): the frame rate `start_timecode` is counted at, the media's own (`{num, den}`, or the fps shorthands); unset means the plan's fps. The producer sets it from the same probe: the video stream's rate snapped to a standard rate (S18a round 2: BRAW's video stream averages 2953125/98536, which is on no 29.97 frame; snapped it is 30000/1001); the export converts the timecode to time with it (a 25 fps file at 01:00:00:00, 90000, starts its asset at 3600 s in a 24 fps plan). `plan_hash` leaves it out while unset.
  - `Segment.transform`: a static zoom, pan, tilt, rotation and flips, separate from the keyframed `reframe`. The effective zoom is the transform's zoom times the reframe zoom; `no-same-camera-jump` uses it.
  - `end_fade_frames`: the audio fade-out at the very end of the timeline.
- **Versioning rule.** `version` is 1 or 2, and a plan that leaves it out is version 2. Version 2 only adds fields, so every valid version 1 plan is valid, and lints the same, as version 2. A plan that says version 1 and gives a version 2 field a value is a validation error (`plan_version`) naming the field, for example `segments[1].transform`. Null, or an empty `audio_tracks`, is not a use, so a full dump of a version 1 plan reads back as version 1. `tests/plan/fixtures/v1_compat` pins the pre-v2 profile and the reports the pre-v2 code wrote for the plan fixtures; linting them today must give the same bytes.
- **Where problems are reported.** Version 2 cross-references are validation errors (exit 2), each with the field's location: an outro source that is not a plan source, an outro that plays to the end of a source with no duration, an outro range outside its source, a sting longer than the outro, an outro audio track not in `audio_tracks`, duplicate track names, a blank template or name, a CDL triple that is not three finite numbers in range, and a head or outro transition whose type and length disagree (a cut has no length; anything else needs one). The version 1 checks stay lint findings in `ranges-valid` (exit 1), so version 1 plans lint exactly as before.

**Rules.** The `ccn` profile runs these; the thresholds are in `profiles/ccn.toml`, not in code.

| Rule | Severity | What it checks (ccn values) |
| ---- | -------- | --------------------------- |
| `ranges-valid` | error | Ranges positive and inside the media, no overlap on a track, unique source ids, transitions that follow a join |
| `chronological` | error | Each recording plays forward only |
| `no-dialogue-splice` | error, warn | No cut inside a word (error); a cut sits in a pause of at least 250 ms (warn). Needs a transcript |
| `no-same-camera-jump` | error | Same camera across a time jump needs a zoom change of at least 0.2 (static transform included) |
| `timejump-close-to-wide` | warn | A time jump cuts to a wider shot |
| `no-dissolve` | error | Cuts between content segments. **New:** the head and the outro transitions are allowed when the profile says so (`allow_head`, `allow_outro`), up to `max_head_frames` / `max_outro_frames` (30, which admits the 15-frame start dissolve). Without those keys only cuts pass |
| `audio-crossfade` | error | Non-continuous joins get a "Cross Fade 0 dB" of at most 30 frames with enough handle |
| `cut-density` | warn | **New.** No more than `max_cuts` (2) cuts in any `window_s` (10 s) of record time. Overlapping offending windows merge into one finding with the burst's span and cut count |

A rule's thresholds are either required (every profile listing the rule sets them) or optional with a code default. A rule can also check its threshold values, and a bad value is a profile error (exit 2) before anything is linted.

The join-based cut rules (`cut-density`, `no-same-camera-jump`, `timejump-close-to-wide`, `audio-crossfade`, and the neighbour hint of `min-shot`) consider same-track joins only, meaning neighbouring segments on one track, so an overlay entry on another track and the cut into the outro are not counted as cuts. `no-dialogue-splice` (`src/aar/plan/rules/speech.py`) also uses same-track joins, to spot unbroken continuations, but it does not count cuts.

### R6. CCN work end to end

Recipes turn the existing, proven pipeline (the CCN shorts and long-form workflow, thumbpipe, the supoclip runner) into a work graph. The steps are:

1. Brief.
2. Locate sources (cloud project, offline media).
3. Flatten multicam and apply offsets.
4. Transcript and laugh map.
5. Cut plan, rule-checked.
6. Resolve build from the template: lower third, sting, outro, A5 bus.
7. Camera match.
8. Crossfades and loudness.
9. Review render: `render.build` sets the output size and quality, then `aar.deliver` fits it under the review cap.
10. QA: re-transcribe the joins, LUFS, offline frames, colour.
11. Human review loop: the review render is stored, QA'd and sent for a human decision.
12. Master render: `aar.deliver` pulls it, hashes and stores it, and records its QA facts.
13. Shorts, then captions.
14. Thumbnails (thumbpipe).
15. Publish: YouTube through Command Center, Instagram through ccn-web-app.
16. Archive and update the project facts.

House rules ship as a rule profile, `ccn`:

- Never splice dialogue, and keep ranges chronological.
- No whip-pans, and no same-camera jump cuts.
- End hard on the laugh.
- Cut close to wide at time jumps, with no dissolves.
- Audio crossfades are at most 30 frames and sit in room tone.
- Loudness: about -22 LUFS for long-form, about -14 to -15 LUFS for shorts.
- Shorts run under 37 s.
- Captions: at most 16 characters, Montserrat, active word in yellow.
- Review MP4s stay under 20 MB.

Other shows get their own profiles.

#### R6 decisions for S13 (2026-10-19)

These are defaults taken from the owner's recorded feedback on real CCN cuts. Each one is a profile value or a recipe parameter, so it can change without code.

- **End on the laugh means its onset.** The last frame lands between the laugh's onset and 400 ms after it: "end hard right after the punchline word or at the first hint of laugh, no dragging laugh, never fade to silence". A short's audio fade-out is a de-click (at most 1 frame), never a fade to silence. Long-forms end on the laugh, then the outro.
- **Dissolves.** None between content segments. A transition in from black on the first segment and the transition into the outro are allowed (the real long-form build uses a 15-frame start dissolve).
- **Cut density.** Warn when any 10 s window holds more than 2 cuts ("8 cuts in 13 s" was "extremely choppy"; 5 cuts in 50 s was accepted).
- **Shortest shot.** Warn under 1.0 s; fold slivers into a neighbour.
- **Pause trimming is a planner parameter, not a lint rule.** Trim pauses of at least 0.9 s down to a beat of about 0.45 s. The silence threshold is per venue: -42 dB by default, -36 dB where room laughs sit at -36 to -40 dB. QA reports the longest silence left in the output.
- **Joins sit in source-audio quiet.** Transcript word gaps are not enough, because Whisper word times are off by 0.1–0.2 s at joins. The in-side of a join needs at least 60 ms below -40 dBFS in the source audio. After the render, 2–3 overlapping short-window transcriptions around each join must agree with each other and with the plan's words.
- **Loudness.** Shorts get gain plus a limiter, not two-pass loudnorm, which flattened the laugh-to-voice range and padded the tail. Targets: -14.5 ± 0.5 LUFS for shorts, -22 ± 0.5 for long-forms. True peak at most -1.0 dBTP, no clipped samples, and the duration is unchanged.
- **Captions.** Every kept word is captioned (words snapped equals words captioned).
- **Where work runs.** Cold work (analysis, planning, QA, shorts compose) runs on the hub host. Resolve, its renders and the masters stay on the edit PC. Files move through one transport module that checks size and sha256.
- **Builds start from the template with `timeline.branch`,** so the copy is a registered agent branch. A human merges it.
- **Shorts compose with ffmpeg first** (a port of the proven runner). The Resolve template route comes later through the `plan.apply` compiler.
- **Publishing.** aar's last step emits a publish packet (final file and its hash, metadata, thumbnail) and waits on a human approval. Command Center and ccn-web-app do the upload; aar holds no YouTube or Instagram credentials.
- **Hub writes.** Agents create brief, plan and recipe nodes through hub write tools. Deciding a review stays human-only.

#### Media QA (S13b)

`aar.qa.check(file, kind=..., profile=..., plan=..., transcript=..., transcriber=...)` and `aar qa check FILE --kind short|longform|review` measure a render with ffmpeg and return one entry per check: id, status (pass, warn, fail or skipped), measured values, the target, and a one-line message saying what to do. Thresholds live in the profile's `[qa]` block (`QATargets`). Every key added after `review_mp4_max_mb` has a default, so an older profile still loads. `aar.media` runs ffmpeg and ffprobe from `AAR_FFMPEG`/`AAR_FFPROBE` or `PATH`. It passes argument lists only (the path goes in as `file:<absolute path>`), gives every call a timeout that kills the process group, keeps a bounded stderr tail, and raises `MediaError` with the exit code and that tail. The CLI exits 0 when no check failed and 1 when the checks ran and one failed, including media that exists but does not decode (a failed decode check). It exits 2 when the input or a tool cannot be located or opened, or the profile is invalid.

| Check | Definition | Parameters |
| ----- | ---------- | ---------- |
| decode | ffprobe reads the file, and a full `-xerror` decode of every video and audio stream prints no error and exits 0. A file ffprobe cannot read fails here, and the render checks below are skipped as `render-unreadable`. | none |
| loudness | ebur128 on the first audio stream: integrated I within the kind's target ± tolerance (inclusive), and true peak (4x oversampled) at most the maximum. LRA is reported only. `review` uses the long-form target. A render without audio fails. | `short_lufs` -14.5, `longform_lufs` -22, `lufs_tolerance` 0.5, `true_peak_max_dbtp` -1.0 |
| clipping | A clipped sample is a decoded 32-bit float sample, in any channel, whose magnitude is at or above the clip level. When the astats sample peak is below the level, the count is 0 without a scan. Otherwise every sample is counted in pure Python, so a long master that reaches the level can run into the call's timeout (which then fails the check). NaN or infinite samples also fail. A clipped square fails and a -6 dBFS sine passes. | `clip_level_dbfs` -0.01 |
| longest-silence | ffmpeg silencedetect: a silence is every sample of every channel below the threshold for at least `silence_min_s`. The check reports the longest silence and where it starts. It passes unless `longest_silence_warn_s` is set and the longest silence is longer, which gives warn. | `silence_db` -42 (the CLI `--silence-db` or the `silence_db=` argument sets a venue value such as -36), `silence_min_s` 0.2, `longest_silence_warn_s` off |
| size-cap | `review` renders only: at most `review_mp4_max_mb` decimal MB (1 MB = 1,000,000 bytes). Other kinds are skipped as `not-applicable`. | `review_mp4_max_mb` 20 |
| duration | The render's video stream (else its audio stream, else the container) lasts the plan's record duration (`total_frames()` at the plan fps), within the tolerance in frames, inclusive. | `duration_tolerance_frames` 1 |
| join-quiet | Applies to every cut, meaning a join that does not continue the same recording within `join_continuity_tolerance_frames`. The check decodes the incoming source's first audio stream over [src_in − S, src_in + S], clipped to the start and end of the source, at 48 kHz. A window of `join_quiet_window_ms`, starting at any sample, is quiet when the RMS of its loudest channel is below `join_quiet_db`. A quiet run is the union of overlapping quiet windows, so its length is exact to the sample. The cut passes only when a run of at least `join_quiet_min_ms` contains src_in, allowing `join_quiet_slack_ms` at either end of the run: the incoming clip must start in the pause, not near it. When a cut fails, the scan becomes the fix hint. The nearest run of at least the minimum inside the window (the longer one on a tie) is reported with a suggested src_in, the frame at the plan fps nearest that run's middle ("move src_in of join N to frame F"). If there is no such run, the hint says there is no pause within ±S. Each join reports the run at the cut, the nearest pause, the longest run and the quietest window. S must cover the minimum plus the slack, so the window never shortens a run that contains src_in. With the default S, a pause whose qualifying part ends more than 40 ms before src_in is outside the window and gets no suggestion. | `join_quiet_db` -40, `join_quiet_min_ms` 60, `join_quiet_slack_ms` 10, S = `join_quiet_search_s` 0.10, `join_quiet_window_ms` 10, `join_continuity_tolerance_frames` 1 |
| join-retranscribe | Applies to every cut. An injected `Transcriber` (`aar.qa.Transcriber`) transcribes `join_windows` windows of the render, each `join_window_s` long, centred on the join and offset by `join_window_step_s`. The windows are compared on their overlap less `join_window_edge_s` at each end. A word is in that region when its midpoint is. Every pair of windows, and every window against the plan's expected words, must reach a difflib ratio of `join_agreement_min`. The expected words are the source transcript words, mapped through the plan. A source word that the cut slices by more than `word_straddle_s` on both sides fails the join, and so does a transcriber exception. | `join_windows` 3, `join_window_s` 4.0, `join_window_step_s` 0.5, `join_window_edge_s` 0.25, `join_agreement_min` 0.8, `word_straddle_s` 0.03 |
| caption-coverage | Every kept word is covered by a plan caption in record time. A kept word is a transcript word whose midpoint lies inside a kept segment's recording range, and it is covered when its record midpoint lies inside a caption's [record_in, record_out). The check lists the uncovered words. A short with no captions fails. A long-form or review plan with no captions is skipped. | none |

Skipped never means passed. A check is `skipped` only when the caller chose not to give an input (`no-plan`, `no-transcript`, `no-transcriber`, `no-captions` for a long-form or review plan), when the render could not be read or has no audio (`render-unreadable`, `no-audio`, which always come with a failed decode or loudness check), or for the size cap on a render that is not a review (`not-applicable`). Every skip carries a `skip_reason` and a message that says what was missing. A check that ran but could not check everything sets `incomplete` and puts the cause in `measured["unchecked_reason"]` and in its details. This covers a join check whose plan sources cannot be read (`source-unreadable`: the file is missing, the path is not local, or the source has no audio), a transcript that does not cover the recordings on both sides of a cut or under every segment (`transcript-does-not-cover`), and a truncated silence log (`log-truncated`). Such a check warns, or fails if something it did check failed. When nothing could be checked it warns, so it never looks better than a check that ran. The report's status is the worst status among the checks, and a skip counts as neither pass nor fail. The report's `unchecked` list names every check that was skipped or incomplete, so a runner can tell an all-clear (pass with an empty list) from "not checked" without parsing messages. The CLI prints that list under its head line. QA targets must be finite numbers: TOML allows `nan` and `inf`, and the profile refuses them. Any measurement that fails, including an ffmpeg error or a timeout, is a fail that carries the tool's message. Missing ffmpeg or ffprobe raises an error rather than producing a report in which every check is skipped. Source media paths in a plan are local hub paths. A relative path resolves against the plan file's folder in the CLI, or against `media_root` when the library is called. S13f adds the map from edit-PC paths to hub paths. Plan version 2 (S13a) works as is: `duration` measures against `total_frames()`, which includes the outro, and the step into the outro is the outro's transition, not a content cut. A v2 plan still does not say which audio track carries each segment, so every content join on a video track is treated as an audio cut.

#### Plan producers (S13d)

`aar.plan.produce` and `aar plan produce STUB --transcript T --keep K --out PLAN` turn analysis outputs and a keep list into an EditPlan v2 that lints clean. They are cold and deterministic: the only media access is ffmpeg decoding the source audio for pauses and joins. Every parameter is in the profile's `[produce]` block (defaults in code, so a profile without the block still loads); the cut-in-quiet test reuses `[qa]` `join_quiet_*`, so the planner and QA cannot drift apart. **The governing rule: the producer never plays material the human excluded, and never removes a word.** No edge, nudge, fold or ending moves outside a keep range.

- **Inputs**, each validated at the boundary with a typed `ProduceInputError` (exit 2): a **plan stub**, an EditPlan with no segments or transitions, whose `sources` are the source list and whose other fields (template, head, outro, audio tracks) pass through; the **transcript** (`aar analyze transcript`), which must name its recording (`transcript-unnamed`), and that must be the cut's recording; a **keep list**, `{"recording"?, "ranges": [{start_s, end_s, label?}]}` in recording time, chronological; optionally **sync** (`aar analyze sync`: each `ok` pair sets its source's origin; any other status is refused), **face tracks** (`aar.faces/1`, bound to the source whose media is the measured file; faces are sorted by size here, never trusted in file order), a **laugh map**, and a **camera schedule** `{"spans": [{start_s, end_s, camera}]}`, a camera being a `Source.camera` label or a source id. A label shared by sources that follow one another on the recording clock (one camera's consecutive files, S24a; sources of one label that overlap stay `ambiguous-camera`) names all of them: a range on it is split where one file ends and the next begins, and the two pieces play as one shot (no transition, the same framing level, and a piece is a sliver only when the whole shot is). A keep range that crosses a gap between two files of the camera on screen is cut at the gap (`range-crosses-gap` warning, with the gap's place and length), and a range whose start or end lies in a gap starts or ends at the file beside it (`range-edge-in-gap`, likewise): the frames with no file are left out, with the crossfade's handle at each file edge the range meets there and any word an edge would split, as a keep edge does, and a run of files left between gaps (or between a gap and the range's edge) shorter than `min_shot_s` goes too, named in the warning; the cut is then judged like any other. One change for single-file plans too: two keep ranges whose inward-rounded edges meet on the same frame play unbroken (not a cut), and the framing level now carries on across them instead of dropping back to 1.0. A range wholly in a gap is `range-in-gap`, naming the camera, the range and the files' spans; one past the last file is `camera-does-not-cover`. A sync pair naming a part the stub placed (`part_placement`) is refused `sync-part-placed`. Without a schedule, `default_camera` is on screen throughout. **Automatic speaker-driven camera switching is out of scope:** the cameras come from the schedule. All cameras of one cut share one recording.
- **Keep edges move inward only.** Touching ranges merge first (they play unbroken, so a word across the seam stays), and edges round inward to whole frames. An edge inside a word (the `no-dialogue-splice` test, `word_at`) moves inward past it, the in point to the word's end and the out point to its start: the partial word goes with the material the human excluded, and the range never grows. Each word an edge cuts through is named in a `keep-edge-cuts-word` warning (its text, time and edge). Where transcript words touch, the frame nearest the shared boundary is allowed, so a boundary with no frame inside the tolerance does not pass whole words. Where they overlap, a whole word can go with it, and a `keep-edge-drops-word` warning says so. A range this empties is dropped with a `keep-dropped` warning; one that falls under `min_shot_s` is refused (`keep-too-short`).
- **1. Pause trim.** `[produce] pause_trim` (default true; TOML `true`/`false` only, anything else is a profile error) or `aar plan produce --no-pause-trim` / `--pause-trim` (the library's `produce(pause_trim=)`, None or a bool, which wins over the profile) switch it. Off, this step does nothing and the pause scan never runs; every other step (keep edges, joins in quiet, sliver fold, end on the laugh, the camera path) still runs, and the report's `log.pause_trim` says whether it ran and whether the profile or the argument decided. It suits a multicam show with a board feed; on one camera with room audio, quiet speech and audience reaction sit below `silence_db`, so trimming removes real material and every trim is a jump cut (the S19 pilot: 63 s of 236 s in 26 cuts). Off, the pilot's two keep ranges give 2 segments and 1 cut. A pause is a quiet run of the scheduled camera's audio (10 ms RMS of the loudest channel, `aar.media.quiet_runs`, below `silence_db`: −42 dB, or a venue's, e.g. `[produce.venues.loud]` −36 dB), never a transcript gap. Runs that meet at a scan chunk's edge or a camera change join. A pause strictly inside a keep range and at least `min_pause_s` (0.9 s) long keeps `beat_s` (0.45 s): `beat_lead_s` (0.25 s) after the outgoing speech, the rest before the incoming. A transcribed word inside a quiet run splits it, so no trim removes a word; every word occupies at least `min_word_ms` (40 ms) around its middle, so zero-length and 15 ms words count too. A source longer than `no_pause_warn_s` (60 s) whose kept parts hold no quiet stretch at all, not even between words (silent audio, or the wrong venue threshold), gets a `no-pauses` warning.
- **2. Joins in quiet.** Every cut's in point must pass QA's join-quiet test (`aar.qa.scan_join_quiet`: a run of at least 60 ms below −40 dBFS containing src_in). A human cut (between keep ranges) also needs the crossfade's incoming handle inside that run, and its out side checked on the outgoing audio envelope: one quiet run from `out_quiet_preroll_ms` (20 ms) before src_out to the end of the outgoing handle, so the kept tail holds no real word tail that Whisper ended early, and the fade-out holds no onset of the next removed word. A failing point moves up to `join_nudge_ms` (150 ms, in whole frames rounded down), nearest first, to a passing frame that adds or drops no word, keeps the cut a cut and leaves the shot foldable: at a human cut inward only (the in point later, the out point earlier), inside a keep range either way. Otherwise it stays and a warning names the join (`join-not-quiet`, `join-out-not-quiet`). When the media has no frame for the crossfade's handle, the point moves to the first frame that has one if that frame passes, else `ProduceError("no-handle")` names the cut.
- **3. Sliver fold.** A shot under `min_shot_s` (1.0 s) folds within its own keep range, never across a human cut. Across a camera change it merges into the neighbour; across a trimmed pause the trim is re-run: the sliver grows into the pause just far enough to last `min_shot_s` and the rest stays trimmed, and only a pause too short for that comes back whole. The option that brings back the least removed audio wins, the previous side on a tie. A sliver with no option is an error.
- **4. End on the laugh.** With a laugh map, the content ends `end_after_ms` (200 ms) after the onset of the latest laugh in the final keep range (at least the end-on-laugh rule's `min_strength`). Content after it is dropped, with an `end-dropped-speech` warning saying how much when it held words. The out point stays inside the final keep range and the piece ending there must belong to it, so a laugh at the range's first frame never stretches the previous range across the human's cut. A frame inside a word moves to the nearest clean frame inside the rule's window; with none, the ending stays and a warning says so. `end_after_ms` must lie inside that window.
- **5. Framing.** A same-camera cut steps the framing: a long-form toggles `Segment.transform.zoom` 1.0 ↔ `punch_in_zoom` (1.25); a short cycles the `[[produce.framing]]` presets (A zoom 1.0, B zoom 1.22 with y 0.45, the house limit for a shorts punch-in), which must differ by `no-same-camera-jump`'s 0.2. A short's reframe follows the face track's largest face with the supoclip `steady()` path (`[produce.steady]`: dead zone 0.25 crop widths, Gaussian glide σ 0.7 s, the edge-safety passes), then a clamp into the picture and a slew limit at `speed_headroom` (0.9; at most 0.95, because keyframe x is rounded to 4 decimals) × `no-whip-pan`'s 0.3 frame widths/s; zoom and height are static per segment. Keyframes every `key_step_s` (0.5 s). A face that still nears the crop edge is a warning. A face track over a source with camera cuts inside it smooths across them; split the keep list at those cuts. **Source size (S18).** Each source gets `frame_size` for the FCPXML export's framing: the stub's own, else the display size of the video stream the producer's probe reads from the same file (`aar.media.probe`: pixel aspect applied, then a 90/270 rotation swaps it; the cut's sources reuse the audio probe, other readable sources are probed, an unreadable one is a `frame-size-unread` warning), else the face track's sampled size. An audio-only source gets none. Sizes whose aspects differ by more than 1 % are a `frame-size-mismatch` warning; the stub's size still wins, and the probe wins over the face track. **Start timecode (S18 round 4).** Each source gets `start_timecode` the same way: the stub's own, else the same probe's `timecode` tag (the video stream's, then a tmcd or other stream's, then the container's) counted at the video stream's rate (the plan's for a file with no video), drop-frame handled. It also sets `start_timecode_rate` to that rate. A tag that cannot be read is `start-timecode-unread` and a stub value the probe disagrees with `start-timecode-mismatch` (the stub's wins); a stub `start_timecode` without its rate, for media the probe shows at another rate than the plan's, is refused as `start-timecode-rate-required` (exit 2). **BRAW start timecode (S18a).** Every `.braw`, `.mov` and `.mp4` source that is a local file also has its tmcd track read by `aar.media.quicktime` (pure Python, seek-based and unbuffered, a few hundred bytes read: the top-level atoms to `moov` wherever it is, the timecode track (round 7: the one the first video track's `tref/tmcd` names by tkhd ID, which must be unique and a tmcd track, else the movie's only tmcd track; several and no tref is `unsupported`), the `stsd` entry that `stsc`'s first row (which must start at chunk 1) gives the first chunk, walked by the entries' sizes (entry 1 when there is one entry and no `stsc`; with several, `stsc` is required), the first chunk offset from `stco` or `co64`, which must lie in a top-level `mdat`'s payload, and the big-endian signed 32-bit frame number there; round 7 also requires the chosen entry's data reference to say the data is in this file (else `unsupported`: timecode in an external file) and `stsz` to give the first sample at least 4 bytes). Precedence stays stub > ffprobe tag > tmcd sample for the frame: the tmcd sample is used when ffprobe gives no tag or cannot open the file (then `frame-size-unread` still warns). **The rate (rounds 2-3)** is the video stream's average, else its r_frame_rate, snapped to the nearest of 23.976, 24, 25, 29.97, 30, 47.952, 48, 50, 59.94 and 60 within 0.1 % (`aar.media.probe.snap_rate`); when neither snaps (a 15, 120 or 240 fps clip) it is the stream's exact rate, its r_frame_rate when that is whole or n/1001, else its average, as before S18a; with no video it is the tmcd track's rate (snapped when it snaps), else the plan's (an audio-only tag). The tmcd track only says how many frames a second it counts: its numberOfFrames must equal the snapped rate rounded, so a 29.97 stream whose tmcd says 30000/1001, 2997/100 or 30/1 gives 30000/1001 and a 23.976 stream with a 24/1 tmcd gives 24000/1001, and the tag counts at that rate. Only a tmcd track can make the rate ambiguous: one whose numberOfFrames is not the rate rounded (a 25 fps tmcd on a 50 fps stream), a drop-frame tmcd at a rate without drop-frame, one the reader refuses as `unsupported`, a tmcd track whose first edit is not trivial (its `edts/elst` first entry must have media_time 0 and rate exactly 1; a trimmed start, an empty edit (-1) or another rate is refused as `unsupported` rather than applied, since how Resolve maps an edited tmcd is unverified and the CCN BRAW's edits are all trivial; the video track's edits are not read), or a negative start (the sample is a signed 32-bit count; the reader refuses any negative one as `negative_timecode`, and ffprobe's tag from the same track, read unsigned, is not used either). Then, unless the stub gives `start_timecode` (with `start_timecode_rate`), the producer refuses with `timecode-rate-ambiguous` (exit 2), naming the values. Timecodes are worked out only for the sources the plan plays (the cut's and the outro's): a source it does not play keeps the stub's values and can neither warn nor refuse. A tag the tmcd sample gives another frame for is `start-timecode-reader-mismatch` (the tag wins); a tmcd track that cannot be read is `start-timecode-unread` only when nothing else gives a timecode; the stub rate check (`start-timecode-rate-required`) uses the snapped rate. The report's `log.start_timecodes` gives each source's frames, rate, label, drop-frame flag and what supplied the frames (`from`: stub, media probe or tmcd reader) and the rate (`rate_from`). `aar media timecode FILE` prints the reader's result as JSON (frame number, the tmcd rate as written, drop-frame flag, HH:MM:SS:FF, and the stub fields to copy), exit 0, or 1 when the file has no readable timecode and 2 when it is missing. The reader validates every size and offset against its parent and the file, caps `moov` at 64 MiB, each walk of the file at 1,000 top-level atoms (a real movie has about ten; each costs a seek), all walks at 100,000 atom headers and 8 MiB read, and refuses anything it would have to guess at (numberOfFrames that is not its own rate rounded, drop-frame other than at 29.97 or 59.94, a count past 24 hours without the 24-hour flag) with a typed `TimecodeUnreadable` whose `code` says why.
- **Every cut** gets a `crossfade_frames` (2) audio crossfade of `audio-crossfade`'s type; its handle is `ceil(crossfade_frames × handle_fraction)` frames each side.
- **Invariants.** Chronological order and no edit point inside a word are checked on the result (`InvariantError`). The plan is then linted under the profile; a lint error is `LintGateError` and nothing is written (exit 1). Warnings are allowed and listed in the report with the planner's own warnings and a log of snaps, trims, nudges, folds and the ending.

#### Edit-PC transport (S13f)

Cold work runs on the hub; Resolve, its renders and the masters stay on the edit PC. One module (`aar.host`) moves files between them and runs PowerShell there. It is security-sensitive: it builds remote commands and moves files, so every path and string is treated as hostile.

- **Config, not code, names the host.** The edit PC is an ssh alias plus an ssh config file (`ssh -F <config>`), given by `AAR_EDIT_*` environment variables or an explicit `EditHostConfig`. There is no default host anywhere in code, and the ssh config and key material are never read. The alias must be a plain ssh host/alias (`^[A-Za-z0-9][A-Za-z0-9._@-]*$`): `/`, `[`, `:`, spaces and a leading `-` are refused, because they change how scp splits `host:path`.
- **Roots bound every transfer.** The config lists allowed remote (Windows) roots and allowed local (hub) roots. A source or destination outside them is refused before any command runs. Local paths are resolved with `realpath`, so a symlink that escapes its root is refused.
- **Runner seam.** All argv go through a `Runner` (argv list, optional stdin, timeout). The real one uses `subprocess` with an argument list and never a shell, and always passes `-F <config>`, `-o BatchMode=yes` and `-o ConnectTimeout=<n>`. Tests use a fake runner; nothing in the module or its tests contacts a real host.
- **PowerShell.** Scripts run as `powershell -NoProfile -NonInteractive -EncodedCommand <base64 of UTF-16LE>`. The command-line cap is a config value (`AAR_EDIT_CMDLINE_MAX`), not a fixed constant: Win32-OpenSSH runs the command through the sshd DefaultShell, and the default DefaultShell is `cmd.exe` (~8191 characters), far below the 32767 a PowerShell DefaultShell allows. The default cap is sized for `cmd.exe` and the refusal says so and how to raise it. Output CRLF is normalised to LF and CLIXML progress is stripped from stderr (error text is kept). Values embedded in scripts use one quoting helper (single-quoted literals), which doubles every character PowerShell treats as a single quote -- `'` and the smart quotes U+2018, U+2019, U+201A, U+201B -- so a filename like `Don’t Tell Mom.mp4` cannot break out of its literal. Parent paths inside scripts are taken with `[System.IO.Path]::GetDirectoryName`, never `Split-Path -LiteralPath ... -Parent` (an invalid parameter-set combination).
- **Transfers.** `pull`/`push` use scp in SFTP mode (the OpenSSH 9 default; `-O` is never passed). Remote size and SHA-256 come from `Get-Item`/`Get-FileHash`, local from `os`/`hashlib`. The file lands under a temporary name beside the destination and is moved into place only when both size and hash match; a mismatch or failure removes the partial and raises a typed error. The local move prefers an atomic hard link and falls back to an `O_EXCL` claim-then-replace on filesystems without hard links (FAT/exFAT, some SMB/CIFS and FUSE mounts); a local I/O failure surfaces as a typed error with the partial removed. An existing destination (file or directory) is never overwritten unless the caller asks; `--overwrite` still refuses a directory destination and a destination whose parent is a reparse point (the move fails closed).
- **Path forms and globbing.** A Windows path becomes one of `alias:E:/...` (default) or `alias:/E:/...`, selected by config, because it is unsettled which Windows OpenSSH needs. The spec is rebuilt from validated components, so no raw separators or alternate spellings leak through. scp in SFTP mode globs a remote *source* client-side, so glob metacharacters (`[ ] * ? \`) in a download source are backslash-escaped; a remote *destination* is not globbed and is sent literally. scp is always run with `-s` to force SFTP mode rather than rely on the client default; there is no toggle. The hub needs OpenSSH >= 8.7. Legacy SCP is unsupported because it is unsafe: in legacy mode scp sends the remote path unquoted through the remote shell (`cmd.exe` by default on Windows), so a data-controlled filename containing `&`, `^`, `%VAR%` or `$( )` would run a command (the round-2 HIGH-1 class of bug). A client older than 8.7 rejects `-s` and so fails closed with a typed transport error; a client of 8.7-8.9 defaults to legacy SCP, which `-s` overrides. The hub is OpenSSH 9.6p1. If the removed `AAR_EDIT_SCP_SFTP` env var is still set, config load refuses with a typed error rather than silently ignoring it.
- **Timeouts.** `connect_timeout` (ssh `ConnectTimeout`, default 10 s) bounds the handshake. `command_timeout` (default 300 s) is the wall-clock for each runner call, so it also bounds the scp of a large master and the `Get-FileHash` of one; callers pass `--timeout` (or a larger `command_timeout`) for big files.
- **What is refused.** Relative and drive-relative paths (`E:Show`), `.`/`..`/empty components, verbatim and device namespaces (`\\?\`, `\\.\`), reserved device names (`CON`, `COM1`, …), illegal or control characters (including an alternate-data-stream `:`), trailing dots or spaces, UNC paths unless a UNC root is configured, and anything that does not resolve inside an allowed root. Path parsing, NTFS upcasing and the edit-PC↔hub map reuse `aar.drp.modify.paths`.
- **Root confinement folds ASCII case only.** A path is inside a root when its leading components match the root's, compared with an ASCII-only upper-case fold. ASCII case differences fold (`E:\Show` == `E:\SHOW`), but a non-ASCII character must match exactly: the full NTFS upcase over-folds 246+ pairs NTFS keeps distinct (long s vs `S`, dotless i vs `I`, Kelvin sign vs `K`), so e.g. `E:\ſhow` or `E:\CAFÉ` under root `E:\Café` is refused as `outside-allowed-roots`. Under-folding is the safe direction: at worst it refuses a path that NTFS would place inside the root, never the reverse.
- **Known limit.** Root validation is lexical, so a junction or symlink (reparse point) under an allowed root could still redirect a transfer outside it on the edit PC. The push move refuses when the destination's immediate parent is a reparse point, but a reparse point higher in the tree is not caught. This is acceptable for a trusted, single-tenant edit PC on a tailnet; a complete fix needs an atomic remote resolve-and-move that SFTP does not offer (any check-then-move still races).
- **Residuals for a live Windows test** (the hub has no PowerShell or Windows, so these are reasoned, not confirmed):
  - the generated move script on Windows PowerShell 5.1 (the `GetDirectoryName` parent for a drive-root and a UNC-share-root destination, HIGH-2); `Move-Item -LiteralPath ... -Destination` with `[ ]` in the name on 5.1; the no-`-Force` move refusing an existing file; and the container and reparse-point guards against a real junction;
  - the real command-line budget for a cmd.exe DefaultShell (the `cmd.exe /c` wrapper and full path);
  - which path form (`E:/...` vs `/E:/...`) Win32-OpenSSH's sftp-server accepts for stat, glob, download and upload;
  - UNC over SFTP in both forms (slash form is `///server/share/...`), including the second-hop credential, and `Get-Item -LiteralPath '\\server\share' -Force` on a share root;
  - smart-quote (`Don’t ...`, with U+2019) and non-ASCII names end to end (UTF-8 over SFTP to UTF-16);
  - `scp -s` acceptance on the client actually used (a client older than OpenSSH 8.7 rejects it and fails closed);
  - stdin handling (ssh/scp get `/dev/null`), CLIXML noise on a first-run module load, and hidden files (`Get-Item` without `-Force` fails closed);
  - paths of 260+ characters through `GetDirectoryName`/`Get-Item` on .NET Framework (5.1);
  - whether the cleanup `Remove-Item` after an interrupted upload races the sftp-server's still-open handle and silently leaves the `.aarpart-*`;
  - legacy SCP (toggle-off) mode is unsupported because it is unsafe (see the transfers note): the remote shell parses the path, so it is never exercised and never allowed.

#### Project registry (S17, S19e)

The hub's registry (`aar.hub.registry`) gives every project a stable id (`prj_...`), a display name, aliases and zero or more sources: where the project lives in Resolve (`cloud_library`, `local_db` with the Resolve unique id in the locator, or a `.drp`/`.drt` file on a named host). It is a projection of `project.*` events. `aar hub project add|list|show|alias|source|rename` and the MCP tool `project_register` (with `--agent-writes`) are the validated way to write it (`aar.hub.project_register`); humans and agents may, a node may not.

- **A sourced project is identified by its Resolve unique id.** One uid belongs to one registry project: registering it again, or adding it as a source of another project, is refused `project_exists` with `existing_id`. Its name is only a label (two sourced projects may share one).
- **A project without a source (S19e)** is a show edited from hub media before any Resolve project exists (`ccn-longform` with the edit PC off). It is registered with a name and no `--source-kind`/`--locator` (MCP: no `source_kind`/`locator`); giving one of the two without the other, or a host without them, is `invalid_input` naming the field. Having no uid, **its name is its identity**:
  - Registering a source-less project whose name or any alias is already the name or an alias of any project, sourced or not, is refused `project_exists` with `existing_id` and the colliding `name`.
  - **Reserved names.** A name or alias a source-less project holds is reserved to it: `aar hub project rename` and `aar hub project alias` refuse (`project_exists`, same details) to give it to any other project, and a source-less project may not be renamed or aliased to a name or alias any other project holds. Renaming a project to its own name, or to one of its own aliases, and re-adding an alias it has, work as before. Once a source is attached the project is identified by its uid and its names are no longer reserved. There is no MCP rename or alias tool.
  - **What a name may be.** On these paths (source-less registration, rename, alias) a name or alias with surrounding whitespace, a control character (C0 or C1), a format character (zero-width space or joiner, BOM, bidi marks) or a line/paragraph separator is `invalid_input`. Names compare NFC-normalised, so a composed and a decomposed `Café` are one name; case still matters (`Show` and `show` differ). The node's `hub_project_id` name fallback compares exact text; it finds a source-less project by the name it was registered under.
  - The rule is applied by the agent-facing paths (`aar.hub.project_register`: `project add`, `rename`, `alias` and the MCP `project_register`), which pass `unique_name=True` to `Registry.create_project`, `rename_project` and `add_alias`. The library default is off (a library caller may still create projects that share names). The check runs inside the write transaction after the idempotent-retry check: the same idempotency key with the same request returns the existing project (`replayed`), the same key with another request is `idempotency_conflict`, and two racing registrations of one name give one project.
  - A registration with a source may not take a name or alias a source-less project holds either (`project_exists` with `existing_id`, and the hint to attach instead): registering a show's Resolve project under the show's name used to make a second project, splitting its plans, reviews and Resolve jobs between two ids. The source is attached to the existing project with `aar hub project source` or the MCP `project_source` tool. Two projects that both have sources may still share a name (their Resolve ids tell them apart), and a sourced name keeps its looser character rules. Refusing twins keeps the node's name fallback unambiguous for source-less shows (a node that finds no project by uid takes the single project with the Resolve project's name or alias).
- **Attaching the Resolve source later.** When the edit PC has imported the show and a real Resolve project exists, `aar hub project source PRJ --source-kind local_db --locator '{...}'` (the locator `aar node locate` prints) adds it to the same `prj_...` id, so the run's history stays on one project; the one-uid-one-project rule applies as to a new registration.
- **Consumers accept an empty source list**: `project list`/`show`, `projects_list`/`project_get`, the console pages and `project_board` (which is keyed by the Resolve uid and shows an empty board for a registry id). A Resolve job names its target by Resolve uid. `job_submit` (and `aar hub job submit`) refuses a `project.project_id` with `not_a_resolve_project` only when it is the registry id of a project **and** no project lists that same text as the Resolve unique id of one of its sources (an explicit registry id may be any text, including a Resolve uid; such an id is accepted as on dev). The fix hint says to attach a source first (no source) or names the project's uids, which never include the refused text. The check runs inside the submit transaction after the idempotent-replay lookup, so a retry of an accepted job always replays.

#### Hub write surface (S13g1)

How agents write to the hub (`aar.hub.writes`, `aar.hub.facts`). The MCP tools and `aar hub write` are thin wrappers over the same functions.

- **Opt-in.** `aar hub serve` stays read-only and lists exactly its 13 read tools (12 from S13g1 plus `recipe_status`, added in S13g2: it is always listed, even without agent writes, because an agent needs it to drive a recipe run). `--agent-writes` opens the existing database writable and adds six write tools (`brief_create`, `recipe_create`, `plan_submit`, `node_set_status`, `facts_record`, `facts_retract`), the S13g2 recipe write tools (`recipe_start`, `step_complete`, `recipe_retry`, `recipe_cancel`, and `recipe_reopen` from S19f) and three reads (`facts_get`, `brief_get`, `plan_get`). Human-only actions (deciding a review, granting or revoking an approval, resuming after a stop) are never tools. Agents without MCP use `aar hub write {brief,recipe,plan,status,fact,retract}` and `aar hub facts show`: one JSON request in (a file or stdin, with the tool's arguments), JSON out, a refusal as `{"error": {code, message, fix_hint, details}}` on stderr with exit 2. A plan stored as `blocked` exits 1, as `aar plan lint` does.
- **Identity is self-declared.** A write tool records the caller's `agent_id` as `Actor("agent", agent_id)`, checked only against the agent-id rule. That is attribution, not authentication (decision 6): any caller that reaches the server can claim any agent id. The CLI's `--actor` is the same.
- **Node kinds and schemas.** The graph gains a `recipe` kind; logs written before still fold to the same state (pinned by a fixture generated on the old code). Node data is typed with strict models (unknown keys refused, every string and list bounded, no NaN or infinity), each with a `schema` literal:
  - `aar.brief/1`: hub `project_id`, `show`, `kind` (longform, short, thumbnail), `recipe`, `rule_profile` (a built-in profile name), `sources` (at most 64 cloud-project, timeline-by-unique-id or media refs), `deliverables` (1 to 32, unique names, typed kinds) and optional `hook`, `handle`, `title`, `notes`.
  - `aar.recipe/1`: `recipe`, `brief_id`, `params` (a JSON object of at most 64 KiB, nested at most 8 deep), `max_review_rounds` (1 to 10, default 3). The recipe's own validator checks the params (a hook for S13g2; the default accepts any bounded object). The brief must be typed and ask for that recipe.
  - `aar.plan-node/1`: the EditPlan is stored as a content-addressed artifact (its canonical JSON, at most 1 MiB); the node holds its sha256, the plan version, the rule profile, the parent, the brief it resolves to, and a lint summary (counts, the first 20 findings errors first, and the rules that could not run). A plan derives from a brief, recipe, earlier plan or review, never an op or artifact. A plan that fails validation is refused with each field location; one with lint errors is stored `blocked`, one without `pending`. The hub lints without a transcript or laugh map, so the rules that need one are listed as skipped, not passed.
- **Profiles by name only.** The hub accepts built-in profile names, never paths, so a tool caller cannot make the hub read a file on its host. A plan whose parent resolves to a typed brief must use that brief's `rule_profile`, so an agent cannot dodge the house rules by naming another profile.
- **Who may change what.** An agent (or node) may move the status of a brief, recipe, plan or op node that it created (the actor on the node's creation event), through the graph's transition table. A human may move any node except a review. Reviews close only through a human decision or the requester's withdrawal. **Runner-managed nodes are the exception:** a recipe step's op node (`aar.step/1`) and a recipe node once its run has started are refused for every actor (`runner_managed`) — they mirror runner evidence, so a human acts on a running recipe through `recipe_cancel` and review decisions, never a status move.
- **Actor kinds** are `human`, `agent`, `node` and `runner`. `runner` is the recipe engine's own identity (`aar.recipes.RUNNER`); it is the only writer the scheduler trusts for `recipe.*` evidence and op nodes. No string surface can produce it (the actor parsers and MCP refuse `runner:*`). The runner may request reviews, but may never decide one (human-only) and may not move a node through `set_own_status`; local trust still applies (a direct event-log writer on the host is trusted, as everywhere).
- **Idempotency.** Every write needs a caller-chosen `idempotency_key`, namespaced per actor. The same key with the same (normalised) request returns the first result again, marked `replayed`; the same key with a different request (another project, op or content) is `idempotency_conflict`. A write that takes several events appends them in one transaction with a `hub.write` record (the op and a sha256 of the request) last, so a crash before the commit leaves nothing and a retry writes it whole. `plan_submit` stores its artifact first; it is content-addressed, so a retry reuses it.
- **Errors** are `{code, message, fix_hint, details}`. Codes include `unknown_project`, `unknown_parent`, `wrong_parent_kind`, `untyped_parent`, `unknown_node`, `not_creator`, `kind_not_allowed`, `protected_review`, `illegal_transition`, `idempotency_conflict`, `invalid_brief`, `invalid_recipe`, `invalid_plan`, `invalid_params`, `unknown_profile`, `profile_mismatch`, `recipe_mismatch`, `unknown_namespace`, `invalid_fact`, `unknown_fact`, `unknown_source` and `too_many_facts`.
- **Facts** (`facts.recorded`, `facts.retracted`, scoped to the project). Keys come from a closed set of namespaces, each with its own value model; every `<...>` part is 1 to 64 of `A-Z a-z 0-9 _ -`:
  - `sync.offset.<angle>`: whole frames, the frame rate as a rational, and what the offset is relative to.
  - `audio.gain.<track>`: dB, -96 to +24.
  - `template.trap.<id>`: text, up to 2000 characters.
  - `template.id.<name>`: a Resolve unique id.
  - `path.map.<name>`: `from` and `to` paths.
  - `render.hash.<deliverable>`: sha256 and byte size. An optional leading role segment, only `review` or `master` (`render.hash.review.<deliverable>`, `render.hash.master.<deliverable>`), lets a review and a master of one deliverable coexist; any other role word is refused.
  - `qa.<metric>.<deliverable>`: a finite number and its unit.
  - `transcript.<key>` (S19a): a stored transcript of one media file (`media_sha256`, `model`, `recording`, and the `transcript`, `text` and `report` artifact ids); `<key>` is the sha256 of the file's sha256, the model and the settings that change the words.

  The projection gives each key's current value (the last event in log order wins), who set it and when, an optional source (a recipe node and/or a stored artifact) and its last 10 changes. A retraction keeps the history. Malformed or forged events are skipped and listed. Any actor kind may record; a project holds at most 1000 keys.

#### Recipe runner (S13g2)

`aar.recipes` drives a recipe node through its steps on the hub. Every piece of run state lives in the event log (the op nodes, the `recipe.*` event family, and the reviews), so a killed process resumes from the log alone. This slice ships the engine, the gate library and a test-only recipe; the CCN recipes are a later slice.

- **Recipes are defined in code**, in `aar.recipes.registry`. A `RecipeDef` has a name (the hub's `NAME_RE`), a version, a pydantic params model and an ordered tuple of `StepDef` (at most 64). A `StepDef` has an id (`[a-z][a-z0-9_]{0,31}`), a kind (`cold`, `hot`, `agent`, `gate`), the ids of earlier steps it `needs` (a DAG, validated at registration), `max_attempts` (1–5, default 3), a finite `timeout_s` (≤ 24 h) and per-kind fields. Registering a recipe installs its params model into the recipe-params validator hook (the `ParamsValidator` seam from S13g1): the running surfaces (`aar hub serve`, the recipe engine) plug in `registry_params_validator`, so `recipe_create` then refuses an unregistered recipe name with `unknown_recipe` (a new error code) and validates params against the registered model (`invalid_params`). `build_server`, `aar hub serve` and `aar hub write recipe` all default to `registry_params_validator`; a caller opts out of the registry with `accept_any_params`. `recipe_start` (and the worker) re-validate the stored params, so a recipe slipped in through the generic graph API with bad params is refused `invalid_params` rather than crashing a step.
- **Each step attempt is an op node** with typed data `aar.step/1` (`recipe_node`, `step_id`, `attempt` from 1, `round` from 1, `step_kind`), created by RUNNER. It links to the recipe node with `derives_from` and to any artifact it produces with `produces` (also by RUNNER). **The op's and the recipe's graph status are mirrors the engine writes; they are never read as truth.** The scheduler derives every status from runner evidence: an attempt is done/failed from a runner `recipe.result`; a gate is done from a human decision on the runner-linked review; cancelled from a runner `recipe.cancelled`. So an agent that owns an op node and moves its graph status changes nothing the scheduler reads (it is also refused `runner_managed`). A round rollback supersedes attempts with a `recipe.cancelled` event.
- **The `recipe.*` event family** (typed payloads, each written with S13g1's atomicity pattern — one transaction, the `hub.write` record last): every one is **attributed to RUNNER**, with the real caller recorded (`caller` in the `hub.write` record, `worker` on a claim, `by` on a result). Their idempotency keys are **global under the single runner identity** (not per-actor), which is what makes op creation unique across concurrent callers. The family: `recipe.started`, `recipe.claimed` (a lease, with `worker` and `claim_index`), `recipe.heartbeat` (keyed per claim), `recipe.hot_intent`, `recipe.hot_submitted`, `recipe.result` (`done`/`failed`, canonical-JSON outputs enforced ≤ 64 KiB — over it the step fails `outputs_too_large`; artifact ids; an error `{code, message, fix_hint}`), `recipe.review_linked`, `recipe.cancelled`, `recipe.run_cancelled`. The fold ignores any `recipe.*` event or `aar.step/1` op node not authored by RUNNER (listed in `ignored`).
- **Scheduling is a pure function over runner evidence**: `advance(log, recipe_node, *, actor, dispatcher=None, clock)` does one pass. It creates the op node for each ready step (one per attempt — the op-creating event uses a global idempotency key under RUNNER, so two concurrent callers produce exactly one op), submits and polls hot steps through the port, opens gate reviews and reads their decisions, advances review rounds, and reconciles the recipe node's graph status to the evidence status each pass (so a block that clears, e.g. after a legitimate retry, never sticks). It never runs a cold step itself. `actor` is the real caller, recorded on every write; the writes are RUNNER's. Every recipe write tool and the worker loop call `advance`.
- **Cold steps run in a worker** (`aar recipe worker`, the D6 cold worker on the Linux hub host). It claims a pending cold op with a 60 s lease (heartbeat every 15 s; both config), runs the registered callable with a `StepContext` (the recipe params and brief, the needed steps' outputs, an artifact `put`/`get`, a facts writer attributed to the op, a deadline, `cancelled()`), records the result and calls `advance`. A claim whose lease has lapsed is re-claimed only for steps registered `idempotent=True`; a non-idempotent lapsed claim fails `lease_lost` and needs an explicit retry; a live lease is never stolen. **Timeouts are cooperative: an in-process step cannot be killed.** The context carries a deadline and a callable that overruns it is recorded as `timeout`, but it could not be interrupted. SIGINT/SIGTERM stop claiming new work and let the current step finish.
- **Hot steps go through a port**, the `HotDispatcher` protocol (`submit`/`poll`). Before `submit`, `advance` records the intent with a deterministic `request_id` (the op id); the dispatcher is idempotent on that id, so a crash between the intent and the submitted record re-submits the same id. **The port's `request_id` idempotency is load-bearing** (F11): two concurrent `advance` callers may both call `submit` for the same op, which is safe only because the port dedupes on `request_id`; the fake is strict about it, and the real S15b job store keys its jobs on the request id. A port call that raises is caught per op inside `advance` (it never escapes or fails the step): a submit error leaves the recorded intent so the next pass re-submits, a poll error shows `waiting:dispatcher_error`. With no dispatcher the op stays `pending` and the status view shows `waiting:no_node_dispatcher` — "the Linux hub works with the PC off". `waiting_for_node` and `node_offline` show through unchanged. The real port (hub jobs plus a remote node) is S15b; this slice ships the protocol and a fake.
- **Agent steps** hand work to an agent, which completes them explicitly with `step_complete`. The step declares an `instruction` and an `expects` contract: a `plan` node that derives from the recipe node (round 1) or this recipe's gate review for the previous round (round > 1) and passes `plan_gate`; an `artifact` of a stated media kind, stored in this recipe's project; or `json` for a pydantic model. Outputs are canonical-JSON ≤ 64 KiB (`outputs_too_large` otherwise). The runner validates against the contract; on failure the call is refused (`expects_unmet`) and the step stays open. Any agent or a human may complete it; the completion is a runner write with the caller recorded as `by`. `step_complete` and `recipe_retry` honour the caller's `idempotency_key` (replay the first result marked `replayed`, or `idempotency_conflict`); an optional `round` guard on `step_complete` stops a replayed earlier-round call completing a later round.
- **Gate steps are human review gates.** On activation the runner opens a review (a review node and `reviews` edge written by RUNNER, so **the requester is the runner identity**: no agent can withdraw it, a human can) whose subject is a prior step's output. A step the gate needs may offer the reviewer more than the render: artifact ids under its `review_attachments` output are carried on the review (`attachments`, at most 8) and the console shows each small `text/plain` one, escaped, open on the review card above the decision, on the queue and the detail page (anything else is a download link that says why). `ccn-longform` attaches the export's handoff notes, so the video is not approved without seeing what the delivered timeline lacks. The subject step may also say what the review is of: its `review_timeline` (text) and `review_fps` (a number) outputs become the review's `timeline` and `fps`, and with a rate the console takes a note's frame from the player and derives its timecode instead of asking the reviewer to type both. A value a review could not hold is left out, never written. `ccn-longform`'s render offers the stub's timeline name and the plan's rate. Approve finishes the step. Reject, while `round < max_review_rounds` (the S13g1 bound, 1–10, default 3), starts the next round and supersedes every live-or-done attempt from the step named by `on_reject` onward. At the limit the step fails `review_rounds_exhausted` and the recipe blocks; that gate is **terminal** — `recipe_retry` on it is refused `rounds_exhausted`, and the only exit is `recipe_cancel`. A review withdrawn by a human (no decision) fails the gate `review_withdrawn` and blocks the recipe; `recipe_retry` then opens a fresh review **in the same round** (a withdrawal does not use a round). **Nothing in this slice decides a review — that stays a human action in the console.**
- **Reopening an agent step (S19f).** A cold step may declare `on_fail`: the id of an earlier `agent` step it needs, directly or through other steps (checked when the recipe is defined, like `on_reject`; refused on any other step kind). A `StepFailure` raised with `upstream=True` means the output of that step caused the failure, so running the cold step again unchanged fails the same way; the worker records it in the failed `recipe.result` as `error.upstream: true` (written only when true; a result without it, every log written before S19f included, folds as false, and `_bound_error` drops any value but `true`). `recipe_reopen(log, recipe, step, actor, idempotency_key=...)` (CLI `aar recipe reopen RECIPE STEP`, MCP `recipe_reopen`; the creator or a human, as `recipe_retry`) is **a new attempt of the agent step in the same round**, asked for explicitly; nothing reopens by itself and it is not a review round. Its typed refusals, in order: `recipe_not_open` (not started, cancelled or done), `recipe_blocked` (blocked for a reason the reopen does not clear: exhausted review rounds, a withdrawn review, a step out of attempts that is not this step's upstream failure; a run blocked only because the failed `on_fail` step ran out of attempts can be reopened), `not_agent_step`, `step_not_done` (no done, non-cancelled op of the step in the current round), `no_upstream_failure` (no cold step with `on_fail == step` has, as its latest attempt in the round, a failure marked upstream), `no_attempts_left` (the step's ops in the round, superseded ones included, reach its `max_attempts`), `already_reopened` (lost a race, below). The effect: every non-cancelled op of the round from `step` onward in recipe order is superseded (the set a gate rejection's round rollback supersedes, `round_ops_from`), then the step's next attempt is created in the same round with `reopened_for` in its op data (the failing step and attempt, its code, message and fix hint, and the failed op's node id). Later steps are created by the normal ready pass; every new op takes the attempt number one past every op of its step in the round, superseded ones included, so no op key collides. `current_round()`, `max_review_rounds`, review titles, the report's round count and the export's `.r<round>` names do not change; a gate rejection after a reopen opens the next round as before, where attempts start again at 1. The plan contract refuses with `plan_unchanged` a plan byte-identical to any plan the recipe's agent steps took before (any round, any attempt, superseded or not), not only a rejected one. **Crash safety.** The first write supersedes the agent step's done op with the whole reopen (the op ids to supersede, the new attempt number, `reopened_for`, the caller's key) on the `recipe.cancelled` event (a field on an existing runner record, no new event type). The rest (`finish_reopen`: the supersedes, then the withdrawal of the open reviews of the gate ops among them, then the create) is idempotent and is made by the command, by **any `advance`** (the worker tick: `finish_reopens` runs first in each pass, before the ready pass), by **every recipe write command** before it decides anything (`recipe_start`, `step_complete`, `recipe_retry`, `recipe_reopen`, `recipe_cancel`: each finishes an unfinished reopen of an active or blocked run first, so none of them writes next to a half-made reopen; a `recipe_retry` of the failed step in that window is then refused `step_not_open`, because the reopen has superseded it) and by a re-run of the command with the same key, whichever comes first; the caller's `hub.write` record is written last, so a replay after that changes nothing. While a reopen is unfinished, the ready pass leaves its step alone (only the reopen creates that attempt, so it always carries `reopened_for`), and the status view gives the ops it will still supersede and the step it will still create the state `waiting:reopen` and the action `who: worker` "a reopen ... is being finished" instead of a retry, a run or a review to decide. A gate op the reopen supersedes has its open review withdrawn by the reopen, as RUNNER (its requester), the way `recipe_cancel` withdraws reviews; it is one more idempotent write of `finish_reopen` (a closed review is left alone), made before the create, so the crash and replay rules above cover it, and the new attempt's gate opens a new review. A reopen does not move the round, so unlike a gate rejection's rollback (whose superseded gates are in a round already rejected, where one more rejection adds nothing) a decision left on such a review would: the fold therefore ignores a decision on the review of a gate op listed in a reopen's plan when the decision was recorded after the reopen's first write (by log position; `RunState.gate_decision`). A human who decides or withdraws that review inside the window, or races the withdrawal, opens no round, blocks nothing (also with `max_review_rounds` 1), records no gate result and is not a round-2 plan's parent; the status view (`ignored_decisions`) and REPORT.md's gates say in one line which review, which decision, and that the reopen had already superseded its gate. A decision recorded before that write counts as it always did: an approval stays in REPORT.md as that round's history (it does not pass the new gate attempt, which opens its own review), and a rejection cannot precede the write, because the first write is conditional: inside its transaction it re-reads the run and writes only if the run is still in the plan's round and the reopen still applies (the plan written is the one made from that read); otherwise the reopen is refused (`no_upstream_failure` when the round moved on, or the refusal the re-read gives, such as `recipe_blocked` when the rounds are used up) and writes nothing. Two calls racing with different keys both pass the preconditions, but only one supersede of the done op can land (its key is per op): the other reads the winner's plan from the fold, helps finish it and is refused `already_reopened`, so the step never has two live ops. The status view offers `recipe_reopen <step>` (agent, with the tool and its args) on a failed step whose failure is upstream while the agent step has attempts left (instead of the retry, which would fail the same way); with none left it says so and that what remains is `recipe_cancel` and a new run. The reopened step's entry carries `reopened_for` and its attempt. REPORT.md adds `fix attempts: round N: k, ...` under an agent step when any round had more than one attempt.
- **The gate library reads evidence, never node status** (`aar.recipes.gates`). `plan_gate` passes only when the stored lint summary has no errors and every required rule actually ran; it ignores the plan node's graph status, so an agent that moves its own lint-`blocked` plan to `active` (a legal transition — S13g1 F2) still cannot pass it. `qa_gate` reads a `QAReport`: a required check passes on `pass`, on `warn` only when allowed, and fails on `fail`, on `incomplete`, or on `skipped` unless its `skip_reason` is `not-applicable`. Exit 0 from `aar qa check` is not a pass.
- **REPORT.md (step 16).** A built-in last step `recipe.report` (cold, idempotent) writes a deterministic `REPORT.md` artifact: every step's attempts, rounds, durations, outcomes and error codes; the gate decisions with the deciding human; the QA summaries; the facts recorded; and every produced artifact with its sha256. For now "archiving" is that report plus the recipe node going `done`; files move in S16b.

#### Delivery (S13i)

R6 steps 9 to 12 turn a finished render into a stored, hashed, QA'd and (for review) sent artifact. Two parts carry it.

- **Render output size (`render.build`, `render` job).** The build op takes an optional output size (`width`/`height`, both or neither, even, 16 to 8192), `video_quality` (a bit rate in kbit/s from 100 to 400000, or one of Least/Low/Medium/High/Best; 0 is refused, so None means automatic), `export_audio` and `audio_codec`. `_configure` writes them through `SetRenderSettings` **after** the delivery preset loads, so they override it, and the §5 Deliver snapshot carries the human's own size and quality back on restore. After `AddRenderJob` the op reads the size back off the queued job: a size the queue reports but that does not match is `render_size_ignored` (the just-added job is cleaned up), while a queue that reports no size keys is recorded as `size_verified: false` rather than failing. A resumed build adopts its journaled job and never re-applies or re-verifies the size.

- **`aar.deliver` (hub-side library, `aar deliver review|master`).** Dependencies are injected (an `EditHostLike` for the verified transport, a `Transcoder` with a default two-pass `FfmpegTranscoder`, a QA callable defaulting to `aar.qa.check`, and the hub's `EventLog`, `ArtifactStore` and `Actor`). Each delivery works in `<workdir>/<project>/<deliverable>/<render_job_id>/`; the `workdir` is required, absolute and durable (never a scratch directory — the library creates none of its own), and every file it writes, including the ffmpeg two-pass logs, stays inside it.
    The `workdir` must be absolute and durable: a path that resolves under a fixed system scratch root (`/tmp`, `/var/tmp`, `/dev/shm`) is refused (`invalid_workdir`). Each delivery takes an exclusive per-work-dir `flock` for its whole run: a second concurrent delivery of the same render job gets `delivery_in_progress`, and because the lock is an `flock` a crashed delivery releases it so a later resume is never blocked.
  - **Review.** Pull the render (skipping the pull when the local copy already matches the remote sha256; a different sha256 is `deliver_local_mismatch`, never overwritten). The review box is 1280×720 or 720×1280, chosen by the **source aspect, not by kind**; the fit keeps the aspect, uses even dimensions and never upscales. A render is used as is only when it already fits the box and the cap (`review_mp4_max_mb`, decimal MB) **and** is already a browser-playable file: H.264 video at `pix_fmt` yuv420p (8-bit 4:2:0 — so High 4:2:2, High 4:4:4 and 10-bit are excluded), AAC or no audio, in an `.mp4`/`.mov` container (its stored mime then follows the container, e.g. `.mov` → `video/quicktime`); anything else — ProRes, 10-bit, a non-yuv420p profile, a `.mkv` — is transcoded. The transcode is two-pass H.264 (`yuv420p`, High profile, so every browser plays it) + AAC 128 kbit/s + `+faststart` at `floor((cap·0.92·8/duration − 128000)/1000)` kbit/s (capped at 4000, refused below 250 as `review_cannot_fit`), retried once at 85% of that rate, and `review_over_cap` if it is still over. A partial transcode goes to a `.part` and is renamed only after ffmpeg exits 0, the output decodes, and its size is checked against the cap; the two-pass logs are deleted on success and failure, and the per-pass ffmpeg timeout is `max(120 s, 4×duration)`. A review.mp4 left by a prior attempt is reused only if it fits the cap and still decodes — an over-cap or undecodable (or unprobeable) leftover is rebuilt, never reused. Each delivery takes an exclusive `flock` on the work dir; a second concurrent delivery of the same render gets `delivery_in_progress` (exit 3), while an flock errno other than EWOULDBLOCK/EAGAIN (an NFS `nolock`, FUSE or SMB mount) is `lock_unsupported` (exit 2) and names the errno. QA holds the review to the **content kind's** loudness and duration targets (short or longform) plus the review checks (decode and the size cap), composed in the delivery library without changing what `qa.check(kind="review")` means for other callers; a failing report is `review_qa_failed` and nothing is stored or sent. The review MP4 is stored (`ArtifactStore.put`, deduped by content); its sha256 and size go to `render.hash.review.<deliverable>` and its size in MB to `qa.size.<deliverable>`; then a human review is requested, and any still-open review previously requested for the same project, deliverable and review role is withdrawn ("superseded by delivery <id>", via the requester-withdraw path, same actor), so a human can never approve a stale proxy. The facts and the review carry deterministic idempotency keys derived by hashing `(project, deliverable, render job id, role, content sha256)` (well under the hub's 128-char key limit for any input), so an unchanged re-run writes nothing new and does not transcode again, while a re-delivery whose bytes changed (a lowered cap, an ffmpeg upgrade, an F5 rebuild) is a new delivery that supersedes the previous `render.hash` fact through the facts store's last-writer-wins path — never a hub idempotency conflict.
  - **Master.** Pull (same resume rules), store with role `master`, and QA with the source kind. The hash fact (`render.hash.master.<deliverable>`) is always written; a `qa.<metric>.<deliverable>` fact is written for each numeric value a check measured (integrated loudness in LUFS, true peak in dBTP), never guessed. Duration is not written as a pass/fail fact without a plan (the master QA runs without one); the measured duration stays on the `RenderOutput`. There is no transcode and no review request: the master is stored whether QA passes or fails, because the publish gate (step 13) is a human. Masters can be several gigabytes, so every hash and copy is streamed; `command_timeout` on the edit host has to be raised for a large master. Review and master write distinct `render.hash.<role>.<deliverable>` keys, so they never clobber each other for one deliverable name.
  - **Errors** are a typed `DeliverError(code, message, fix_hint, **detail)`; any hub, media, environment (a locked or read-only event log, an unwritable artifact store) or value error after the first write is wrapped into one, carrying the truthful `completed_steps` already done — a `sqlite3` error becomes `hub_unavailable`, an `OSError`/`PermissionError` from the artifact store becomes `store_unavailable`, and a local-filesystem read/write error elsewhere (an unreadable source, a broken work dir) becomes `local_io_error`. Opening the hub db with a bad `--db` (not a sqlite file, or a missing directory) is caught by the CLI and reported as `hub_unavailable` (exit 2, no traceback). The stable codes are `invalid_render_output`, `invalid_workdir`, `invalid_name`, `invalid_input`, `deliver_local_mismatch`, `delivery_in_progress`, `lock_unsupported`, `review_cannot_fit`, `review_over_cap`, `transcode_failed`, `review_qa_failed`, `media_unreadable`, `unknown_subject`, `hub_write_failed`, `hub_unavailable`, `store_unavailable`, `local_io_error` and `unsupported_platform`. The CLI exits 0 (done), 1 (QA failed), 2 (bad input, a missing tool, an unavailable hub/store, or running on Windows), or 3 (a transport error or `delivery_in_progress`). `fcntl` (POSIX-only) is imported lazily inside the lock, and delivery refuses on Windows with `unsupported_platform` before any lock, so `aar` — which imports the deliver CLI to register its commands — still loads on the Windows node. Recipe wiring is a later slice.

#### Remote node link (S15a)

How a node on the Windows edit PC does everything `LocalHubLink` and `EventLogTransport` do in process, against a hub on the Linux host in another process. This slice adds the link only; hub-side jobs and the run loop are S15b.

- **Direction.** The node dials out to the hub; the hub never connects to the PC for job work (decision 1). This works with the PC off and behind NAT.
- **Auth.** Identity is an enrolled bearer token, not reachability (decision 3; a default Andrew may change). The hub stays tailnet-only, so the token is a *second* factor, not the only gate. `aar hub node enroll <id> --actor human:<id>` mints a `secrets.token_urlsafe(32)` token, stores only its `sha256` in `node.enrolled`, and prints the token once. `aar hub node revoke` writes `node.revoked`; `--rotate` revokes and re-enrols in one transaction. Lookups fold the enrolment events fresh on every request (no cache outlives a revocation) and compare hashes with `hmac.compare_digest`, so a revoked or rotated token stops working on the very next call. The node reads the token from a file (`token_file`), never an env var; on POSIX a group- or other-readable file is refused, as ssh does (skipped on Windows). The token never appears in a repr, a log line, an exception or the event log.
- **Transport.** `aar hub nodeapi --db [--host <loopback>] [--port 8789] [--allow-remote]` is a Starlette app run by uvicorn with `proxy_headers=False`, opening the existing DB read-write. A non-loopback bind needs `--allow-remote`. Routes: `POST /node/v1/<op>` only (anything else 404, a non-POST 405). `Authorization: Bearer <token>`; a missing, unknown or revoked token is 401 with no detail. The authenticated node id comes from the token; a body `node_id` that differs is 403 `node_mismatch`. `Content-Type: application/json` is required, the body cap is 1 MiB (over it 413), a bad shape is 400 `invalid_request`. Every request carries a validated `request_id` (≤64 chars), echoed back. Responses: `200 {ok, result, replayed, request_id}`; `4xx {ok:false, error:{type, message}, request_id}`. A traceback never appears; an unexpected error is a generic 500. The node side (`aar.node.remote`, stdlib only) caps responses at 4 MiB.
- **Ops** are thin calls into the same hub functions `LocalHubLink`/`EventLogTransport` use: `assert_running` (always checks `node:<token node>` plus `all` and the project), `control_status`, `approval`, `consume_approval` (see idempotent consume), `record_branch`, `branches` (a new `HubLink` read for S15b's branch rebuild), and `feed_deliver` (runs `deliver_feed_event`, keeping the spec's idempotency key so a resend is a no-op). For `consume_approval` and `record_branch` the body `actor` is the job's on-behalf-of actor; it must be `agent`, or `node` with the token's id; a human actor is refused 403 `actor_not_allowed`.
- **Error table** (same contract as `HubLink` and the feed; each row is tested):

  | Node sees | Raised (an `OSError` = unreachable, a `ValueError` = refused) |
  | --- | --- |
  | connection refused/reset, DNS failure, timeout, TLS failure | `HubUnreachable` |
  | 5xx, 429, 503, over-cap response, non-JSON 200 | `HubUnreachable` |
  | typed 4xx: an approval code | the matching `ApprovalError` subclass |
  | 423 `stopped` | `Stopped` |
  | 409 `feed_conflict` | `FeedConflict` |
  | typed 4xx: `unknown_hub_project` / `invalid_input` | `UnknownHubProject` / `InvalidInput` |
  | 4xx with an unknown type | `HubRefused` (generic `ValueError`, carries the code) |
  | 401 or 403 | `NodeNotEnrolled` (a refusal: the runtime stops dispatching and stops the feed, no retry; a human re-enrols) |

  `HubUnreachable` is fail-closed and temporary: the job waits `hub_unreachable` and the feed backs off; a stop issued while the link was down still bites on reconnect, because `assert_running` is a live call before every hot op (decision 5, no cached "running"). A `stopped` is 423 Locked, because an emergency stop is a deliberate hold a human must lift.
- **Idempotent consume across a lost ack.** A retried consume after a dropped response must not park the job. `approvals.consume_for_node` records the authenticated node as `via_node` in the `approval.consumed` payload, in the same transaction as the consume. A retry whose token, scope, target and on-behalf-of actor match the recorded consume, through the same node, returns the first result with `replayed: true` and writes nothing; any other second consume is still refused and audited (`ApprovalAlreadyConsumed`). The local `approvals.consume` is unchanged, so its existing callers keep single-use semantics. The runner's existing write-ahead `approval_pending` intent and `_verify_approval`/`approval` read already heal a lost ack on reconnect (it re-reads the token rather than re-consuming); the hub-side replay is kept as defence in depth for a genuine re-consume.

#### Resolve build ops (S13h1)

The `plan.apply` compiler (S13h2) compiles an EditPlan v2 into hot ops. `aar.node.ops.build` adds the six it was missing; there is no compiler yet.

- **The ops.** `media.import` (edit-PC files into a media-pool bin), `track.ensure` (append tracks; set name, enabled, locked), `transition.add` (a transition at an item's start or end), `item.set_color` (a CDL and/or a LUT on an existing node), `item.set_transform` (zoom, pan, tilt, rotation, flips) and `title.place` (a Text+ title template at an exact record range, with its text).
- **Idempotent by read-back,** like the other write ops: the current state is read first and a match is `present` with no call; every write is read back, and a write that returned True but reads back differently is an `OpError` with a stable code. Lists hold 1 to 50 entries, a target may not repeat, every number is finite and every string is non-blank and bounded.
- **Never destructive.** No op deletes or replaces a track, clip, transition, node or media-pool item it did not create in the same call, moves or relinks media, or changes the project or database. The one deletion is `transition.add` undoing the transition it has just made when its read-back is wrong (`transition_short`, `transition_misplaced`; `transition_left_behind` if the delete fails). An AST scan of `build.py` pins this. Tracks are only appended; there is no `DeleteTrack` op. A title never overwrites: an occupied range is `track_occupied`, and the same template exactly there is reused.
- **Branch guard.** Five ops edit a `timeline` named by unique id, so R3 applies unchanged. `media.import` names no timeline; its guard exemption reads "additive: only adds media-pool items to the named bin and, with create_bins, the missing bins on its path; never alters, moves, relinks or deletes existing items or any timeline". It matches existing items by their `File Path` (separators normalised, ASCII case folded), never re-imports one, and matches what `ImportMedia` returns by `File Path`, never by position; strays and duplicates are reported (`import_unexpected`), never deleted. The bin is made current only for the import, and the folder that was current is put back.
- **No Fairlight mute, solo, bus or bounce in 21.1.** The API has none of these. `AudioTrack.mute` can only be approximated by a disabled track (`track.ensure` with `enabled: false`), which neither plays nor renders (inferred) but is not a Fairlight mute; S13h2 reports bus assignment and bounce as manual steps. A track's channel format cannot be changed by script: an existing audio track of another format is `track_format_mismatch`.
- **Colour.** 21.1 has no CDL getter, so a CDL is sent but never claimed: the result says `verified: false, reason: "no-cdl-getter-21.1"` and lists what was sent. `SetCDL` sets absolute values, so a rerun sends it again. `GetLUT` returns a path relative to the LUT folder, so LUTs compare by normalised trailing components. There is no add-node call: a node that does not exist is `node_out_of_range`. Set colour after `grades.copy`, which replaces the node graph.
- **Titles.** `InsertTitleIntoTimeline` and `InsertFusionTitleIntoTimeline` land at the playhead with a default length that nothing can change afterwards, so `title.place` appends a template media-pool item (a Fusion composition holding a Text+) with `AppendToTimeline`, through the `timeline.append_ranges` machinery, then sets `StyledText` on the comp's `TextPlus` tool and reads it back. Captions and subtitle tracks are not part of S13h1.
- **Transitions.** The handle check before `AddTransition` is advisory (`center` needs `frames // 2` each side, `left`/`right` all of it on one side; the rules are inferred); the read-back of the new transition's type, length and position is the real check. The R6 rule that allows only the head and outro transitions is enforced by `plan.lint` and the compiler, not by the op.
- **Inferred, to confirm in a live smoke** (gated live tests in `tests/node/test_ops_live.py`, on a scratch timeline they create, deleting nothing): `ImportMedia` skips an unreadable path silently and can import a file twice; `StartIndex`/`EndIndex` may be left out; the audio format names; what `AddTransition` does with short handles (the op handles both a shorter transition and `None`); that `DeleteClips` deletes a transition item; the alignment meanings; the `TextPlus` id, the `StyledText` input and its `"\n"` line breaks, and that `SetInput` without a time sets a constant; that `FlipX`/`FlipY` read back as booleans; and that `SetCDL`, like the other setters, can jam after the Color page (the op bounces and retries once).

#### FCPXML export (S18)

The owner's decision (2026-11-08): the app makes edits and saves them in a file Resolve opens, with no running Resolve. `aar.plan.export` is a pure, cold, deterministic library on the hub that writes an EditPlan v2 as one FCPXML 1.10 timeline (`fcpxml > resources > library > event > project > sequence > spine`), imported in Resolve with File > Import > Timeline. It is a sibling of the `plan.apply` compiler, which stays as it is, and reuses its plan-walking helpers (first and last content segment, title track, audio track index, handle arithmetic). It uses only the stdlib (`xml.etree`).

```console
aar plan export PLAN --profile ccn --format fcpxml --out cut.fcpxml [--media-map map.json] [--overwrite] [--json]
aar plan export PLAN --verify cut.fcpxml [--media-map map.json]
```

The export lints first and refuses a plan with lint errors (exit 2); warnings are printed. It writes the file and `cut.report.json` beside it as one pair (both are written to fsynced temporary files, then placed; a failure puts the previous pair back, byte-identical, or leaves nothing for a fresh export, with no temporary file left; the rollback is best effort per destination, and one it cannot put back is named with its final state in `rollback_failed`, or `output_conflict` when another writer replaced it; aar exports to one destination are serialized by exclusive locks on `<name>.aar-lock` beside the FCPXML and the report (`x.fcpxml` and `x.xml` share `x.report.json`), taken in sorted order with the node job store's portable helper and held for the whole write, so a second export fails at once with `output_locked` (another export holds the lock, or the file system has no locks) and touches nothing; the lock files stay; a process outside aar replacing the files mid-export is not serialized, and the identity check is only the best effort against it), never over an existing file unless `--overwrite`, and prints the report. The report's `import` section says how to bring it in (round 4, from the rerun): File > Import > Timeline with "Import source clips" left on, which links each clip to its file (a scripted import needs `importSourceClips: True` with `sourceClipsPath`); a clip links only when its asset starts at the file's start timecode; importing a 9:16 short changes the project's resolution, flipping every timeline without custom settings, so import shorts into a project of their own or a timeline with custom settings, with "Use sizing information" and "Automatically set project settings" ticked (the import otherwise ignores the FCPXML size: a 9:16 short came in at 1920x1080); audio crossfades and fades arrive as volume keyframes on overlapping clips, to replace with Fairlight crossfades by hand if preferred. **Round 3 (Resolve 21.1 import test, 2026-11-08)** set the layout below: what Resolve mishandled is never written. Before handing out a file it reads it back with its own reader and refuses (`self_check_failed`) unless it reproduces the plan exactly. `--verify FILE` runs the same check on any file: exit 0 when it matches, 1 on a mismatch, 2 on unreadable input. Element and attribute names follow Apple's FCPXML reference; the URLs, and the DTD content models the reader checks against, are recorded in aar-evidence/s18/PROGRESS.md.

**Transitions.** Spine clips keep their plan record ranges and abut; a `transition` sits at the edit and plays over the media beyond the outgoing clip's out and the incoming clip's in (handles), so neither clip is lengthened. Its `offset` is the cut minus its frames before the cut: the cut for one that starts on it, the cut − `d // 2` when centred, the cut − `d` when it ends on it. Apple's reference supports this: the spine "contains elements ordered sequentially in time", "only one story element is active at a given time, except when a transition is present" (DTD), and the transition's "offset and duration attributes define the position and extent of the transition effect" (https://developer.apple.com/documentation/professional-video-applications/transition, .../spine); the Resolve read-back is the ground truth. The alignment is the compiler's own rule, `aar.plan.apply.compile.transition_alignment`: centred when the handles hold all its media (`d // 2` frames before the cut on the incoming head, the rest after it on the outgoing tail), else starting on the cut, else ending on it; an unknown source duration counts as no handle (`no_handle_for_transition`). A split-edit crossfade uses the same windows for the sound. Two transitions on one clip may not overlap (`transitions_overlap`). A clip's sound plays its plan range, widened only by a split edit. Final Cut Pro ignores a transition's audio crossfade on a clip with split timing; the report flags each case.

**Media start timecode.** Each `asset` starts at its media's start timecode (`Source.start_timecode` over `Source.start_timecode_rate`, else the plan's fps, as rational time; one that falls between two plan frames is refused as `start_timecode_off_grid`; an unknown one is refused by default as `start_timecode_unknown` (exit 2), naming the sources, since Resolve then links clips only if the file's timecode starts at 00:00:00:00; set it from the clip's "Start TC" in Resolve, the camera metadata or `aar media timecode FILE`, or pass `--allow-unknown-timecode` to write the asset at `0s` with a report note; `aar plan produce` reads BRAW's from its tmcd track since S18a, when the file is local), and every time inside a clip counts from there: its `start` and `audioStart`, its keyframe times, and the `offset` of every item anchored to it (titles, connected clips), which FCPXML measures in the parent's own time. The 2026-11-08 rerun linked every clip only with asset `start` = the file's timecode (01:00:00:00, `3600s` at 24 fps); with `start="0s"` the import with source clips was cancelled, and titles whose offsets were not shifted with their parent landed an hour before the timeline start. Sources that share one file must agree on its timecode (`conflicting_source_start_timecodes`); one left unset takes the other's. The self-check counts each clip's times from its asset's start, checks each asset's start against the plan and each title's and connected clip's resolved position against the plan's frames.

**Media paths.** `src` must be a path Resolve on the edit PC can open. An absolute edit-PC path (`E:\...`, `\\host\share\...`, checked with the build ops' own rule) becomes a percent-encoded `file:` URL. A `file:` URL of a drive or UNC path is used as is. A hub (Linux) path, or a `file:` URL of one, needs `--media-map` (a JSON object of `linux_root -> windows_root`, the S13f path map); without one, or outside it, it is refused as `media_not_on_edit_pc`. A media-pool name (a multicam clip) is refused as `pool_source_not_exportable`, with a hint to give the underlying camera file. Also refused as `media_not_on_edit_pc`, each with a `reason`: a `file:` URL with a drive letter in the host (`file://E:/...`), with userinfo, or with any `%` in the host (an encoded separator would move the host and share); a map root (a directory, not a file); a path component ending in a space or a dot; and a relative name. Two sources whose media map to one file on the edit PC from two different hub files are refused as `media_collides_on_edit_pc`, naming both hub paths: names that differ only in case (`A.mov` and `a.mov` are two files on the hub and one on Windows), or map roots that overlap. Paths are compared as NTFS compares names (`ntfs_upper`, either separator). Only mapped hub paths are compared, because only there are the two known to be different files; one hub file used by two sources stays one asset. The `ccn-longform` params refuse the same pair before the run starts. `aar plan produce` keeps a stub's media names as given, so a stub for export must give absolute edit-PC paths, or hub paths with `--media-map`. Each asset starts at 0s, so source frames count from each file's first frame; its duration is the source's, or the furthest frame used (reported).

**Refusals** are typed `ExportError`s: `lint_errors`, `fps_not_representable`, `bad_timeline_start`, `empty_timeline`, `unknown_source`, `zero_length_segment`, `media_not_on_edit_pc`, `media_collides_on_edit_pc`, `source_size_required`, `pool_source_not_exportable`, `bad_media_map`, `outro_audio_track_missing`, `duplicate_transition`, `no_handle_for_transition`, `transitions_overlap`, `duplicate_keyframe_time`, `non_finite_value`, `unsafe_text` (text XML 1.0 cannot carry exactly), `fade_too_long`, `item_outside_timeline`, `self_check_failed` and `output_exists`.

**The self-check** parses the file with the stdlib, refuses entity declarations and DOCTYPE internal subsets before parsing, checks every element, attribute and child order it meets against the FCPXML 1.10 content models of the elements aar writes, every id and `ref`, and every time (an exact rational on a frame boundary). It fails anything the writer never emits, as an allowlist: an element (a `marker`), an attribute (`enabled`, `anchor`, `srcEnable`, ...), a value of a fixed attribute (`tcFormat`, `audioRate`, `kind`, fade and keyframe types, asset `start`, `hasAudio`, ...), or a second `media-rep`, so a hand-edited or foreign file cannot pass. It then rebuilds the timeline (each segment's track, record in and out, source in and out and media, each transition's cut, length (its window's frames before the cut decoded from its offset) and effect name and uid, split crossfades from the clips' sound ranges and fades, sound ranges, volumes, fades, conform, transforms and keyframes, titles, markers and assets with their start and duration) and requires it to equal the plan; spine clips must abut and never overlap; it checks that every clip, with the handles its transitions play, reads inside its asset and its plan source, and recomputes each filled clip's crop window from the XML (conform, scale, rotation, position, source size) against the plan's reframe within 0.5 source pixels.

**Confirmed by the 2026-11-08 import test and its rerun:** clips link to their files only with asset `start` = the media's start timecode (the first run's "source frames count from the file's first frame" was measured on unlinked clips and is withdrawn); with that, the stills show the right source frames, the 9:16 fill and reframe (position is a percentage of the timeline's height), the exact cut at 216 and the outro dissolve drawn from segment 4's tail handle; the outro once; dense lanes; audio fades arrive as volume keyframes on overlapping clips, not Fairlight crossfades; importing a 9:16 timeline changes the project's resolution (import shorts into their own project or a timeline with custom settings); cut lengths, order and record positions; the 01:00:00:00 start; the head dissolve; static zoom; clip gains; titles at their frames; the split crossfade keeps the picture cut (the overlap goes on another audio track: the rerun found A1 holding the later clip's sound). **Still to confirm:** that a centred or left-aligned transition plays the handles as written; the audio track each lane's sound lands on; `fadeIn`/`fadeOut` and keyframed `adjust-transform` (not readable by script); negative scale as a flip and the pan, tilt and rotation signs; titles at their frames on timecoded media (offsets in the parent's timecode-based time); the Basic Title and the effect uids (`FxPlug:4731E73A-8DAC-4113-9A30-AE85B1761265` for Cross Dissolve, `FFAudioTransition` for the audio crossfade), which come from Final Cut Pro's own exports.

#### Hub render (S18b)

The owner's direction (2026-11-08): review copies and simple masters need no edit PC. `aar.plan.render` renders an EditPlan v2 to MP4 with ffmpeg on the hub, from the hub's own media copies (docs/MEDIA-STORE.md), with no Resolve. The results feed `aar.deliver` and `aar.qa` as any render does.

```console
aar plan render PLAN --profile ccn --out cut.mp4 [--media-map map.json] [--preset review|master] [--memory-budget MB] [--transcript T] [--laughs L] [--overwrite] [--json]
```

It lints first and refuses a plan with lint errors (exit 2), as the export does, and a plan whose resolution has an odd side (`odd_resolution`: 4:2:0 and 4:2:2 need even sides). **Media.** Every used source must be a readable hub file: a plan media path that exists (absolute, a `file:` URL of one, or relative to the plan file's folder), or an edit-PC path (`E:\...`, UNC, or a `file:` URL of one) mapped through `--media-map`, the export's own `linux_root -> windows_root` JSON read the other way. Anything else is `media_not_on_hub` with a `reason` (`no-media-map`, `not-in-media-map`, `missing`, `unreadable`, `pool-name`, `relative`). Each file is probed (`aar.media.probe`, plus a timing probe of stream start times, frame counts, base and average rates, and one ffprobe pass over **every** video packet's timestamp, round 3, cached by the file's identity, size and mtime: about 0.1 s for a 10-minute 1080p file) and refused unless it can be cut exactly (round 2): unreadable media, a video stream with no time base, or one whose index lists more frames than its packets hold (a truncated copy, checked first: its last packets leave a hole that would read as a variable rate) is `media_unreadable`; no video stream `no_video_stream`; a base frame rate more than 0.01 % from the plan's `source_rate_mismatch` (24 fps in a 23.976 plan drifts 0.6 s in 10 minutes); a variable frame rate `source_vfr`: any step between two packet timestamps (sorted, so B-frames are in order) that is not one frame within 1/8 frame, naming its time (a 20 ms jump, a dropped frame), then base and average rates more than 0.1 % apart, or a frame count other than the stream's duration times its rate; an unknown picture size `size_not_renderable`; and a `Source.frame_size` whose aspect is not the file's display aspect (0.5 % tolerance) `frame_size_mismatch`. Both rate refusals say to conform the media first. The frame count is the **video stream's** (`nb_frames`, else its packet count), never the container's duration; the stream's duration for the frame-count test is its own `duration`, else its Matroska `DURATION` tag less the stream's start time (round 4: ffmpeg's Matroska muxer writes that tag as the stream's end timestamp, so a 250-frame 25 fps video starting at 5 s says 15 s; a missing start counts as 0, and a non-positive result skips the test); a clip that plays past its file's last video frame (handles included) is `segment_past_media_end`, naming the clip.

**One layout.** The render builds S18's own `Layout` (`build_layout` with a resolver that gives the hub paths, `resolve_media`, a pinned extraction whose default is the FCPXML rules), so clip record ranges, transition windows and alignment (the compiler's `transition_alignment`), split-edit sound ranges and fades, the head and end fades, framing (`fill` conform, `source_size_required`) and each clip's volume (segment gain plus its audio track's gain) are the export's. Start timecodes do not matter to a render and are left out of its layout copy.

**One input per use (round 2).** Every picture and every sound is its own ffmpeg input: the file opened again with an accurate input seek just before the range it plays (`-ss` half a frame before a picture's first frame, a quarter second before a sound's first sample), decoding on one thread. So nothing is decoded from a file's start, no decoded frames queue between two uses of one file, and each use is cut exactly where it starts (the round-1 graph split one input per file, and ffmpeg 6.1's `amix` then zeroed a sound whose frames were queued before it reached them).

**Memory bounded by construction (round 3).** An open picture input holds decoded frames whether or not the graph reads it yet: the validation measured 1,177 MB plus 44.7 MB per 1080p picture use (r = 0.99999), 14.6 GB for a 300-cut long-form in one ffmpeg. So the picture is encoded in **chunks**, one ffmpeg after another, each with its own graph over its record frames and only its own pictures' inputs, and joined by stream copy. The **budget** is `min(6 GiB, half of MemAvailable, the free headroom of every cgroup above the process that sets memory.max)`, read at render start; a cgroup's headroom is `memory.max - (memory.current - inactive_file)` from its `memory.stat`, floored at 0 (round 4: cgroup v2 lets page cache fill a group to its limit, and inactive file pages are reclaimed first, so they are room; Command Center's group is mostly cache), or `memory.max - memory.current` when `memory.stat` is missing or unreadable; `[render] memory_budget_mb` or `--memory-budget` replaces it (the round-2 `decode_memory_mb` is accepted and ignored). The **cost model** is the measurement rounded up: a base of 300 MB plus 1,000 MB at a 1080p output (scaled by output pixels), and per picture use 50 MB, or 80 MB windowed (a crop, punch-in or moving reframe; measured 63 MB), at a 1080p 8-bit 4:2:0 source scaled by its decoded bytes per frame, plus 2 MB. A chunk is cut only at a **hard cut**, a record frame no picture crosses on any track: a dissolve's window, a head fade and a moving reframe all lie inside a picture (the outgoing picture plays through the window), so none is split; titles are static text and are drawn on both sides. Chunks are packed greedily to the budget (and to the filter-script limit); when the pictures between two hard cuts alone are over the budget the render is refused (`render_too_large`, naming the record frames, their times, the picture count and the encoder's share); when the encoder's base alone is over it (a 4K output needs 4,300 MB) the refusal says so, naming the base, the budget and the output size. The mix runs in passes of at most `(budget - 200 MB) / 5 MB` sounds (measured: 305 MB at 75 sounds, 539 MB at 150), each over its own sounds' samples, summed in one more pass; at 6 GiB that is one pass up to about 1,180 sounds. Every chunk is encoded with identical encoder arguments (closed GOPs: x264's first frame is an IDR), read back and required to hold exactly its frames, start on a key frame and share the first chunk's stream setup (codec, profile, level, size, format, reorder depth, time base, extradata hash), else `render_incomplete`. The join is the concat demuxer (exact `duration` per chunk) with `-c:v copy`, the sound muxed once; the demuxer places chunks in microseconds, so `setts` puts every presentation time back on the frame grid and numbers the decode times one frame apart behind the chunks' shared reorder delay: one continuous stream with one SPS/PPS set, exact timestamps, a video track timescale that holds a frame in whole ticks. The joined file is then read back: exactly the timeline's frames, presentation times one unbroken frame grid, decode times strictly increasing and never after presentation, and a sound stream.

| Plan concept | Render |
| ------------ | ------ |
| Segment ranges | Pictures: cut by **presentation timestamp** (round 3; `-copyts`, `trim=start_pts:end_pts` in the stream's own ticks, from half a frame before the first frame to half a frame before the one after the last), then `settb` + `setpts=N` at the plan's rate, and everything after that joins by frame count (`concat`, `trim=start_frame:end_frame`, `blend`/`overlay` with `shortest=1`). A frame that is missing or does not decode (a damaged file) therefore leaves its chunk short instead of shifting the rest: the chunk fails its frame count and the render is refused (`render_incomplete`), naming the clip, the source, the file and the source frame range whose decode came up short (each picture re-decoded alone to find it). Sounds: cut by timestamp (`-copyts`, `atrim=start_pts:end_pts` at 48 kHz) at the absolute time the sound's first frame is shown, so a source whose audio starts after its video stays in sync (noted) and an audio start after the sound's own start is silence; every record position is converted from frames exactly (`round(frame * den * 48000 / num)`: 2002 samples a frame at 23.976) |
| Framing | A conformed clip (`fill`: aspect differs, reframe or transform) shows S18's crop window (`aar.plan.export.verify.window_from_plan`) at each frame, its reframe `x`, `y`, `zoom` linear between keys and held outside them (head-handle frames included). The window's four corners (S18's transform maths: a rotation or flip rotates or mirrors the window) go to `perspective` (`sense=source`) as one expression per coordinate in the filter's frame count, `A * x + B / zoom + C` piecewise over the keys (chosen by a balanced tree of tests, so nesting grows with the log of the key count), exact at every frame, with a half-pixel correction (perspective maps pixel indices). Keys on a straight line between their neighbours are merged first (the same path); a window that still needs more than 256 KiB of per-frame expressions (perspective parses them at every frame), or a chunk's picture script over 512 KiB, is `reframe_too_complex`. That cap is about **300 keys per moving window** (measured: 300 keys give 31.9 KB per corner expression, about 255 KB for the eight), roughly 2.5 minutes of face tracking at 0.5 s steps; a longer moving segment is refused (an explicit limit, kept in round 3: split the segment). The source is padded with black where a window leaves the picture (Resolve shows black there) and cropped to the box all the clip's windows fit in first; `scale` makes the timeline size. An unconformed clip is scaled when its aspect is the timeline's, else fitted (letterboxed, Resolve's default, noted) and padded in 4:4:4 (the format right before the pad, after the scale: round 3, an odd margin such as 187 px is not rounded down to 186 for the chroma), so it sits exactly in the middle |
| Dissolves | At the window S18 chose, playing the handles: the outgoing picture runs `tail_part` past its out, the incoming starts `head_part` before its in. The spine is one `concat` of run bodies and, for each dissolve, a `blend` of the outgoing run's last n frames and the incoming run's first n (`shortest=1`, cut by frame count: round 3, so a frame missing before a dissolve shortens the chunk where round 2's fixed `xfade` offset hid it). Frame k of n is weighted k/n incoming (as xfade did: the first window frame is all outgoing, the frame after it all incoming; S18's layout and FCPXML fix only the window, not the weights). The head from black is a `fade` on the first picture |
| Connected clips (V2+), outro off V1 | Each track a full-length stream of its clips and transparent gaps (`concat`), laid over the spine with `overlay` (`shortest=1`), the higher track on top |
| Titles, lower thirds, sting | `drawtext` per line on their record frames (`enable` on the frame number), white on a 55 % black box: lower thirds bottom left, titles and the sting centred. | Sound | Each clip's sound plays S18's `sound_range` and `fades` (a split edit's J/L overlap), widened by a dissolve's audio crossfade onto both handles; gains by `volume`, fades and crossfades by linear `afade` ("Cross Fade 0 dB"). Each sound is exactly its own length; the sounds go on as few layers as there are overlaps (S18's `stack_lanes`: two for an edit with crossfades), each layer a `concat` of silences and sounds to the timeline's exact sample length, and the layers are summed by `amix normalize=0` (every layer the same length, so none ends early). Round 3: no sound is padded to the timeline any more, so the mix's work is linear in the timeline (round 2 padded every sound and summed them all: 382 s for 400 sounds on 10 minutes, exponent 1.99). A mono source plays on both channels; a file with more than two plays its first two (noted) |
| Mute and bus | A muted track that feeds a bus stays audible (the CCN A1-A4 topology, as in S18); a muted track that feeds no bus is silent (noted), and the FCPXML export writes its clips silent to match. Bus routing and the bus track's gain on its feeders are not rendered (reported, as in S18) |
| Loudness | Both kinds (round 2): the mix is measured, brought to its kind's `[qa]` target by one linear gain, and a true-peak limiter (`alimiter` at 192 kHz, latency compensated) holds the peaks at `[qa] true_peak_max_dbtp` - `[render] true_peak_margin_db` (0.5), so the AAC encode stays at or under -1 dBTP. It is measured again and the gain corrected (up to twice: limiting loud peaks lowers the loudness) while it lands further than `gain_tolerance_lu` (0.1 LU) away. Nothing compresses the programme: loudnorm (round 1, long-forms) fell back to its dynamic mode on wide-range or peaky material, compressing the laugh range and missing the target. The report gives the achieved loudness and the limiter's gain reduction (the true peak the gain alone would give less the one measured), and warns when that passes `limiter_warn_db` (3 dB). A silent mix is not normalized (reported; QA fails it). The processed sound must keep the timeline's exact sample count (`render_incomplete` otherwise) |
| `Source.color` | A `lut` that names a LUT file on the hub (`.cube`, `.3dl`, ...) is applied with `lut3d`; a Resolve LUT name, the CDL and the input colour space are not rendered (reported) |
| Not rendered (reported) | `template`, markers, captions and `caption_style` (S13e burns captions in), transition types other than dissolve (rendered as a dissolve, as the export writes them), audio crossfade lengths or types that differ from the dissolve, the outro's audio transition, transitions the layout drops (off V1, across a gap), Resolve title templates (drawn as plain text) |

**Output.** `review` is H.264 High yuv420p (`[render] review_crf` 20, preset medium) with AAC (192 kbit/s) and `+faststart`, at the plan's resolution and frame rate; `master` is H.264 High at `master_crf` 14 (preset slow, AAC 320 kbit/s), or ProRes 422 HQ (`prores_ks` profile 3, yuv422p10le, PCM 24-bit) in a `.mov` when `[render] master_codec = "prores"` (a `.mp4` out is then `bad_output_path`). The MP4's movie timescale is 48 kHz, so the sound track's edit list states its exact length (ffmpeg's own decoder still emits the last AAC frame whole). After the join the render reads the file back and requires exactly the timeline's frames as one continuous stream and a sound stream (above; `render_incomplete`, never left to QA); then `aar.qa.check` runs with the plan's kind (the plan's media replaced by the hub paths, so the join checks read the sources), and the report `<stem>.render.json` (never the export's `<stem>.report.json`) says what was rendered (pictures with their framing and first and last crop window, dissolves, sounds, titles, LUTs, the font), the media and probe facts (frame counts, stream start times), the loudness passes and measurements, the memory plan (`memory`: the budget and where it came from, each chunk's record frames, pictures and planned MB, the mix passes), the QA report, every plan feature not rendered (`not_rendered`) and notes. The file and its report are placed as one pair by S18's pair writer (`write_pair`, which also takes a finished file and moves it), never over existing files without `--overwrite`; a failure leaves the previous pair or nothing.

**Exact numbers in graphs.** Every Fraction written into an ffmpeg argument or graph (seek times, dissolve durations) goes through `aar.plan.render.fixed.decimal`: integer arithmetic, rounding half to even, byte-identical to Python 3.12's `format(x, ".6f")`; Python 3.11's `Fraction` takes no format spec (round 4: CI on 3.11 failed there), and the test suite runs with `Fraction.__format__` behaving as on 3.11 so such a spec fails locally too.

**Bounded.** Every graph is an argv list with `-filter_complex_script` files in a per-render work dir beside the output (`.<name>.aar-render-<token>`, so the result is placed by a rename on its own file system); ffmpeg runs there (`run_tool` gained `cwd`), so side files (title text, the font, a LUT) have plain relative names and no path needs filtergraph escaping. Every ffmpeg call has a timeout of `[render] timeout_base_s` + `timeout_per_media_s` x the source seconds it decodes (each use's span plus a seek's slack, and the chunk itself for its encode, the timeline for the loudness passes and the join), kills its process group on expiry, and keeps a bounded stderr tail. SIGTERM is handled like Ctrl-C: ffmpeg's process group is killed and the work dir removed (the CLI exits 143). The work dir is removed on success and failure. Nothing touches `/tmp` or the network. Refusals and failures are typed `RenderError`s: the render's own codes (`media_not_on_hub`, `media_unreadable`, `no_video_stream`, `source_rate_mismatch`, `source_vfr`, `size_not_renderable`, `frame_size_mismatch`, `segment_past_media_end`, `odd_resolution`, `reframe_too_complex`, `render_too_large`, `bad_output_path`, `tool_missing`, `render_failed`, `render_timeout`, `render_incomplete`) plus every export code the shared layout and pair writer raise. The CLI exits 0 when it rendered and QA did not fail, 1 when it rendered and QA failed (the file and report are written), 2 for a refusal or unreadable input, 3 when ffmpeg failed, timed out or left an incomplete file, and 143 on SIGTERM.

**Verified (S18b) with synthetic media** that encodes the frame index as a 4x4 bit block inside a black ring, a per-source colour and a per-source tone (or seeded noise): every output frame of the CCN long-form fixture is the source frame the S18 layout puts there (cuts exact) except inside the dissolve (a blend at its midpoint) and the head fade; the reframed short's crop edges sit within 0.1 source px of S18's windows at every frame (the test allows 1 px); rotations, flips and pans put the picture where S18's FCPXML transform does (under 1 px); tones per segment, the split crossfade's linear ramps, gains within 0.5 dB, sound placement to 2 ms (to the sample at 29.97 on a PCM master), a file reused out of order with every sound kept, a late audio start in sync, and each kind's loudness through QA. Round 2 also replays the independent validation's harness (its random plans, decoders and checks) over the new code.

#### Native Fusion graphics

`aar.fusion` adds cold, headless support for DaVinci Resolve Fusion `.setting` macros and `.drfx` packages on the hub, paired with alpha-preserving rendering, companion `.fusion.json` export manifests, `ccn-longform` auxiliary sources/templates, and live Resolve `MacroOperator` input writes.

- **Template parser, customizer, and CLI (`aar.fusion`, `aar fusion inspect|customize|render|manifest`).** Parses Resolve's Lua table `.setting` syntax (including `ordered()`, `MacroOperator`/`GroupOperator`, `InstanceInput`/`InstanceOutput`, `FuID`, and nested `Expression` strings) and `.drfx` archives without `eval()`, extracts published inputs, `Loader` assets (`Templates:`/`Setting:`/adjacent/search-dir resolution), and `TextPlus` fonts, and round-trips customized `.setting` files while preserving expressions and formatting.
- **Headless RGBA renderer (`aar.fusion.expr`, `aar.fusion.render`, optional extra `fusion = ["Pillow>=10"]`).** A safe recursive-descent Fusion Lua expression evaluator (`time`, `comp.RenderStart`/`RenderEnd`, `Point(x, y)`, `min`/`max`/`clamp`/`iif`/`math.*`, sibling properties, and 1-based `Output.DataWindow[1..4]`) drives a Pillow + ffmpeg compositor covering `Background`, `RectangleMask`, `EllipseMask`, `Loader`, `TextPlus`, `Transform` (`Xf`), `Merge`, and `Dissolve` (plus `BezierSpline` keyframe curves). Emits RGBA PNG stills or alpha-preserving `.mov` clips (`qtrle` ARGB, `prores4444` `yuva444p10le`, or `png`) with SMPTE `00:00:00:00` timecode so both Resolve and `aar plan stub` link them cleanly.
- **EditPlan v2 & hub render (`aar.plan.model`, `aar.plan.render`).** `Title` and `Sting` accept optional `setting` (`.setting`/`.drfx` ref) and `inputs` (named scalars or 2D points), `TitleKind` adds `"graphic"`, `Title.lines` may be empty when `setting` or `inputs` is set, and `RenderSettings` adds `fusion_templates_dir` (while `version = 1` refuses them and `plan_hash` stays unchanged for plain titles). Connected video lanes (`V2+`) whose probed media carries an alpha channel preserve alpha (`yuva444p` / `yuva420p` / `black@0` / `fade:alpha=1`) instead of stripping through `yuv420p`. When a `Title` or `Sting` specifies `setting`, `render_plan` pre-renders it to an alpha `.mov` inside the render work dir and composites it in lane order alongside plain titles (raising `fusion_template_missing`, `fusion_render_failed`, or `render_timeout` on failure instead of silently falling back).
- **FCPXML export, `ccn-longform`, and live Resolve (`aar.plan.export`, `aar.recipes.ccn`, `aar.node.ops.build`).** `export_fcpxml` / `aar plan export` still emits a self-checked Basic Title placeholder (FCPXML 1.10 cannot embed Fusion macros directly) and writes a companion `<stem>.fusion.json` manifest (and optional customized `.setting` files) only when Fusion titles/stings are present so existing goldens stay byte-identical. `build_stub(..., extra_sources=())` and `ccn-longform` params (`extra_sources`, `fusion_templates`) support video-only alpha `.mov` overlays (`recording_id=None`), forward the explicit `fusion_templates` allowlist and `AAR_MEDIA_ROOT` confinement to `render_step`, copy `.fusion.json` in `export_step`, and list placements under `FUSION GRAPHICS` in the handoff notes. On the live Resolve path, `title.place` and `plan.apply` support `MacroOperator`/`GroupOperator` named inputs, `Tool.Param` targeting, optional `.setting` loading (`ImportFusionComp`/`LoadSettings`) with idempotent reuse on retries, and read-back verification.

#### CCN long-form recipe (S19a)

The first real recipe chains the Linux-only steps into one run on the hub, with the edit PC off. Decisions D8/D9 (2026-11-12): the hub holds **proxy copies only** (the camera proxies, 1080p H.264 with a tmcd track) on a media root that is read-only inside agent sandboxes; the PC maps `<media root>/share` as a network drive (docs/MEDIA-STORE.md). The S19 pilot (a 90-minute single-camera show by hand) is the acceptance reference.

**Plan stub (`aar.plan.stub`, `aar plan stub MEDIA... --out STUB --recording R --project P --timeline T [--kind] [--profile] [--camera L]... [--shot-size S]... [--source-id I]... [--part N]... [--placement CAMERA=timecode|contiguous]... [--resolution WxH] [--base JSON] [--allow-unknown-timecode] [--force] [--json]`).** Builds the stub `aar plan produce` takes from hub media files, so nobody writes it by hand. Per source: the hub path as `media`, the video stream's frame count as `duration`, the display size as `frame_size`, and `start_timecode` with its rate. Nothing is measured twice: the frame count, size and constant-rate check are the hub render's `resolve_source` (one packet scan), the rate is the producer's `media_timecode_rate` (snapped), and the timecode is the producer's `probe_sources` + `source_start_timecodes` (ffprobe's tag, else the tmcd track). Every source belongs to the recording at origin 0 (sync sets the others in `produce --sync`); a source without a camera label gets A, B, C... by position (the profile's `default_camera` is A) and without an id `cam-<label>`. **A camera of several files (S24a):** sources that share a camera label and give `part` 1..n are one camera's consecutive files (a camera that splits its recording, an operator who stopped and started). Only the reference camera (the first source's) may be several files for now (another is refused `parts_unsupported`: S24b). Its parts go first in the stub, in part order, with ids `cam-<label>-p<n>`, `part` and `part_placement` set (two v2 `Source` fields), and each part's `recording_origin` placed by the camera's placement: `timecode` (the default when every part's start timecode was read: the part's start timecode less the first part's, in frames at the plan rate, drop-frame counted as the frames it labels, a start before the previous part's read as the next day when the wrapped gap is at most 12 h) or `contiguous` (each part where the previous ends; the default without timecodes, with a `parts-contiguous` warning, when `allow_unknown_timecode` lets them through). The report's `parts` gives each part's origin, duration, gap to the previous part (frames) and placement. Refused: `bad_parts` (a part without a camera label, a label repeated without parts, part numbers that are not 1..n, a placement for a camera of one file), `parts_overlap` (a part starting more than 2 frames before the previous one ends), `parts_out_of_order` (a part's timecode before the previous part's, and not a midnight wrap), `parts_rate` (a timecode at another rate than the plan's), and `timecode_unknown` for a camera placed by timecode with a part whose timecode cannot be read. A stub holds at most 48 files. The plan runs at the first source's rate; the resolution defaults to its display size for a long-form (a short must give one). A base JSON's `template`, `head`, `outro` and `audio_tracks` pass through (with the outro's source from its `sources`); other keys are listed as ignored. Refusals are `StubError`s, exit 2: `unreadable` (also a FIFO, a directory or a path that is not UTF-8), `no_video`, `no_audio`, `vfr`, `rates_differ`, `timecode_unknown` (unless `allow_unknown_timecode`, the export's own opt-out), `timecode_ambiguous`, `duplicate_source_id`, `duplicate_media` (one file twice, directly, through a symlink or through a hardlink: real paths and `(st_dev, st_ino)` compared, by `first_duplicate`, which the recipe's params use too), `resolution_required`, `bad_base`, `invalid_stub`, and the parts' codes above. The stub loads through `load_stub` and, with a transcript and a keep list, produces a plan that lints clean (tested on synthetic media).

**Reading artifacts (`aar hub artifact get ID --db --artifacts [--out FILE] [--force] [--project P]`).** Copies one artifact out of the store, verified against its sha256 as it is read, to a file (never over one unless `--force`) or stdout; exit 2 with a JSON error otherwise. The agent uses it to read the stub and the transcript.

SIGTERM during the render (the render's own handler kills ffmpeg) hands the signal back to the worker and leaves the claim to lapse, so the op is claimed again (no attempt used); a SIGKILL does the same through the lapsed lease. Outputs carry `subject_node` (the plan node) and `artifact_ids` (the MP4) for the gate, and `review_timeline` and `review_fps` (the timeline's name and the plan's rate as a number) for its review |
| `export` | cold, idempotent, 1 h, `on_fail="cut"` | The plan checked as for the render, then `export_fcpxml` with the params' media map (hub root -> edit-PC root) and the run's `allow_unknown_timecode`; the FCPXML and its report are stored, and so are the **handoff notes** (`aar.recipes.ccn.handoff`, plain text): how to import, the edit-PC media paths the timeline links (said to be unchecked: the hub cannot see them, so a missing file or a different file under the same name shows only as Media Offline or a wrong frame after the import), what the review video's sound has that the timeline does not (the render's one gain and its limiter, with the numbers; the gain is deliberately not written into the clips, because without the limiter it would clip the peaks the review tamed, and mastering belongs to the PC), every feature the FCPXML cannot carry with what to do, and the markers to add by hand. Then the review MP4, the notes and the FCPXML are copied to `AAR_EXPORT_DIR/<project>/<timeline>/` as `<timeline>.r<round>.review.mp4`, `.r<round>.notes.txt` and `.r<round>.fcpxml`. The copy is the step's purpose: with `AAR_EXPORT_DIR` unset the step fails `export_dir_unset` before any work (not the cut's fault: fix the worker's environment and `recipe_retry export`), so no review opens on a timeline nobody was given. A round is published whole or not at all: every file is written to a temporary name and fsynced first, then each is placed, the FCPXML last, and a failure removes what was placed; an importable timeline is therefore in the share only when its review video and notes already are, even after a crash between two placements. The notes are also the export's `review_attachments` output, which the gate's review carries and the console shows on the review card (below). The project and timeline come from the stub step's runner-recorded outputs (the brief's show, the params' timeline), never from the plan; names are made safe for Windows (`safe_name`: device names such as `CON`, `con .txt`, `LPT1 ` get a `_`). No symlink is followed: a folder below `AAR_EXPORT_DIR` that is a symlink or not a folder fails `export_path_symlink`, and a file name taken by other bytes, a symlink (dangling too) or anything not a regular file moves the pair to `-2`, `-3`... (at most 50); a name holding the same bytes is reused (a re-run copies nothing twice). No file is ever replaced |
| `review` | gate, subject `render`, `on_reject="cut"` | A human reviews the render; a rejection starts the next round from `cut` (the transcript, stub and sync are never redone) |
| `report` | cold | The built-in `recipe.report` |

**Params** (`CcnLongformParams`, `extra="forbid"`): `sources` (1-48 of `{path, camera?, shot_size?, id?, part?}`; the first is the reference; sources of one `camera` with `part` 1..n are its consecutive files, S24a, and only the reference camera may be several files: another is refused naming S24b, a label repeated without parts or part numbers that are not 1..n are refused), `recording_id`, `timeline`, `kind` (longform, short), `media_map` (1-16 entries, parsed as the export parses it; it must cover every source, and no two sources may map to one file on the edit PC, such as names that differ only in case), `whisper_model` (default `medium.en`), `whisper_threads` (0-64), `normalize_audio` (default true), `pause_trim` (`auto`: off for one camera, on for several, counting cameras, not files; `on`; `off`), `laughs` (default false), `allow_unknown_timecode`, `part_placement` (camera label -> `timecode` or `contiguous`, for the reference camera of several files; default by timecode when every part has one). The S24 `extra_sources` (graphics, intros, outros) count towards the same 48-file bound, are never parts (`part` on one is refused) and are not cameras (not in `cameras`, `camera_labels` or the guide's camera line). For example, one camera of three files placed by timecode: `{"sources": [{"path": "/media/cam-a_C001.mov", "camera": "A", "part": 1}, {"path": "/media/cam-a_C002.mov", "camera": "A", "part": 2}, {"path": "/media/cam-a_C003.mov", "camera": "A", "part": 3}], "recording_id": "show-1", "timeline": "Synthetic Long v1", "media_map": {"/media": "E:\\Shows"}}`. Every path is checked at the boundary: absolute, no `.`/`..`, an existing regular file, under `AAR_MEDIA_ROOT` (`realpath`) when that is set. The worker re-validates on every step, so a file removed later fails the step `invalid_params`.

**How a run starts.** A show usually has no Resolve project yet. Register it without a source (`aar hub project add --name SHOW --actor agent:ID --idempotency-key KEY`, or `project_register` with only a name); if the name is already taken, `project_exists` gives the `existing_id` to use. Then `brief_create` (the brief's `project_id`, `show`, `recipe: "ccn-longform"`, `rule_profile`), `recipe_create` with the params, and `aar recipe start`. Nothing in the run needs a Resolve source; it is attached with `aar hub project source` (or the `project_source` tool) once the edit PC has imported the export and a Resolve project exists. Registering that Resolve project as a new project under the show's name is refused (`project_exists`): the show keeps its one id.

**Every cold step** fails with a typed `StepFailure` and a fix hint (`stub_<code>`, `sync_<type>`, `transcript_<type>`, `laughs_<type>`, `render_<code>`, `export_<code>`, `work_dir_unset`, `kind_mismatch`, `qa_failed`, `export_copy_failed`...), keeps its scratch under `AAR_WORK_DIR` (never `/tmp`, never the artifact store's disk) and removes it on success and failure, calls the libraries (never the `aar` CLI), and checks `ctx.cancelled()` before each long phase (the libraries themselves cannot be interrupted): a stopping worker then raises `StepInterrupted` past the worker, which records nothing, so the claim lapses and the idempotent step is claimed again without using an attempt. Library timeouts (the decode in the transcript, sync and laughs) are their defaults cut to the step's time left. Timeouts are sized to a 90-minute show (pilot: transcript 9-30 min, render about 0.8x realtime of the cut, export under a second).

**Limitations of the engine, by design (S13g2, S19f).** A step's failure can be retried; a gate's rejection goes back to an earlier step in the next round; and, since S19f, a failure marked upstream can be answered by an explicit `recipe_reopen` of the step's `on_fail` agent step in the same round. Nothing goes back by itself. A failure that is not marked (the environment) can only be retried, or the run cancelled; a retry of a marked failure renders the same plan again and fails the same way, which is why the status view offers the reopen instead.

**Which render and export failures are the cut's (S19f).** `render` and `export` declare `on_fail="cut"`. A failure is marked upstream exactly when a different plan can fix it; the one table is `aar.recipes.ccn.faults` (each code decided from the code that raises it), and a marked failure's fix hint names `recipe_reopen cut`. Marked: `plan_not_from_stub` (the plan's frame, sources or names differ from the stub); `qa_failed` only when every failing required QA check ran on the content and judged it (`faults.qa_failure_upstream`: `loudness` with `integrated_lufs` measured (and, when it is above -70 LUFS, the true peak too), `clipping` with `clipped_samples` counted, `join-quiet` with every failed join's audio read and judged, i.e. carrying `run_at_cut`; the check not `incomplete` and not in the report's `unchecked`); at render (`render_<code>`) and export (`export_<code>`) the plan layout codes the exporter raises and the renderer passes through: `lint_errors`, `empty_timeline`, `unknown_source`, `zero_length_segment`, `source_size_required`, `conflicting_source_durations`, `conflicting_source_start_timecodes`, `outro_audio_track_missing`, `duplicate_transition`, `no_handle_for_transition`, `transitions_overlap`, `duplicate_keyframe_time`, `non_finite_value`, `unsafe_text`, `fade_too_long`, `item_outside_timeline`; at render only, `segment_past_media_end`, `reframe_too_complex`, and `render_too_large` when its reason is `pictures` and more than one picture overlaps (`pictures > 1`: too many overlapping pictures with no hard cut). Unmarked (the environment; retry or fix the hub): `media_changed`; `qa_failed` when any failing check could not run or check everything (an ffprobe or decode timeout, a `MediaError` while measuring, no audio stream, NaN samples, an unknown duration, an `incomplete` check, a check missing or skipped), a `loudness` failure whose true peak was not measured, and whenever `decode`, `duration`, `longest-silence` or `size-cap` fails (the renderer's output; for `duration`, the renderer already refuses output that does not hold the timeline's frames, `render_incomplete`, so a QA duration failure after it is the container or the measurement; a check that only warns; a cap not applied here), its hint saying to retry the render; `render_too_large` for one picture alone over the budget (its cost is the stub source's frame size, which no cut changes, and the budget is the machine's free memory), for the encoder alone at the stub's resolution or a budget that holds no sound; `media_not_on_hub`, `media_unreadable`, `no_video_stream`, `source_rate_mismatch`, `source_vfr`, `size_not_renderable`, `frame_size_mismatch`, `odd_resolution` (the media, or the stub's own values, which `check_plan` holds the plan to), `tool_missing`, `render_failed`, `render_timeout`, `render_incomplete`, `bad_output_path`; at export `fps_not_representable`, `bad_timeline_start`, `start_timecode_off_grid`, `start_timecode_unknown` (the stub's or the profile's values, the params' `allow_unknown_timecode`), `bad_media_map`, `media_not_on_edit_pc`, `pool_source_not_exportable` (the params' media map), `self_check_failed`, `output_exists`, `output_conflict`, `rollback_failed`, `output_locked`; and the steps' own `invalid_params`, `no_profile`, `missing_input`, `work_dir_unset`, `export_copy_failed`, `export_path_symlink`, `timeout`. `media_changed` keeps its hint to cancel and start a new run: the new run rebuilds the stub and transcript from the file as it is now, which a reopen does not.

**After a failure the cut caused.** The agent sees the failed step in `recipe_status` (its error with `upstream: true`) and the next action `recipe_reopen cut`; the guide's section 8 prints the reopen command with the worker's own `aar`, quoted like its other commands. The cut then has a new attempt in the same round, whose status entry carries `reopened_for`; an unchanged plan is refused `plan_unchanged`; the cut has `max_attempts` (3) attempts in a round, reopened ones included, after which only `recipe_cancel` and a new run remain (the new run's transcript step finds the `transcript.<key>` fact and skips the transcription). A second export in one round keeps `.r<round>` and moves to `-2`, `-3`... by the never-overwrite rule.

**Deploy** (deploy/linux): `aar-hub-worker.service.in` runs `aar recipe worker --recipes aar.recipes.ccn` with `EnvironmentFile=<root>/hub.env` (`hub.env.in`: `AAR_RECIPES`, `AAR_MEDIA_ROOT`, `AAR_MODEL_DIR`, `AAR_YUNET_MODEL`, `AAR_WORK_DIR`, `AAR_EXPORT_DIR`), the same user as the other units, `Restart=on-failure`, writes only to the data, work and export folders; the MCP and console units read the same env file, so `recipe_create` accepts the recipe and validates its paths.

#### Shrunk working copies (S19b)

A camera proxy is about 5.5 GB per 90 minutes (H.264 at about 5.9 Mbit/s and 24-bit PCM stereo at 2.3 Mbit/s), and the hub's media disk holds about one. The hub only transcribes, syncs, finds faces and renders a review copy from its proxies; the FCPXML links the edit PC's own full-size copy through the media map. So `aar media shrink` (`aar.media.shrink`, stdlib only, also `python -m aar.media.shrink` from a copy of `src` on the PC) makes a small copy that describes **the same frames**: the same frame size, pixel aspect, frame count, constant rate and start timecode, and the audio bit for bit.

**Settings (version 2, all in `aar.media.shrink`'s settings block):**

- **Video: libx264, `-preset medium -crf 30`, yuv420p, `-g` = 2 s of frames (59 at 29.97), `-fps_mode passthrough -enc_time_base demux`, input `-noautorotate`.** Measured on 60 s of the pilot's proxy: CRF 26/28/30 at `medium` gave 1149/848/630 kbit/s at about 7x real time on the hub; `slow` saved 1 % for 20 % more time; `faster`/`veryfast` were smaller only by spending fewer bits on detail. The audio cannot shrink below about 1.26 Mbit/s (below), so a quarter of the source (2.05 Mbit/s) leaves the video about 0.75 Mbit/s: CRF 30. On 5 minutes of the pilot (from 20:00) the copy was 23.8 % of the source (video 689 kbit/s), projecting the 90-minute file to 1.31 GB from 5.52 GB, and a still at the same frame keeps faces and action readable for choosing a cut. `passthrough` gives one output frame per input frame (no duplicated or dropped frames); the keyframe at most every 2 s lets a review render seek per segment. `-enc_time_base demux` keeps the source's timestamps: without it the encoder rounds them to whole frames, so a video that does not start on the frame grid (0.25 s after the sound) came out starting at 0.233 s, 17 ms off the sound. `-noautorotate` keeps the stored picture and its display matrix, so a rotated source keeps its size and rotation (version 1 rotated the pixels and dropped the matrix, then refused the copy).
- **Audio: lossless, every stream, the source's channels, rate and bit depth: FLAC in MP4, ALAC in QuickTime.** The shows' far-field audio (mean about -40 dBFS) is already hard to transcribe, so no lossy codec. On the same 5 minutes FLAC took 1258 kbit/s (level 8: 1257, not worth twice the time), ALAC 1278; PCM itself is 2304. ffmpeg's QuickTime muxer refuses FLAC, so `.mov` takes ALAC. Both keep integer samples of at most 24 bits exactly; a float or 32-bit source is refused (`audio_unsupported`). The channel layout: FLAC in MP4 stores no channel mask, so on ffmpeg 6.1 it keeps mono, stereo, 3.0, quad, 5.0(side), 5.1(side) and 7.1 but turns 5.1 into 5.1(side); ALAC in QuickTime keeps mono, stereo, 3.0, 4.0, 5.0 and 5.1 (`KEPT_LAYOUTS`). A source whose named layout the destination's codec does not keep is refused before encoding (`audio_unsupported`, the hint names the container that keeps it); an unset layout (the pilot's proxy says `unknown`) takes the codec's default for its channel count.
- **Container:** the source's (`.mp4`, `.m4v`, `.mov`), its metadata copied, a tmcd track written from the source's start timecode (none when it has none), and the mark `aar_shrink=aar-shrink v2 ...` (`-movflags +use_metadata_tags`) so a second pass knows the file. Changing any setting bumps `SETTINGS_VERSION`.

**Verification, before a copy gets its name** (and of a destination that already exists, before it is skipped as done). ffprobe and one packet scan of each file (every packet's timestamp, duration and keyframe flag) compare: frame size, pixel aspect, rotation, frame count, frame rate (and every frame step of the copy is one frame), the start of the video and of every audio stream (within 1 ms, `START_TOLERANCE`: far under a frame and under what anyone hears as sound off picture, above timestamp rounding at 1/30000 or 1/48000), the ffprobe timecode tag and the tmcd track as `aar.media.quicktime` reads it, the audio streams' channels, named channel layouts, sample rates and sample counts (the packets' durations summed; the stream's own duration when a packet has none, as the MP4 muxer leaves the last FLAC packet of a stream that starts late); the copy must be H.264 yuv420p with no keyframe gap over 2 s and carry the mark. Then the picture, then the sound: every audio stream of both files is decoded and its SHA-256 compared. A difference removes the temporary file and fails `verify_failed`, naming each.

**The picture check** (`picture_differences`). Five windows of three consecutive frames, the first and the last frames included and the rest evenly between, are decoded from both files (a seek by the frame's own timestamp, `-seek_timestamp 1`, half a frame early, which lands on the frame exactly) at 128x72 in 8-bit gray, and compared by mean absolute difference. A frame more than 6 gray levels from the source's same frame is another picture (`PICTURE_MAX_DIFF`). **The shift test** (`shift_difference`, fix round 2) is decided over all the windows together, against the source's own motion. For a shift of one frame later (and again for one earlier), each copy frame's *gain* is how much closer it is to the source's next frame than to its own, and the *motion* how far the source's frame is from that next frame; the copy is shifted when its gains summed over the windows exceed 0.05 (`PICTURE_SHIFT_MARGIN`) of the motion summed. The share always lies between -1 and 1 (no frame is closer to a neighbour than the neighbour is to its own frame), a true copy sits near -1 wherever the picture moves and a shifted one near +1. A window whose source frames differ by less than 0.05 levels a frame (`PICTURE_MIN_MOTION`) is too still to tell and counts neither way. Round 1's rule (any window 0.03 levels closer to a neighbour) refused true copies of noisy, slowly changing pictures: on a still picture fading under sensor noise single frames of a true copy are closer to a neighbour about a third of the time, because noise and the encoder's own error (x264 trails a fade a little within a GOP) are as large as the change from frame to frame. So the earlier statement that a true copy is always closer to its own frames holds only where the picture moves more than its noise; it held on the pilot's footage, not in general. Noise and encoder error point either way from window to window and largely cancel in the sums, while a shift points the same way in every window that moves. Measured with the validation's matrix (640x360, 5 s, 30 kinds of content; `aar-evidence` picture matrix, not in the repo): every true copy is accepted, at a share of at most 0.006 (static grain) and -0.05 to -0.99 wherever anything moves (the noisy still fades -0.05 to -0.13, which round 1 refused); every copy shifted by one frame either way is caught wherever the picture moves, at 0.10 (a noisy exposure ramp) to 0.99; a negated picture is caught as another picture. On two 10 s excerpts of the pilot's proxy (20:01 and 49:59) a true copy scored -0.46 and -0.48 and the copies shifted either way +0.46 to +0.56. **What it cannot see:** a shift where nothing moves (a still picture, black, static grain whose frames differ only by noise): such a copy shows the same picture at every frame either way, so it changes nothing that the copy is used for (transcription follows the sound, which is compared sample for sample; a still frame chosen for a cut is the same frame). It is also blind to a shift confined to frames between its windows, which the frame count, the packet timing and the stream starts already compare in full. And a copy encoded without weighted prediction (x264 `ultrafast`) trails a fade by about a frame, so a shifted copy of a fade made that way can look aligned; the shrink's own encode (`medium`) has it. **Cost:** ten ffmpeg runs, each a seek and the decode of at most one keyframe interval (the camera's proxy has one every 2 s, the copy too). On the pilot's full 90-minute proxy the source's five windows took 0.92 s in all (0.16 to 0.21 s each), against 31 s for the packet scan alone; the copy's side is the same order, so the check adds about 2 s per file whatever its length. The shift test decodes nothing more: it is arithmetic on the frames already decoded, about 30 ms for the five windows (pure Python); the whole check on a 10 s 1080p excerpt of the pilot took 1.9 to 2.0 s, ten ffmpeg runs as before.

**Refused before encoding** (no time spent on a copy that would fail): a variable frame rate (`vfr`, with the stub builder's wording, "has a variable frame rate: ...", "conform the file to a constant frame rate first"); an odd width or height (`odd_size`: 4:2:0 H.264 needs even ones); a video or audio stream starting before the file does (`negative_start`: packets hidden by an edit list, a cut made with `-c copy` inside a GOP, which the copy cannot keep hidden); float or 32-bit audio, or a channel layout the destination's codec does not keep (`audio_unsupported`); `--replace` on a symbolic link (`symlink`: it would replace the link and leave the full-size file); a folder the user cannot write (`not_writable`: the temporary name is created empty and exclusively before ffmpeg starts). On the pilot's 5 minutes the transcripts of the source and the copy (deployed hub CLI, `--normalize`) had 378 and 375 words; a second run on the unchanged source gave 377, so the transcriber's own run-to-run variation covers the difference (the decoded audio is identical).

**Safety.** ffmpeg runs through `aar.media.tools.run_tool` (argument list, no shell, a timeout of 300 s + 4x the duration that kills the process group), writing `.<name>.aar-shrink-<random>.part` in the destination folder; a timeout, error, failed verification or stop removes it. Before encoding the destination must have half the source's size free (`low_space`). The verified copy is flushed (`os.fsync`) before it is renamed, and the folder after, where the platform lets a folder be opened (POSIX; on Windows a folder cannot be opened as a file and NTFS journals the rename). `--out` never overwrites (a hard link on POSIX, `os.rename` on Windows, both of which refuse an existing name); an existing destination that verifies is skipped, one that does not is refused (`destination_exists`). **The no-hard-link fallback:** a POSIX file system without hard links (FAT32 and exFAT, an SMB/CIFS mount without Unix extensions, some FUSE file systems) makes `os.link` fail; then the name is checked free immediately before an `os.rename`, which on POSIX would replace a file that appeared in between. What protects that window: it is microseconds long, right after a check, the temporary name is random and nothing else writes the shrink's destination names; the edit PC uses Windows' `os.rename`, which refuses an existing name atomically; the hub's media disk is ext4, which has hard links. `--replace` renames the verified copy over the source with `os.replace` in the same folder (atomic on one volume), refuses a file already marked (`already_shrunk`), and refuses if the source changed while it ran (`source_changed`). Both modes check the source before the rename: size, modification time, change time (on Windows the creation time), device and file number, so an append, a rewrite that puts the modification time back (POSIX) or a swap for another file is caught. A folder batch takes at most 64 files (`.mp4`, `.m4v`, `.mov` directly in it, not hidden, sorted by name), carries on past a failed file and exits 2 at the end. Every error is typed with a fix hint; stdout has one JSON line per file, `--report` the whole run.

**Stopping.** While the command runs, Ctrl-C (SIGINT), `kill` (SIGTERM), a closed terminal (SIGHUP) and Ctrl-Break (SIGBREAK, Windows) raise in the main thread (`stop_signals`), wherever the platform has the signal (chosen by `getattr(signal, ...)`, not by platform name); the `finally` blocks on the way out kill ffmpeg's process group and remove the temporary file, exactly as on a timeout, in both modes and in every phase (the encode, the picture check, the audio hash). The run then prints the file's JSON line with the typed error `interrupted` (the signal named), writes `--report` (with `"interrupted"`), stops the batch and exits 2. Only the first signal raises, so a second Ctrl-C cannot cut the cleanup short; a signal the process inherited as ignored (`nohup`) stays ignored. From the moment the files are done, a signal is only noted: one that lands while the lines or the report are written still ends the run with `interrupted` (its line printed after the report, the report rewritten with it) and exit 2, never a traceback. The command line (`python -m aar.media.shrink` and `aar media shrink`, `run_command`/`main(ending=True)`) keeps ignoring later stop signals after a stop instead of restoring the previous handlers, so one that arrives after the cleanup cannot end the process by the signal (-15) instead of exit 2; called in-process (`main()`, `run_args`) the previous handlers are always restored. A signal that lands just after the copy got its name (after the rename or the link, while the folder is flushed) reports `interrupted` with `placed`: the copy is complete and in place, and a rerun skips it. What cannot be handled: SIGKILL (or a crash) ends Python at once, so ffmpeg, in its own session, runs to the end and leaves a complete hidden `.part` file; it is safe to delete. On Windows, as far as the documentation tells (`SetConsoleCtrlHandler`): closing the console window sends CTRL_CLOSE_EVENT to every process attached to it; the C runtime hands it to Python as SIGBREAK, but Windows ends the process a few seconds later (or as soon as the handler returns), so the cleanup cannot be counted on, while ffmpeg (in the same console) treats the event as a stop and closes its output, so the encode does not finish but a short `.part` file is left behind. Ending the process from Task Manager is like SIGKILL. Ctrl-C and Ctrl-Break reach both processes and are cleaned up as above.

**Not verified here.** The edit PC (Windows, Python 3.13, ffmpeg 8.x) is untested: only ffmpeg 6.1 with Python 3.12 on Linux ran it. Windows-specific paths: `os.rename`'s no-overwrite rule, `proc.kill()` without a process group, `file:C:\...` input URLs, the console events above, `os.fsync` on a file opened read-write. ffmpeg 8.x is expected to accept `-noautorotate`, `-enc_time_base demux`, `-seek_timestamp`, `-fps_mode` and `streamhash`, and its FLAC/ALAC layouts may differ from the table above; the verification compares rotation, starts and layouts, so a difference there fails the copy rather than passing it. The module needs only the standard library: `python -S -m aar.media.shrink` with `PYTHONPATH=src` (`-S` leaves site-packages out; `-I` cannot be used, it ignores `PYTHONPATH`) is what the test runs.

#### Timeline import (S20)

The owner edits the imported timeline in Resolve (trims, moves, deletes, adds); `aar.plan.timeline_import` brings those edits back so the agent continues from the owner's version. The flow: plan -> FCPXML (`aar plan export`) -> Resolve -> edits -> File > Export > Timeline as `.drt` into the share (docs/MEDIA-STORE.md) -> import -> an edited plan and a diff. A `.drt` and not a Resolve-written FCPXML, because `aar.drp` already reads `.drt` in full and real exports exist; Resolve-written FCPXML is still unsampled. Pure and cold: the only file read is the `.drt` (or, since S25a, a project's `Project.db` in a Resolve disk library, which needs no export; see "Shared project library (S25)"), through `aar.drp.read_drp` with its own size limits, and at most 20,000 items per timeline.

**The rule: a wrong plan or a wrong diff is never returned without saying so.** Where the code cannot know (which of two segments an item came from, whether a same-named file is the same file), it reports; it does not guess quietly.

```console
aar plan import-timeline TIMELINE.drt --plan PLAN.json [--media-map MAP.json] --out PLAN2.json --report DIFF.json [--timeline NAME] [--profile P] [--json]
```

Exit 0: both files written, the edited plan lints clean and the export's layout step accepts it; 1: both written, but the edited plan has lint errors or the export's layout refuses it (the owner's edit stands; the diff says `lint_errors` / `export_errors` and holds the lint report and the export refusal), or the timeline holds an edit the plan does not carry: any entry under `not_carried`, on any track (a sound added or removed on its own, a retime, a title or a transition added in Resolve). The next export would not have that edit, and an automated revision loop that read exit 0 as clean would drop it without telling anyone, so it is never a clean import. An item on the primary track is also counted in the diff's `primary_not_carried` (the plan keeps its own version or loses the item, and the segments around it need checking by eye); 2: refused or unreadable input, nothing written. Nothing else exits 1 (a plan the model refuses is the typed refusal `invalid_edited_plan`, exit 2). The plan and the diff are written as one pair with the export's writer (`write_pair`, never over an existing file; it leaves its `.aar-lock` files beside them). Stdout is a bounded summary an agent can act on (opening, when `primary_not_carried` is not 0, with one plain line saying how many items on the primary track the plan could not hold and that the segments around them should be checked by eye, then, when anything is not carried, a `NOT CARRIED` line with the count and the reason codes; counts, at most 12 changed segments with at most 3 pieces each, a `TRACK ASSUMPTION FAILED` line when an element was found on another track, kept segments at another length, the uncertain matches and titles, the file-name matches, the reason codes grouped with per-track counts); the diff file has every entry.

**One implementation.** The expected timeline is S18's `build_layout` of the original plan (lanes, record ranges, source ranges), not a re-derivation; media go through the export's own `media_ref` with the same media map; ranges and joins come from the plan model's `record_ranges` and `joins`; the edited plan goes through the plan model, `lint`, and `build_layout` again (the export check, with the options the original was laid out with).

**Reader issues.** `aar.drp` reports what it could not read as issues. A `.drt` with any issue that can hide or change a timeline item, its position, its source range or its media path is refused as `damaged_timeline`, listing the issues: every `scan-*` code (a truncated or unparsable member), `missing-container`, `missing-member`, `unreadable-member`, `empty-member`, `blob-decode`, `blob-partial`, the budget codes, `zstd-unavailable`, `bad-integer`, `bad-frame-count`, `bad-hex`, `duplicate-id`, `missing-id`, `unexpected-root`, `sequence-link-conflict`, `track-type-mismatch`, `unknown-track`, `implausible-extents`, `unresolved-media`, `path-unknown`, `no-main-stream`, `path-from-later-stream`, `timeline-path-conflict`, and any code not in the list below (a new reader code refuses until it is classified). Passed through as `reader_warnings` in the diff (they cannot change the cut list): `uninterpreted`, `linked-files`, `stale-media-file-path` (the pool path is used), `orphan-markers`, `marker-decode`, `issues-truncated`, `codec-unknown`, `no-version-header`, `version-mismatch`, `orphan-timeline`, `orphan-bin`, `bin-cycle`, `unknown-media` (an item that uses such media raises `unresolved-media`, which refuses), `drb-best-effort`, `no-timelines` (no timeline at all is `no_timeline`). The list is `READER_WARNING_CODES`. The issues are the whole file's: a refusing issue anywhere in the `.drt` refuses the import, even when `--timeline` picks a timeline the issue does not touch (the reader does not always say which timeline an issue belongs to, so this stays conservative). The five real Resolve 21.1 exports carry only `uninterpreted`, `linked-files` and `stale-media-file-path`. A timeline whose media items match no plan source at all (media relinked to other paths in Resolve, or the wrong media map) is refused as `nothing_matched` rather than imported as "every segment removed".

**Matching media.** An item matches a source when its media path is the edit-PC path the export named for that source (for a hub source, the map's hub root -> edit-PC root image; for a drive, UNC or `file:` URL source, that path), `/` read as `\` and case folded. Matching by file name alone is allowed only for a source whose edit-PC path is unknown (the export rules cannot place it: a hub path with no map entry, a pool name), and only when that name names one file among such sources; every such match is listed per item (`matched_by_file_name`, and `match: "file-name"` on the piece or added entry) and on stdout. An item with a known source's file name but another path is **foreign**, `reason: same_name_different_file` (camera cards reuse names such as C0001.MP4); a name two unplaced sources share is `ambiguous_file_name`; anything else is `unknown_file`. Foreign items are listed, never guessed. Several sources naming one file: the one an original segment uses with the largest source overlap, else the first in plan order.

**Segments.** On each content track (a video track the layout gives a planned segment: V1 for the spine, V(N+1) for lane N) the picture items, in record order, become the plan's segments on that plan track, frame-exact (`source`, `src_in`, `src_out`, and `record_in` only where a segment does not follow its predecessor on its track): positions come from the timeline. Items are assigned to the track's original segments as a whole (`assign_items`): first an exact source range that one original has (at its planned position, then anywhere). An exact range that several originals share (a teaser or hook copied from a later moment and its main take) is decided by context first (the item's assigned neighbours in the timeline are the candidate's neighbours in the plan), then the nearer planned position, then plan order, and the other candidates that differ in any field are always listed (`uncertain_matches`, `why: "same_source_range"`; copies identical in every field but position need no entry). Then each other item goes to the original of its source it overlaps most (an original already matched exactly is not split by a second item: that item is added); among originals it overlaps equally, one no item holds yet comes first, then the nearer original record position, then plan order (tied items are given out in record order). An item that overlaps nothing it can take is **added**. Overlap cannot always tell: the originals really in contention (overlapped equally, or covering at least half of the item, or at least half of them inside it; a sliver of overlap is not a contender) are listed (`also_overlaps` on the piece, and `uncertain_matches` with the index it was given and `why: "overlap"`). A matched segment inherits the original's other fields (`track`, `transform`, `gain_db`, `label`, `notes`, `reframe`). Reframe keys count frames from the segment's start, so when the source range changes they are windowed to the new range: shifted by the head trim (later, for a head extended into the handle), and a side whose keys were cut away gets one key at the new boundary holding the linearly interpolated framing. Two plan neighbours on one track, contiguous in source and record, that the owner joined into one item (one has no piece, a piece of the other runs across their common source frame) are both `joined`, and the result keeps the fields of the one that holds the piece (`joined: {segments, fields_from}`). A segment off V1 is placed in the list after the V1 segment its original followed (an added one, after the last V1 segment that starts at or before it). The outro is the last item of the outro's source on the outro's track; its source range is carried (`src_out` stays unset when it still plays to the end). A timeline nobody edited gives `unchanged: true`, empty lists and the original plan back.

**Kept, not carried.** A picture item the plan cannot hold (`retimed`, `sub_frame`, `still_image`) of a known source stands in for an original of that source: the plan keeps that original's own version (its source range and fields) in the item's place in the order (`status: "kept"`, `kept_because` = the code; the `not_carried` entry stays). A stand-in with evidence claims its original after the exact matches and before the overlap matching: its in point inside the original's source range, or, with no in point, the item at the original's own planned position (the nearer planned position, then plan order, among several). A carried item that only overlaps a claimed original goes to another original or is `added`. Wherever a stand-in and a carried item are both candidates for one original (the claimed original overlaps a carried item, or an exact carried item took the original the stand-in's evidence points to), whichever won is listed (`uncertain_matches`, `contested_by`: the other items, each with its new `index` or null, track, timeline range and `carried`; `why: "contested"` when nothing else is uncertain about it). Any other stand-in takes an original no item took, chosen by evidence: the item's in point inside its source range (`aar.drp` keeps a retimed item's `<In>`; a still's in point is not a plan frame, so stills have none), then context (the carried items around it are the original's plan neighbours), then the nearer planned position, then plan order. The other candidates with as much evidence are listed (`uncertain_matches`, `why: "not_carried_item"`), and a choice with no evidence (a readable in point outside the original's range; or none, no context and not at the original's own position) is kept, but always listed. The plan can still lose content: an item it cannot hold whose original is gone or taken stands for nothing, and the item's own edit (its speed, its frames) is never carried, so a timeline with a not-carried item on the primary track exits 1. A retimed item's length can differ from the original's: the next segment keeps its timeline position, so the plan has a gap or an overlap there; every kept segment whose timeline extent differs from the plan's version is listed (`kept_other_length`: `location`, `index`, `track`, `record_in`, `timeline_frames`, `plan_frames`, `detail`) and has a stdout line, and an overlap also shows up in lint. `zero_length`, `outside_timeline`, `negative_source_in` and `unreadable_item` items stand for nothing: their original is `removed`.

**Elements on another track** (the `tracks` assumption failing). An original with no item of its exact source range on its predicted track is the item of that exact source and range on another video track (never one on the primary track, which is the owner's spine, unless the primary track holds no picture at all; never one that is an exact match on its own track); a title is the title item at its own range, or at the range its content moved to, on another track that misses none of its own expected titles (own tracks are searched first, for every title); the outro is the item of exactly its range on another track. The plan keeps the element, and the diff says so once per element under `track_mismatch` (location, expected and found track, range), not as a removal and an addition; any entry there sets `unchanged: false`.

**Timing.** Whatever exists as an item in the timeline takes its position from the timeline: segments on every content track, and titles. A title item's text cannot be read: in a real Resolve 21.1 export a title item's name is its template (`Fusion Title`) and the text sits in the Fusion comp, which `aar.drp` leaves uninterpreted (`uninterpreted`). So a plan title is a title item only on evidence of position: an item at its own record range, then an item at the range its content moved to (`by: "content"`), own track first (above for other tracks). Without that evidence, per track, the remaining titles are paired with the remaining title items in record order when as many remain: the pairing is kept, so a title the owner merely moved keeps its text, but it is listed under `uncertain_titles` (location, track, old and new range) and repositioned `by: "order"`, never as a plain move, and stdout prints `uncertain titles (N), paired by order only`. A title with no item was removed in Resolve and is dropped, `title_removed`. What the plan positions in record frames but is never an item in the timeline (captions, which are burned in; markers, which Resolve does not import from FCPXML) is re-anchored to the content it sat over: its first and last frame are each mapped to the same source frame of the same V1 segment (or the outro) in the edited timeline, and it moves when both survive the same distance apart; otherwise it is dropped (`caption_content_gone`, `marker_content_gone`). Every move is listed under `repositioned` (`by: "timeline"`, `"content"` or `"order"`, old and new range) and every drop under `dropped`; nothing keeps an old record frame without an entry.

**The diff** (`format: aar.timeline-import/2`, keys and lists in a fixed order; positions in plan record frames from the timeline's start): `primary_not_carried`; `matched_by_file_name`; per original segment `status` = `unchanged`, `trimmed` (with `head_frames` and `tail_frames`, the frames removed at each end, negative when extended), `moved` (old and new position), `removed`, `split` (every piece), `joined`, or `kept` (with `kept_because`), each piece with its `match` and `also_overlaps`; `uncertain_matches` (`index`, `assigned_to`, `why`: `same_source_range`, `overlap`, `not_carried_item` or `contested`, `also_overlaps`, `contested_by`); `uncertain_titles`; `track_mismatch`; `kept_other_length`; `added` (with its plan track); `outro` (`unchanged`, `moved`, `trimmed`, `missing`, `kept`); `repositioned`; `foreign` (with `reason`); `not_carried`; `dropped`; `limits`; `assumptions`; `lint`; `lint_errors`; `export_check` (`ok`, or the export's refusal code, message and hint); `export_errors`; `reader_warnings` (count and up to 50 listed).

**Not carried** (the timeline holds it, a plan cannot; the plan keeps its own version where it has one, `kept` above): `retimed` (speed other than 100 %, or a retimed timemap), `still_image` (a still: the media pool says one frame, or a still-image file name; see the source-frames assumption), `sub_frame` (a sub-frame start, length or in point), `zero_length`, `outside_timeline` (starts before the timeline's start), `negative_source_in`, `unreadable_item`, `audio_only_edit` (a sound that is not a picture item's own sound: same file, in sync, over the picture's range, widened only by an audio-only crossfade the plan carries at that cut; or a picture whose own sound is gone), `other_picture_track` (known media on a video track the plan has no segments on), `title_added` (a title, generator or solid the plan has no title for), `transition_added` (a transition item with no matching transition in the edited plan, which includes a changed length), `transition_missing` (a plan dissolve with no item at its cut; kept, since Resolve's import of FCPXML transitions is unconfirmed), `outro_missing`, `outro_position` (a plan always starts the outro where the content ends), `outro_changed` (cut shorter than its sting), `sting_missing` (no title item where the edited plan puts the sting; the plan keeps it). **Dropped** (a plan entry no longer valid): `transition_join_gone` (its two segments are no longer abutting neighbours; a surviving join is re-indexed), `title_removed`, `title_past_end`, `caption_content_gone`, `caption_past_end`, `marker_content_gone`, `marker_past_end`. Head, audio tracks, fades, template and caption style are carried as they are.

**Limits** (in every diff): the reader cannot see an item's enabled state, so a disabled clip imports as if it plays; transition items on audio tracks are not compared; a title item's text is not read, so titles are paired by position (and by order, listed as uncertain); markers, grades, Fusion and Fairlight work in the `.drt` are not read into the plan. The command's text summary says so on every import, in a `NOT READ` line that names the limits, also when it reports no changes: the edited plan is a partial reconstruction of the timeline, to be checked with whoever edited it before the next export.

**Refusals** are typed `TimelineImportError`s with a fix hint, exit 2: `unreadable_timeline` (not a zip, unreadable, a refused `Project.db`, or a timeline without a frame rate or start), `library_busy` (a `Project.db` still being saved after `--wait` seconds; try again), `damaged_timeline` (above), `no_timeline`, `several_timelines` (pick one with `--timeline`), `timeline_not_found`, `timeline_too_large`, `fps_mismatch` (the timeline's rate differs from the plan's by more than 0.001 fps), `media_fps_mismatch` (a matched picture item's media rate differs from the timeline's), `source_range_outside` (a matched item reads past its source's duration), `output_exists` (either output exists, or both are one path), `output_folder_missing` (names the folder), `invalid_edited_plan` (the plan model refuses the result; a guard, no known timeline reaches it), `nothing_matched` (the timeline has media items and none matches a plan source). A plan the export cannot lay out is refused with the export's own code; the writer's `output_locked` likewise.

#### Shared project library (S25)

Decision D10 (owner, 2026-11-24): agent cuts live as projects in a Resolve disk project library kept in a folder on the hub's share. The owner opens one from Resolve's Project Manager, edits it and saves; the hub reads the saved project straight from its `Project.db`, with no export. S25a reads (this section). S25d hands a cut over as a library project from the `ccn-longform` recipe and picks the owner's saves up on the hub ("Library hand-off and pickup (S25d)" below; this is the S25b pickup). S25e adds sound crossfades to the written projects and makes the newest save win at pickup ("Transitions and the latest save (S25e)" below). S25c writes an EditPlan as a library project, staged behind open-in-Resolve checks: S25c1 authors the media-pool rows of the files a cut uses ("Media-pool rows (S25c1)" below), S25c2 the timeline's items, the project file, its place in the library and `aar plan export --format library` ("Timeline items (S25c2)" and "Library projects (S25c2)" below). Until a person has opened its staging projects in Resolve, FCPXML (S18) stays the way a cut gets into Resolve.

**What a disk library is** (checked on real files, 2026-11-24). A folder: each project is `<library>/Resolve Projects/Users/<user>/Projects/<project folder>/Project.db` (the user is `guest` on the samples), beside `Resolve Projects/Users/<user>/User.db`, `ProjectMetadataCache/Metadata.db` and `Settings/*.xml`. `Project.db` is an SQLite 3 file in rollback-journal mode (`journal_mode=delete`, not WAL): 146 tables, about 36 of them non-empty in a real project. Its tables are the element types of a `.drp`'s XML (`SM_Project`, `Sm2Timeline`, `Sm2Sequence`, `Sm2SequenceContainer`, `Sm2TiTrack`, `Sm2MpFolder`, `Sm2MpMedia`, `BtVideoInfo`, `BtAudioInfo`, ...); every timeline item type shares `Sm2TiItem` and every media pool clip type `Sm2MpMedia`, with the element name (`Sm2TiVideoClip`, `Sm2MpMulticamClip`, ...) in `DbType`, and every lockable blob (markers) is a `BtLockableBlob` row the same way. The primary key `<Table>_id` (a uuid as text) is the XML's `DbId`, and the columns are the XML's child element names. Blob columns hold the raw bytes the XML carries as hex text, in the encodings `aar.drp.blobs` decodes (zstd-marked ones included). `Start`, `Duration` and `In` are text and can be NULL; integers are stored as integers and flags as 0/1. An object the XML nests as a single child is a column holding the child's id plus an owner column `<Parent>_id` on the child (`Sm2MpMedia.Video` -> `BtVideoInfo`, `SM_Project.CommonConfig` -> `SM_Config`, `Sm2MpMedia.TimelineSharedHandle` -> `Sm2Timeline`, `Sm2Timeline.Sequence` and `Sm2MpMedia.Sequence` -> `Sm2Sequence`). A vector is a join table named after its two tables in sorted order (`Sm2MpFolder_Sm2MpMedia`, `BtAudioInfo_Sm2MpMedia`, `Sm2SequenceContainer_Sm2TiTrack`, `Sm2TiItem_Sm2TiTrack`, `SM_Project_Sm2Timeline`) with `DbOwner` (the XML parent), `DbAssociate` (the child, or the id a plain-id vector lists), `DbPropertyName` (the vector's element name: `MediaVec`, `EmbeddedAudioVec`, `VideoTrackVec`, `AudioTrackVec`, `Items`, `TimelineHandleVec`) and `DbIndex` (its position); the child also carries the owner column. These were worked out from the five pairs, not guessed. A library stores no `DbAppVer`; `SM_Project.ProjectVersion` is the project version (15 on the Resolve 20 samples, 17 on the Resolve 21.1 ones). The project id occurs only in plain text columns, never inside blobs. An agent-made change of two `Sm2TiItem.Duration` values plus the sequence's `MediaExtents` opened correctly in Resolve 21.1, so these columns are what Resolve itself reads.

**One reader.** `aar.drp.read_drp` reads a `Project.db` (any `.db` file, and SQLite content under any suffix but `.drp`, `.drt` and `.drb`; a `.drb` that is SQLite stays best effort, as before) through `aar.drp.library`: the rows the reader needs are laid out in memory as the members of a `.drp` (`project.xml`, `MediaPool/<bin path>/MpFolder.xml`, `SeqContainer/<container id>.xml`), blobs hex-encoded and vectors rebuilt from the join tables in `DbIndex` order, and the S1 reader builds the model from them. Blob decoding, classification, limits and issue codes have one implementation. The view carries only the columns the reader interprets (`aar.drp.library.COLUMNS`), so it is never a valid `.drp`, and it is never written anywhere. A NULL column is an empty element (a NULL `In` reads as source in point 0, as `<In/>` does), except a NULL `In` on a transition: a transition's XML has no `<In>` at all (all 69 in the private corpus), so its `source_in` stays null. Two orders the pairs cannot show follow the corpus's XML: a media clip's stream infos come `Video`, `EmbeddedAudioVec`, then `Left`, `Right`, `LeftEye`, `RightEye`; a container's track vectors come video, audio, then subtitle. Only the vectors the reader consumes are laid out (`TimelineHandleVec`, `MediaVec`, `EmbeddedAudioVec`, `VideoTrackVec`, `AudioTrackVec`, `SubtitleTrackVec`, `Items`: `aar.drp.library._READ_PROPERTIES`, the only property names on every real save); a join row under any other `DbPropertyName`, or from an owner that is never laid out, is reported (`library-unread-link`), so no row disappears silently.

**Where a value came from.** The model's `kind` is `library`, `members` and `raw_members` are empty, `versions.app_version` is null, and every provenance names a row instead of a byte span: `member` is `<table>/<row id>` for an object (`kind` `row`), `<table>/<row id>/<column>` for a value (`kind` `column`, or `blob` with the reader's `blob_path` inside the blob), and `<join table>/<owner id>/<property>/<DbIndex>` for an id listed by a join row; `start` and `end` are 0. `Bin.member` and `Timeline.member` name the folder and sequence-container rows. With no text to splice, `aar.drp.modify` refuses a library project (`library-project`, before anything is written); aar never writes to a library.

**Reading while Resolve may be saving.** The live file is never opened for writing and nothing is left beside it.

1. *Settle and snapshot.* The file (a regular file; a symlink, folder, FIFO, socket or device is refused as `unreadable`, saying which it is, before anything is opened) is copied, read-only, to a private file in the system temporary folder (never the project's own folder), and only when no `Project.db-journal` or `Project.db-wal` is beside it and it has settled: its modification time is at least 2 s old, or its device, inode, size and modification time stayed the same while watched for 2 s (a share whose clock runs ahead of the hub's). After the copy its identity, change time included, must be unchanged and no journal may have appeared. Otherwise it is tried again every 0.25 s until a deadline (30 s by default; `--wait` on `aar plan import-timeline` and `aar drp library`), then refused `busy`. The same function (`aar.media.settle.copy_settled`) takes the desktop `.drt` returns' snapshots.
2. *Check.* SQLite's own `PRAGMA integrity_check` on the snapshot; every table and column read must exist as an ordinary table (a view or virtual table of that name is refused); exactly one `SM_Project` row; `ProjectVersion` 15 or 17.
3. *Read.* An immutable, read-only connection (`mode=ro&immutable=1`: SQLite takes no locks and creates no journal, WAL or shm file), `trusted_schema` off, `query_only` on. Text that is not UTF-8 is read as bytes and reported by the scanner (`scan-invalid-utf8`), never a decode crash.
4. The snapshot is deleted before the reader runs, on every path, errors included.

**Budgets.** Memory is bounded while rows are fetched and while they are laid out, not afterwards. The file at most 256 MiB (checked by `copy_settled` on the opened file and on every block copied, so a file that grows while copied is refused too); at most 220,000 rows across the tables read (counted by SQLite first, then charged again as each row is fetched, one row at a time); at most 80 MiB of values fetched in total (each value's bytes plus 16 per value, charged as the row arrives, so a column generated from nothing is bounded too); one value at most 16 MiB (and never more than the reader's per-member limit), set as SQLite's own length limit, so a larger value is refused before it is loaded; the layout at most 160 MiB (twice the load budget unless set: a blob's hex is twice its bytes), every value charged at its laid-out size before it is laid out and once per place it is laid out, so one row named by many others is refused before its copies are made, and each folder also charged the length of the folder path the reader will build for it (a folder's path holds its parents' names, so a chain of folders with long names makes paths no single row shows; a cycle is charged its whole length for every folder in or under it); at most 120 s for the read once the snapshot is taken (the integrity check and queries through SQLite's progress handler, the layout by looking at the clock every 1,024 rows or writes, and the model once the reader has built it), with a caller's own deadline (`LibraryOptions.stop_at`, how a listing hands each read what is left of its deadline) honoured the same way; then the reader's own element and decompression budgets. A folder's member name holds at most 1,024 characters of path (it only orders the members), and every name is made in one step, so the layout is linear in the rows whatever the names; a second folder laid out under a name already taken gets `~2` on its folder part (`MediaPool/A/B~2/MpFolder.xml`), so the reader still reads it as a folder (before round 2 it became `MpFolder~2.xml`, which the reader does not read: two folders with one name and parent, or with names alike in their first 200 characters, lost the second one and its media without a word). All are parameters (`LibraryOptions`, `read_drp`), and every command that reads a library project (`aar drp inspect`, `describe`, `diff` and `library`, and `aar plan import-timeline`) raises them with one shared set of options (`aar.drp.library_args`): `--max-rows`, `--max-load-bytes`, `--max-layout-bytes` (at most the reader's 600 MiB), `--max-value-bytes`, `--max-db-bytes` and `--max-read-seconds`; each refusal's hint names the option for the limit it hit. The largest real save measured (a show project: a 29 MB file, 9,878 timeline items in 39 timelines) has 21,637 rows in the tables read, a load charge of 7.27 MB (4.55 MB of values), lays out to 7.09 MB, has no value over 29 KB, and reads in 1.3 s with a 0.13 GB peak; each default reads it at least ten times over (rows 10.2 times, load 11.5 times, layout 23.7 times). Peak memory of one read, measured with `/usr/bin/time -v` in a fresh process that only reads (fixtures built in another), S25a fix round 2: **the worst file the defaults accept peaks at 1.31 GB** (219,900 folders with 204-byte names under 220 parents: 13.6 s); the others measured: 109,900 items on one track with 455-byte names 1.10 GB (10.6 s), the same with 8-byte names 1.02 GB, 219,900 sequence containers with 190-byte ids 0.74 GB, four 16 MiB blobs 0.32 GB. The peak follows the row count more than the bytes (the reader's model of a row costs a few KB); a project read with raised budgets costs more in proportion. Refused at once: one 15 MB blob named by 100 media rows 0.22 GB (before round 2: 0.69 GB), a 1 MB blob named by 24,000 media rows 0.22 GB (0.67 GB), a chain of 49,000 folders with 200-byte names 62 MB in 0.3 s (before: read, 5.2 GB and 99 s). 49,000 sibling folders with one name are read in 2.8 s at 0.27 GB (before: 362 s, and all but one of them were dropped without a word, see below). Round 1's hostile files stay refused at once (1.9 million rows of items, with or without links: 29 MB; one 300 MB blob: 24 MB). The real show project above: 1.26 s, 0.13 GB.

**Refusals** are `aar.drp.library.LibraryError`s (a `ContainerError`) with a code and a fix hint: `busy`, `damaged` (SQLite cannot read it, also when its error message holds bytes that are not UTF-8 (S25c2 fix round 1), the integrity check fails, or it holds more than one project), `too_large` (file, rows, load, a value, the layout budget or the time budget; `timed_out` says whether the read's own time or the caller's deadline ran out), `not_a_project` (not SQLite, no project row, or a table or column the reader needs is missing, `read_rows`' `SM_Project_id` and `ProjectVersion` included), `unsupported_version`, `unreadable` (cannot be opened, not a regular file, or a snapshot folder inside the project's folder) and, for a listing, `not_a_library`. **Issues** the library layer adds (warnings, listed first in `issues`; none is in `READER_WARNING_CODES`, so each refuses an import as `damaged_timeline`): `library-dangling-link` (a join row or reference column names a row that does not exist), `library-link-conflict` (a row linked twice, an owner column that disagrees with its join row, or a `DbIndex` order that is not clear), `library-unlinked-row` (an item, track or media row that no join row places, whether or not it names an owner: it is not read; no real save has one), `library-unread-link` (join rows under a `DbPropertyName` the reader does not consume, or from an owner that is not laid out: the rows they link are not read through them), `library-bad-type` (a `DbType` that is not an element name: not read), and the reader's `duplicate-id` and `missing-id` for rows. None of them appears on the five pairs or the three 21.1 saves.

**Commands.** `aar drp inspect` and `describe` read a `Project.db` (`describe` opens with `LIBRARY project ...`; `inspect --blobs` counts only the blob columns read). `aar drp diff` takes one: when either side is a library project the opaque compare does not run (there is no XML text; a note says so and `--gate` always fails), and when exactly one side is, the file-format fields (`kind`, `sniffed_kind`, `is_zip`) and `DbAppVer` are not compared, nor the resolution of a timeline the library stores as 0x0: the library stores 0x0 for a timeline that follows the project's resolution and Resolve's export writes the project's instead (two of the three exact pairs). Each skip is a note; the exit status follows the decoded changes, so the export of a project and its `Project.db` diff to exit 0. `aar plan import-timeline Project.db --timeline NAME` imports one timeline of a project (a project holds several, so without `--timeline` the existing `several_timelines` refusal applies); a project being saved is refused `library_busy`, any other library refusal is `unreadable_timeline` with the library's code in the message. `aar drp library FOLDER [--json] [--wait S] [--deadline S] [--max-listing-bytes N]` lists every project under `Users/*/Projects`: folder, `ProjectName`, project id, project version, last-modified time (`LastModTimeInSecs`, UTC) and timeline names, each read in full; a busy or unreadable project is listed with its refusal (exit 1 then). The search looks at most 8 folders deep, at 500 projects and at 20,000 folder entries (the `Users` folder's own entries included), and follows no link. The whole listing has one deadline (`--deadline`, 120 s by default) and reads at most 2 GiB of files (`--max-listing-bytes`): each project's wait for a save (`--wait`, 5 s) is cut to what is left and its read stops at the deadline, during the layout too, and a project not reached in time or within the byte budget is listed `NOT READ` with the reason and the option to raise. Nothing is left out silently: symbolic links (never followed), folders that cannot be listed (a user without a `Projects` folder included) folders past the depth limit and a project folder inside another project's folder (`nested`: project folders are searched too) are counted per reason, with the first ten names; the search stopping at the project or entry cap or the deadline is said (`search cut short`); and such a listing is marked `INCOMPLETE` (JSON: `complete: false`, `cut_short`, `skipped`, `not_read`) and exits 3, whatever else it found. Every name, path and message from the library in the text output (folder, project, id, timelines, the library's path, a refusal's or `NOT READ` message) is in double quotes with `\` and `"` escaped, as is every string from the file `aar drp describe` prints (project, bin path, media name, codec and path, timeline, track and item names, an unresolved media id, marker colours, names and notes, and warning messages), so none can read as more fields of its line.

**Verified (S25a, 2026-11-24)** on synthetic projects written both ways (zip members and SQLite rows, laid out by an independent test-side converter): equal models, an empty diff, and the same import plan and diff from a `.drt` and its `Project.db`; every refusal and issue above; and read-only on the private samples: the three exact pairs (Resolve 20, version 15) read to models equal to their exports' apart from the 0x0 resolution above, and diff to no change; the two pairs saved 25 and 58 s after their export differ by `LastModTimeInSecs` only; three Resolve 21.1 saves (version 17) read without issue apart from the marker layout below (an agent-trimmed one shows its two 899-frame items; one show with 8 timelines and 980 items).

**Not read, or not verified.** Project settings (the project's resolution, which a timeline following it does not store; frame rate only through the existing `frame_rate_hint`), `User.db`, `Metadata.db` and `Settings/*.xml`; grades, Fusion and Fairlight work (as for a `.drp`). Resolve 21.1 timeline markers: the marker list of a version-17 save nests its frame one level deeper than the layout the reader decodes, so it reads `marker-decode` (a reader warning, not a refusal) and the markers are missing; no 21.1 `.drp` with markers has been compared yet. Generators, titles, compound clips, stereo stream infos and nested bins have no library sample: they follow the corpus's XML and the synthetic tests only (transitions have one since S25e: the 920 of the answer key read as `transition` items). Project version 16 is refused until a sample is checked. A save that Resolve split into several transactions more than 2 s apart could be snapshotted between two of them; not observed, not excluded. Reading while Resolve saves over a network share with coarse timestamps is tested with synthetic files only. A kill between creating the snapshot file and entering its cleanup, or a SIGKILL during a read, leaves a `.aar-library-*` file in the snapshot folder and nothing sweeps stale ones yet; the default snapshot folder (the system temporary folder) may be memory-backed, so a snapshot can cost its size in RAM (S25b, the hub pickup, chooses the location). `is_library_path` reads the first bytes of a path with no suffix with a plain blocking open, so `aar drp describe` on a FIFO without a suffix waits (this predates S25a; a `Project.db` FIFO is refused without opening it). PostgreSQL libraries are not read.

#### Media-pool rows (S25c1)

A cut is built from files Resolve has never imported, so the library writer must author their media-pool rows itself. `aar.drp.mediapool` does it from **measured facts** of each file (`ffprobe -show_format -show_streams`, the file's size, its modification time on the edit PC's wall clock and in UTC, and its creation time, gathered on the PC) and a **template clip** of the same kind: rows Resolve itself saved in a seed project. Constant and unexplained fields come from the template; every field that depends on the file is derived from the facts; identities are fresh; project-local fields are set as a fresh import has them. `author(facts, template, placement, allow_unverified=False)` returns the rows (table, columns, join rows) and writes nothing. A result that would not be verified (a kind with too little evidence, a file outside the envelope its kind was checked on, a template whose look is unproven or whose facts do not reproduce its own rows) is refused (`unverified`, the hint says how to opt in) unless the caller passes `allow_unverified=True`; then the result says `status="unverified"` and lists the reasons. S25c2 writes the timeline and the project file, places it in the library and adds `aar plan export --format library` (below).

**Facts** (`aar.drp.mediapool.facts.MediaFacts`, pydantic, `extra="forbid"` at the top): an absolute Windows path, the size, the modification time (`Fri Mar 13 04:05:06 2026`, the weekday must match the date), UTC modification and creation times (100 ns kept exactly) and ffprobe's format and streams. The path is checked by the edit PC's one path validator, `aar.host.winpath.check_file_path` (the rules of `validate_windows_path` without the allowed roots: a drive or UNC root, no device namespace, no empty, `.` or `..` component so no doubled separator, no reserved device name, no character Windows forbids in a name (the colon among them), no trailing dot or space, no control character or lone surrogate), and by the hub's `hidden_character` (no bidirectional, zero-width, C1 control or other character a reader cannot see: it would be written into the clip unseen); the writer adds backslashes only and a folder under the root (Resolve's spelling of a `/` and of a file at a drive's or share's root were not seen); at most 1,024 characters. The facts come from another machine: types are strict (a number sent as text is refused), at most 64 streams, 256 tags per mapping, 4,096 characters per text, 1 MiB of JSON per file (counted in bytes), no lone surrogate anywhere, rationals and digit strings checked by pattern, and the ffprobe fields the writer does not read are ignored rather than trusted. Digits are ASCII only, everywhere: a `timecode` tag must be `HH:MM:SS:FF` in `[0-9]`, a `rotate` tag whole degrees in `[0-9]`, a side-data rotation a finite number of at most 360 degrees, and the project rate's text (`SetupBA` field 69) plain `[0-9]` with an optional fraction; `aar.media.probe`'s timecode pattern is ASCII too (`\d` alone matches other scripts' digits, which `int()` then reads, and a timecode in Arabic-Indic digits was authored verbatim). Rates, timecodes and rotations are read with `aar.media.probe`'s helpers (one implementation). The media receipt (`aar media receipt`) is not extended: it binds a hub copy to its PC original, while the writer needs facts for every file a cut uses, copied or not; a facts script on the PC writes one JSON line per file.

After authoring, every layer of every value (envelopes, zstd, keyed dicts, protobuf fields; at most 10 deep and 4,096 layers) is searched for the template's ids, bin, lockable map, file name and folder in UTF-8, UTF-16BE and UTF-16LE: any one found is refused (`bad_template`), so an id in a place the writer does not rewrite cannot leak. A layer that cannot be opened (a zstd frame that is not exactly one complete frame or does not decompress) and more layers than the bound are refused too, never skipped: they could hide an id. The zstd backend returns nothing for a truncated frame instead of failing (a looseness of `aar.drp.blobs`), so the frame is checked first. Every blob is taken apart by a closed list of known fields (with their wire types) and keys: an unknown one is refused, not copied blindly. Every decode and encode on a template value is typed: a NULL or non-blob value, a keyed-dict type the encoder does not write, or a derived number the template's field type cannot hold is a refusal, never an exception from the codec. **One boundary** (fix round 2) backs those specific checks: every public entry point (`author`, `facts_from_json`, `kind_of_facts`, `kind_of_rows`, `read_templates`, `check_clip`, `clips_from_rows`, `ClipRows.from_tables`, `ids` and `media_id`) is wrapped in `aar.drp.mediapool.errors.refusing`, which turns any `DrpError` (`BlobError`, `EncodeError`...), `struct.error`, arithmetic, indexing, conversion or type error that a damaged value raises below them into the entry point's typed refusal, keeping the original error's type and message; `read_templates` lets the project reader's own `LibraryError` through. A hostile template's `Resolution` with a non-zero padding word had escaped as a `BlobError` through the one decoder call no specific check wrapped; with the boundary a future unguarded call cannot leak. An id source (`new_id`, the caller's code, not untrusted input) that raises is `id_collision`, never taken for a damaged template. **Dates** share one range, `formulas.FIRST_YEAR`..`LAST_YEAR` (1970 to 2079, a few decades out): the modification time, the creation time and the date added.

**Kind key** (`aar.drp.mediapool.kinds`): media (sound, still, video), container (extension), video codec tag, pixel class (from `pix_fmt`; on the rows, the class whose frame size rule gives `FrameSize`), transposed, timecode present, and per audio stream codec name, bit depth, channels, sample rate and whether a layout is named. Each is read from the facts and from a template's rows. One more component, the look (`pix_fmt`, colour space, transfer, primaries, range, rotation), is what the unexplained `Radiometry` blob varies with: in the answer key a ProRes file without transfer and primaries tags has another `Radiometry` than the 17 tagged ones, and a grey PNG another than the RGBA ones. The rows cannot be read for it, so a template proves its look only through its own file's facts; without them the result is unverified (refused unless the caller allows it) and says why. That holds for every kind, sound kinds included: a template without its own facts cannot be checked against its rows either. The key was checked against the data: within every supported kind, every copied field was equal across all files of the kind in the answer key (the gate compares them).

**Envelopes.** The key leaves out what does not change which fields are copied (resolution, rate, profile, sample rate), but the evidence covers only the files it was checked on, and every verified kind of the answer key is homogeneous (all 68 MP4 files one resolution, rate and profile, from one project). So each verified kind records its envelope: for each of resolution, frame rate, drop-frame or not, bit depth, chroma class, the video profile ffprobe gives, the audio sample rate and channels per stream and the audio profile, and (fix round 2) every other ffprobe stream property that is constant across each verified kind in the corpus and could change what Resolve stores: for the picture its coded size, level, field order, sample and display aspect ratio, `has_b_frames`, colour range, chroma location, `bits_per_raw_sample`, time base and the stream's own `r_frame_rate` and `avg_frame_rate` (the derived rate may come from a timecode track instead), and per audio stream its codec, sample format, bits per sample, `bits_per_raw_sample`, channel layout, initial padding and time base, the values its checked files had (`kinds.envelope_of`; the scoreboard derives them, the gate test fails when the registry disagrees). A property the facts do not have is recorded and compared as absent (`-`), so an interlaced, anamorphic or other-level file, or a file whose facts leave such a property out, is not taken as covered. A file of a verified kind outside its envelope is unverified, with each property named (`the file's resolution 1920x1080 lies outside the evidence for its kind (checked: 3840x2160)`).

**A template's facts are checked against its rows.** Facts attached to a template prove its look, so they are not trusted on their word: `author` first authors the template clip from its own facts (itself as the template) and compares the result with its own rows the way the gate does. On any difference (facts of another file, or of the file as it is now rather than when Resolve read it) the result is unverified, naming the first differing field. A template without facts can only give an unverified result (`the template's own facts are missing`), for every kind.

**Refused**: BRAW (ffprobe decodes only its sound and timecode: no picture codec, size or pixel format; `cannot_derive`); a file with a second picture that is not cover art (`unsupported_kind`: what Resolve records of it was not seen); camera files with camera metadata (a phone camera app's HEVC files: their metadata entries map to tags ambiguously, as reel, scene and shot all held `1`, and an entry such as the location appears only when its tag exists and is reformatted; the reel number in `VideoMetadata` has no proven rule); a rotated picture; a still whose name holds a digit (one grey PNG whose name held a clip number has that number as its `StartFrame`: Resolve seems to read a number in a still's name as a frame number, which one sample cannot establish); a variable-frame-rate file without a timecode track; a non-standard rate or a frame count that is not whole; any kind not in `KINDS` (`unsupported_kind`); a template of another kind or of another look (`kind_mismatch`); a template whose rows are incomplete, do not decode, or hold a field or key the writer does not know (`bad_template`); a new id already in the project or made twice (`id_collision`); a placement out of range (`bad_placement`); a result that would not be verified without `allow_unverified` (`unverified`). Every refusal is a `MediaPoolError` with a code and a hint, and nothing else comes out: a fuzz test (`tests/drp/test_mediapool_fuzz.py`) feeds randomly damaged facts, template rows and values deep inside template blobs and accepts only those (20,000 seeds were run once with no other exception). Since fix round 2 a second, aimed run damages one byte inside a fixed-layout value at any layer of a template blob (a resolution, a frame rate, audio extents, a timemap, a fixed64 or fixed32 protobuf field: the values the shared decoders read by position), 600 cases a run; unaimed damage had found the padding leak about once in 18,000 cases, the aimed run finds it within its first 25.

**The gate** (`tests/drp/test_mediapool_gate.py`, opt-in: `AAR_MEDIA_FACTS` names the facts file, `AAR_MEDIA_PROJECTS` the Resolve-saved `Project.db` files; `scripts/media_scoreboard.py` prints the scoreboard). For every clip with facts, its rows are authored from its facts with another clip of its kind as the template (each project read once, by its resolved full path, and the target left out by project and media id, so a project given twice or through an alias path still has no template from itself; a clip of another file preferred over the same file imported twice, then one of the same project; not a stale one while another is left; the template's own facts are checked against its rows on every authoring, and a reason the result would not be verified counts against the kind like a differing field) and compared with Resolve's rows (`aar.drp.mediapool.fields`). Rows are compared by role, ids replaced by the role they name (so a reference to the wrong row differs), and the comparison is total: every decoded level compares the value, a keyed-dict entry's type tag and null flag, the order of every keyed dict's entries and every message's fields, and an envelope's version and codec; a key or field that occurs twice is kept as two entries; a message is decoded only if it re-encodes to its own bytes; a bool is compared by its byte and a NaN by its bits; and whatever does not decode is compared byte for byte. Two relaxations, both stated in the code: a zstd payload is compared decoded, not as its frame (Resolve compresses, the encoder writes raw blocks; the codec is still compared), and metadata entries are compared by key, their order sorted (the order is not a function of the keys: clips with the same set of keys store them in different orders, and what decides it is not known; no file is in both saved projects, so whether it changes between saves of one file is not shown). A file whose modification time differs from the one Resolve recorded (`Clip` #3, parsed) changed after Resolve read it: it is counted stale, not compared (13 WAVs); a `Clip` #3 that does not parse is reported and the file compared anyway. Each kind's envelope is what its checked files covered; the gate fails when a verified kind's recorded envelope differs. The fields left out are an explicit list (`EXCLUDED`), each with its reason and each shown by the scoreboard to have differed somewhere: the bin and position; UI state and per-clip notes (playhead, preset, pins, `VideoMetadata`, `MediaMetadata` of the clip and its infos); the date added; a later project age and the relink history in a picture's `FieldsBlob`; the project's rate in a sound clip's `FieldsBlob` and a still's `Time.FrameRate` (the rate when it was imported: one project's sound files and stills hold 24 though the project is now 23.976); `Clip` #14 and #26; the metadata blob's save time and map. An order leaf ignores excluded children. A mutation check showed the gate fails for: the exactly rounded start (68 files), the modification instead of the creation time, an unpadded day, rounding audio samples to the nearest, a missing channel layout, ffprobe's codec name, a frame size without the 8192 pad, and (since this round) a keyed-dict entry's type tag or null flag changed, keyed-dict or protobuf order reversed, and a zstd envelope written plain. Rounding frame counts and ignoring rotation made no difference on the supported kinds, which is why a non-whole frame count and a rotated file are refused.

**Open questions.** `Clip` #26 (the folder without its drive letter) is on some clips only, and what decides it is not known: it is excluded and every result's notes name it. `Sm2MpMedia.FieldsBlob` #1.#3 on ProRes 4444 clips (above). The framing of a 65-byte message.

**Known looseness, not fixed.** The export's edit-PC path check is a second, laxer validator than `aar.host.winpath`; `aar.drp.blobs.zstd_decompress` returns nothing for a truncated frame (the media-pool code checks frames first); a template id nested under a layer that fails strict protobuf decode might survive the leftover-id scan (suspected, not shown); no authored column has a real sample near the 64-byte framing boundary.

**Not verified.** Whether Resolve opens a project holding authored clips without relinking or re-analysing them (S25c2's staging project (a) waits for a person; the spike's one camera clip is the only evidence). Kinds with one file, rotated files, camera metadata, BRAW, stills named with digits, sample rates other than 44.1 and 48 kHz, more than one audio stream, 5.1 and other layouts, drop-frame timecodes on real files (the rule is the existing timecode helper's). Project versions other than 17, and Resolve versions other than 21.1. The project rate's place (`SM_Config` `SetupBA` field 69, text such as `29.97`) was read on two saves only. The answer key is two projects from one machine; the 251 files whose facts could not be measured (gone from the PC) were not checked.

#### Timeline items (S25c2)

A library project's cut is its timeline's items: one `Sm2TiItem` row per picture (`Sm2TiVideoClip`) or sound (`Sm2TiAudioClip`) and one `Sm2TiItem_Sm2TiTrack` join row (`Items`, `DbIndex` the item's place in record order; on every real track the vector is dense and sorted by `Start`). A picture and its own sound name each other in `FieldsBlob`; an item's id occurs nowhere else. `aar.drp.items.author_item(clip, template, template_clips, placement)` returns the two rows of one item playing a media clip (`ClipRows`, Resolve's own or authored by `aar.drp.mediapool`) at full speed, from a template item Resolve saved of the same kind; it writes nothing. Its public entry points (`author_item`, `media_view`, `timemap`, `read_items`, `check_item`, `links_of`, `shape_of`, `field_paths`, `flatten_item`, `compare_items`, `item_excluded`, and the gate's `run`, `extents_seconds` and `format_scoreboard`) sit behind the media pool's one typed boundary (`refusing`, now with the error type as a parameter; since fix round 1 it also takes an `AttributeError`, a value of another type than the code expects, as damage), and every refusal is an `ItemError` (a `MediaPoolError` with the item codes: `bad_template`, `no_template`, `kind_mismatch`, `unsupported_item`, `bad_media`, `bad_placement`, `id_collision`).

**Field map.** D derived from the media clip's rows (`aar.drp.items.media.media_view`), A from the placement, I identity, F fresh (as on an item Resolve has just made), C copied from the template (every other column of the 58 a 21.1 save has; a template with another column is refused).

| where | class | rule |
|---|---|---|
| `Name` | D | the clip's `Name` (a name given in the placement instead; 1,107 supported real items were renamed by a person) |
| `MediaRef`, `MediaFilePath` | D | the clip's id; `Clip` #1 + `\` + #2 of its video info (its first audio info for a sound file) |
| `MediaFrameRate` | D | a picture file's `Time.FrameRate`; a sound file's import rate (`Sm2MpMedia.FieldsBlob` #2.#1 + 8 zero bytes) |
| `MediaTimemapBA` | D | `0x02` + big-endian double of `F / r - 1 / r`, the time of the last frame: `F` = `NumFrames` for a picture file, `Duration / SampleRate * r` (a double) of the first audio track for a sound file; `r` the rate above as a double. The spike's `samples / rate - 1 / rate` differs in the last bit on 16 of 4,615 real sound items |
| `MediaStartTime` | D | a picture file: the start timecode's frame number over the rate (`formulas.start_seconds`, the clip's own `TracksBA` `StartTime` rule), 0 without one; a sound file: its track's `StartTime` |
| `VirtualAudioTrackBA` | D | sound only: `ChannelsBA` = `2`, the channel count, then `0x4001`.. one per channel (big-endian u32); `AudioType` 1 for mono, 0 for stereo; other counts refused |
| `MediaTrackIdx` | D | sound 0 (the first audio stream; no other was seen), picture NULL |

| `FieldsBlob` framing | D | plain up to 64 bytes, zstd above (the media pool's rule, `blobtree.rewrap`) |
| `Sm2TiItem_id` | I | fresh |
| `pLmVerTable`, `CompositionTable`, `EffectFiltersBA`, `ImportExportMetadataBA`, `MarkersBA`, `MediaMetadata`; `FieldsBlob` #1.#1.#2 (Fairlight clip effects), #1.#1.#3, #1.#1.#21, #1.#9 (written by later edits) | F | NULL, or left out |

After authoring, no id of the template (its own, its links, its media, its track) may be left in any layer of any value (the media pool's `contains_text`), so a column such as `Group` holding one is a refusal, not a copy.

**Placement checks** (`_check_placement`, the cut's `_check_cut`, and the verifier of the written project on its own). A picture needs a clip with a picture and reads no further than `NumFrames`; a sound needs a clip with sound and reads no further than its first audio track's sound (the one `MediaTrackIdx` 0 plays): `ceil(Duration × r / SampleRate)` frames, `r` the item's rate as the standard fraction (the picture's rate for a picture file, the import rate for a sound file), rounded up because the last frame may be partial (fix round 4; before, a sound placement only needed channels, so a sound could be authored thousands of frames past a one-second clip). On the item gate's real sound items the bound refuses none: the tightest margin is 0 frames (56 items end exactly on it, 40 of them inside the partial last frame, up to 0.0005 frames past the samples, which rounding down would refuse). Every placement number is a whole number (not a bool) from 0 to 24 hours at 60 fps, a duration at least one frame; a cut entry's record frames are whole frames from 0, and a split edit's own sound range on an entry without sound is refused rather than ignored. A sound clip's `StartTime` must be finite.

**Shapes** (`aar.drp.items.rows.shape_of`). An item is supported (as a template and as something the writer makes) when it is a picture or sound of a media file clip of the project, at whole frames, at full speed (the 9-byte time map), not a title (`PrettyType`), playing the first audio stream, with a `FieldsBlob` of known fields only. Everything else is refused per item with its reason, never dropped silently. A `Start`, `Duration` or `In` written in Resolve's `N|hex` form is classified by its fraction (fix round 1; the old reason, "sub-frame or unreadable", was wrong for most of them): within 1e-9 of a whole frame (the bound `aar.plan.timeline_import.FRAME_ROUNDOFF` uses on the same values) it is a whole frame with float noise in the stored fraction (`NOISY_WHOLE_FRAMES`, not authored and not compared yet: the writer writes plain counts and whether Resolve's form matters is not known); otherwise it is truly sub-frame. On the two real saves: 4,464 items of whole frames stored with a fraction (4,449 sounds, every one of them a sound of a sound file, and 15 pictures), 102 truly sub-frame (46 sound durations, 56 picture in points) and one sub-frame start, 920 transitions, 304 items of compound, multicam or timeline media, 12 retimed pictures and one title (5,804 items). So the gate compares 166 of the 4,662 sound items of sound files (about 4 %; PLAN.md follow-up); every sound item of a picture file (454) is compared. The tags a supported item carries (graded, Fusion, effects, markers, import metadata, edit history, renamed) are counted; the writer never writes them.

**The gate** (`tests/drp/test_items_gate.py`, opt-in with `AAR_ITEM_PROJECTS`; `scripts/items_scoreboard.py`): every supported item of the given projects is authored from its media clip's rows, its own range, position, track, index and links, with a *different* real item of its kind and linkage as the template, and compared with Resolve's rows by `aar.drp.mediapool.fields.compare_flat` (the media pool's total comparison: type tags, null flags, order, envelopes, undecodable bytes byte for byte; ids compared as the role they name). On the two Resolve 21.1 saves: 5,054 items, 338,316 fields, all equal (pictures of files with sound 4,334, without sound 100; sounds of picture files 454, of sound files 166; 3,524 linked, 1,530 unlinked), in three runs: templates from the same project, from the other project, and linked templates for unlinked items (which the writer falls back to). A project is told apart by its resolved full path, not its file name (every library project's file is `Project.db`; fix round 3, tested with two synthetic projects of that name in two folders); each project is read once (fix round 4: a project given twice, or through an alias path, offered a second read of every item as that item's own template, because the target was left out by object, not by project and item id), and a template playing another file is preferred over another clip of the same file. Each sequence's `MediaExtents` length recomputed from its items: 15 sequences, all equal (32 with an item not in plain whole frames skipped). The gate's numbers are unchanged by fix round 1 (5,054 items, 338,316 fields; the `--linked-templates` run of `scripts/items_scoreboard.py` now really uses linked templates: the script parsed the flag and did not pass it on before, while the gate test always did). The explicit exclusions (`ITEM_EXCLUDED`), each shown by the gate to differ somewhere: the later-edit columns and blob fields above; `CurrentSelectorIdx` of a picture (unexplained: 302 distinct values over 4,220 pictures of one project, every sound 0; the writer writes 0, so 804 compared pictures differ there); for 70 items (all on timelines imported into Resolve from FCPXML), `MediaStartTime` holds the exact quotient of timecode and rate instead of the pool's rounded one (tag `exact-start`, only where that is so); for 21 pictures of files without sound it is the neighbouring double of the rule's (tag `start-last-bit`, only where the two are neighbours: such a clip stores no start of its own); the empty `#1.#1` group of an unlinked item with later-edit fields, and the envelope codec of an item whose dropped fields changed its length (tags `unlinked-group`, `blob-later`). The evidence envelope: two projects from one machine and one Resolve version, 23.976 and 29.97 timelines, mono and stereo sound, one audio stream per file.

#### Library projects (S25c2)

`aar.drp.libwrite.make_project` makes one project: in a staging folder inside the library it copies the seed (the library reader's settled copy), checks it, lets the caller author media and items against it, refuses an unopened operation unless allowed, changes the copy's rows in one transaction, reads it back, verifies it independently against the cut, runs the caller's check, and renames the folder into place.

**One typed boundary** (fix round 1). Every public entry point of `aar.drp.libwrite` (`make_project`, `read_seed`, `build_project`, `operations_for`, `sequence_length`, `check_written`, `verify_written`, `expected_items`, `place_project`, `check_project_name`, `fold_name`, `author_cut`, `pick_item_templates`, `unopened`) sits behind `aar.drp.libwrite.errors.refusing`, as the media pool's and the items' do: whatever a damaged seed, template or input makes the code below raise (the shared decoders' errors, `struct`, arithmetic, indexing, conversion, type and attribute errors, SQLite's errors and their `UnicodeDecodeError`), and the library reader's and the item and media writers' refusals, become a `ProjectWriteError` of the entry point's code with the original type and message kept. What a caller's callback raised (`make_project`'s `author` and `check`, `place_project`'s `build`) is the caller's and passes unchanged (`by_caller` marks it), and so do interrupts and `OSError` (the placement turns the library's own into `library_unwritable`). `export_library` has the export's own boundary of the same shape: a writer refusal becomes the export's of the same code (details kept), an item or media refusal `item_refused` or `media_refused`, a library reader's refusal, an `OSError` reading an input and any other damage `bad_input`. A test lists every function each module exports and fails on one that is not wrapped. The library reader itself (`aar.drp.library`) catches `UnicodeDecodeError` with `sqlite3.Error` (`SQL_ERRORS`) on every read: SQLite quotes a damaged schema's bytes in its error message, and Python's decoding of that message raised from `PRAGMA integrity_check` in `read_rows` and `open_library` alike; and `read_rows` refuses a project table without `SM_Project_id` or `ProjectVersion` as `not_a_project` (a renamed column was a `KeyError`). The aimed seed fuzz (`tests/drp/seed_fuzz.py`: row values and types, fixed-layout blobs, other blobs, renamed columns and dropped tables, the file's bytes and the stored schema's text; 600 cases a run) found the three crashes the validator reported (a `TypeError`, a `KeyError`, a `UnicodeDecodeError`) on the code before the round, and none after. `aar.plan.export.library.export_library` is the plan's caller; `scripts/stage_library_projects.py` the staging one.

**The seed** (`read_seed`, refusals `bad_seed`): a Resolve 21.1 (`ProjectVersion` 17) `Project.db` the owner saved, read through the bounded reader, with exactly one timeline listed by the project, one sequence and track container, exactly one video and one audio track and no others, a standard frame rate and a whole-frame start. Every column the reader and the writer use must be in its table (`SEED_COLUMNS`; a renamed one is `bad_seed`, never read as empty), and the seed may hold no trigger but Resolve's own two (on deletes of `BtVideoInfo` and `BtAudioInfo`, compared by their text): the writer changes rows in every table, and another trigger would change the copy behind its back. Its timeline is empty, or holds only plain items (supported shape, no tag) whose ids are named nowhere but in the items and their join rows (checked on every value of every table, every layer): those are removed (`remove_items`, the spike's operation). A seed item that carries a grade, effect, Fusion composition, marker or edit history is refused: removing it would leave the rows it names. The seed's own media stay in the pool (removing media is not proven). New media go in the bin that holds the timeline's own clip, after what it holds. The resolution is the timeline's own, or the project's when the timeline follows it and the project stores it (`SetupBA` field 1, text such as `1920 x 1080 HD`); when neither is stored the export needs it stated (`--seed-resolution WxH`, reported as stated, never written). The plan's frame rate, resolution and start must equal the seed timeline's, else `seed_mismatch` with a hint (changing them is not proven).

**Operations** (`aar.drp.libwrite.ops.OPERATIONS`; every report lists those it used with their status):

| operation | status | what |
|---|---|---|
| `new_project_identity` | opened in Resolve | a fresh project id in every text column that held the seed's (it occurs only there), and the new `ProjectName` |
| `rename_timeline` | not yet opened | `Sm2Timeline.Name` and the `Name` of the timeline's media-pool clip |
| `remove_items` | opened in Resolve | delete the seed timeline's items and their join rows |
| `add_media` | not yet opened | insert media-pool clips authored from facts (the main open risk) |
| `add_linked_items` | opened in Resolve | linked picture and sound items of one range, abutting from the start (the spike's cut) |
| `add_picture_only_items`, `add_sound_only_items` | not yet opened | a picture with no sound, a sound with no picture |
| `leave_gaps` | not yet opened | items that do not start at the timeline's start or do not abut |
| `split_edit` | not yet opened | a linked picture and sound with different ranges |
| `add_sound_transitions` | not yet opened | sound crossfades on joins of the sound track (S25e, below) |
| `set_extents` | opened in Resolve | `MediaExtents` length = the last item's end frame over the rate (a double) minus the start in seconds: Resolve's own formula on 15 real sequences (the spike's `frames / rate` differs in the last bits on 11 of them) |

Until a person opens the staging projects, `add_media` makes every real export need it. The copy stays in rollback-journal mode, as Resolve keeps it, with no journal left beside it.

**Self-check, two independent reads.** Before anything is placed: SQLite's integrity check after the commit, and no journal, WAL or shared-memory file left beside the copy; `aar.drp.read_drp` must read the file with no issue outside the import's `READER_WARNING_CODES`, as the named project, with one timeline of the expected name, rate and start, holding exactly the items written (track, record range, source in and file path); then **`verify_written`** (`aar.drp.libwrite.verify`, fix round 1), which does not use the code that wrote the rows (`author_item`, `media_view`, `author_cut`, `sequence_length`): from the cut the caller authored from (the `Cut` entries, `Authored.cuts`, required whenever there are items) and from each media clip's own rows as written, decoded with the shared blob decoders only, it recomputes by the field map above what every item and the sequence must hold, and compares it with the rows read back: each item's type and track, its place in its track's `Items` vector (dense from 0, in record order, no overlap), `Start`, `Duration`, `In`, `MediaRef`, and that clip's `MediaFilePath`, `MediaStartTime` (to the bit), `MediaTimemapBA`, `MediaFrameRate`, `MediaTrackIdx` and channel count; its links (the other half of the same cut entry and nothing else; one half alone has none); that the timeline holds those items and no others; and the sequence's `MediaExtents` (the seed's start, and the last end over the rate minus the start). A difference is `self_check_failed` naming the field. The validator's planted errors that the first two reads let through (a picture linked to a picture, the sequence length a second long or short, an item's `MediaFilePath`, `MediaStartTime` (also one unit in the last place), `MediaTimemapBA` or `MediaFrameRate` wrong, `MediaTrackIdx` wrong) are each refused by it before placement, in tests. Since fix round 2 it is total over what the writer puts in the file. *Every item column* has one rule (`verify.ITEM_RULES`, one entry per column of the writer's closed list `ITEM_COLUMNS`; a test derives the list from it, so a new column cannot go unverified, and the verifier refuses every project while one lacks a rule; a column outside the list must be empty): recomputed from the cut and the clip's rows (the above, plus `Name` = the media's name, `Sm2TiItem_id` a fresh uuid, `PreConformMediaExtents` the 16 constant bytes every picture of the corpus holds and empty on a sound, `VirtualAudioTrackBA` byte for byte (`ChannelsBA` = 2, the count and ids `0x4001`.., then `AudioType` 1 for mono, 0 for stereo), and `FieldsBlob` byte for byte: `#1` holding the link list when linked and `#1.#4` = 1, then a picture's `#2` (16 constant bytes) or a sound's `#15` = 4, framed version 2, plain up to 64 bytes, else raw zstd; every plain item of the corpus has that form); empty, as on an item Resolve has just made (`pLmVerTable`, `CompositionTable`, `EffectFiltersBA`, `ImportExportMetadataBA`, `MarkersBA`, `MediaMetadata`: the writer's `LATER_COLUMNS`); or a stated constant, the one value every plain item of the two saves holds (`Track`, `Group`, `Flags`, `UiMemento`, `PriorityIndex`, `MediaReelNumber`, the render-text flags, `IsForceConformed` 1, `MixedFrameRateAlignment` 0.0, `CurrentSelectorIdx` 0, the lock ids empty text, and the rest). *Every added media clip*, from its rows as written: one media row of a file clip in the seed's bin once (`MediaVec`, the bin's indexes dense from 0), its picture info (one for a picture file, none for a sound file, named by its `Video`), its sound infos (each naming this clip, joined by `EmbeddedAudioVec` from 0 without a repeat, as many as were authored), its lockable blobs and presets as many as authored, and every `Clip` blob naming the same folder and file, the media's own name. *Every other row of every table*: `read_seed` keeps a digest of each seed row (`Seed.digests`, by table; type and value of every column, a double by its bits, the project id standing for itself), and the written file must hold the seed's tables and columns, each seed row unchanged but for the cells the writer changes (`seed.WRITER_CELLS`: the project's new id, its name, the timeline's and its media clip's name when renamed, and `MediaExtents`, each checked on its own), and beyond those exactly the authored clips' rows: per table the seed's count plus what was added, no row missing, changed or extra. The fix-check's plants (an effect blob, a grade table, a Fusion composition or markers on an item; an extra sound join or picture info of a used clip; a sound info naming another file; a damaged `FieldsBlob` tail; wrong `Flags`, `Name`, `Track`, `Group`, `PreConformMediaExtents`; a seed's media row renamed; a row the writer did not add; the project's or timeline's name) are each refused by it alone before placement, in tests. The six staging projects pass it unchanged. For a plan, last, `aar.plan.timeline_import` of the written project against the plan it was written from must report `unchanged` with nothing not carried, foreign, added, dropped or on another track. Anything else is `self_check_failed` and nothing is placed.

**Placement** (`place_project`). The folder must be a library (`aar.drp.library.library_users_dir`, the listing's own check, `not_a_library`), with one user that has a `Projects` folder or the user named (`--library-user`). No folder below the library folder the caller named may be a symbolic link or, on Windows, any reparse point such as a junction (`Resolve Projects`, `Users`, the user's folder, `Projects`, the staging folder and the build folders; the library path itself may be a link), and the resolved `Projects` folder and staging folders must lie inside the resolved library (`not_a_library`, `library_unwritable` for the staging folder); the folders are checked again right before the rename. The name must be one folder name on the Windows share (`aar.host.winpath.check_name`: no forbidden character, the colon among them, no reserved device name, no trailing dot or space, no control character or lone surrogate; plus the hub's `hidden_character`, at most 200 characters, not starting with a dot) and, since fix round 1, not start with a space, not be `Project.db` in any case, be in Unicode's composed form (NFC; refused with the NFC form named, not normalised quietly) and take at most 255 bytes of UTF-8 and 255 UTF-16 units: all `bad_project_name`, checked before any work (the export checks the name first of all). No folder of that name in any case or Unicode form may exist (`project_exists`): names are compared folded (`fold_name`: `casefold` of the decomposed form, then upper-cased and folded again, so the dotless and dotted i fold together as Windows' comparison has them, then NFC; it folds more names together than a share does, never fewer). From the existence check through the rename a placement holds a lock keyed by the folded name, `Resolve Projects/.aar-staging/lock-<sha256 of the folded name>`, created exclusively (`O_EXCL`, on Windows and POSIX alike) and holding a random token of the placement; a second placement of a name that folds to the same is refused (`project_exists`, naming the lock and any build folder of the staging folder, each safe to delete when no export is running; `leftovers` in its details) while the first holds it, so two concurrent exports of `Race` and `RACE` place one project. The project is built in `Resolve Projects/.aar-staging/build-<random>/project/` (refused when that is on another file system than the projects), given the mode of a project already in the library (its folder's and its `Project.db`'s; the `Projects` folder's when there is none) and, where the process may, its owner and group (the report says what could not be set), checked again for a name clash and renamed into `Users/<user>/Projects/<name>` without replacing anything: Linux's `renameat2(RENAME_NOREPLACE)` where the file system has it (an existing folder of that exact name, even an empty one, is `project_exists`), Windows' own rename (which never replaces a folder), else a rename right after a fresh check (a rename that meets a folder is `project_exists`; the existing folder is never written into; a folder that is not empty, as every project is, cannot be replaced by it). `renameat2` comes from the C library already in the process (`ctypes.CDLL(None)`, looked up at first use: no library search, no subprocess at import); a C library without it, and an error of the call that means it is not available here (`ENOSYS`, `EINVAL`, `EPERM` as a syscall filter returns it, `EOPNOTSUPP`), take the checked rename, which raises the real error if there is one; any other error of the call is refused (`library_unwritable`). A rename that reports an error after the folder has moved (the same device and inode at the destination) is a placed project, with the error in the report's `placement.cleanup`, never "could not be placed". The build folder and the lock are removed on every path, failures and interrupts included (since fix round 2, from the first statement that may make the staging folder to the end of the cleanup, one handler: a lock whose write fails, a full disk among them, is removed with the staging folder; an interrupt between creating the lock and recording it leaves an empty lock that is named as possibly this export's, never deleted; an interrupt right after the rename reports the project placed; an empty staging folder that cannot be removed is named); whatever cannot be removed is named: on a refusal in its message and its `residue` detail (the export's JSON carries it, its text prints it), on a placed project in `placement.cleanup`, and on an interrupt (which may land during the removal) as the interrupt's `residue` and a note, which the export's CLI prints as an `interrupted` error (exit 130, JSON with `residue` under `--json`). A folder or lock a killed process left is listed by the next placement in that library as a leftover (`staging_leftovers`), never deleted by it; a lock left so refuses its name until a person deletes it. A library that is read-only, full or removed mid-write is `library_unwritable`; a write the seed's copy refuses for another reason than storage (a missing column, a constraint; SQLite's error name, or its message when there is none) is `bad_seed`. On Windows modes and owners follow the share (said in the report). **Acting only on what it made** (fix round 3, the automated review). A staging folder that already exists is used as it is only when this user owns it and others can write to it no more widely than the `Projects` folder allows (its group and other write bits within the `Projects` folder's); else `library_unwritable` naming it (and it is left alone, never removed). One the placement makes is private (mode 700), as are the build folder and the project folder until the library's modes are given. The build folder and the project folder are recorded (device and inode) right after they are made, `Project.db` right after the seed's copy creates it (`created_file`: a regular file with one name, this user's), and `make_project` checks after every step that opens the file by its name (reading the seed, writing the rows, the read-back, the verifier, the caller's check) that the name still leads to that file (`check_created`). Modes and owners are changed only through descriptors opened without following a link (`O_NOFOLLOW`, `O_DIRECTORY`, the file relative to the project folder's descriptor, that one relative to the build folder's) and checked with `fstat` to be the very folders and file recorded (`fchmod`, `fchown`); a build folder, project folder or file swapped (for a link, a hard link to another file, or another file or folder) is `library_unwritable` naming it, nothing is placed, and a file outside the library is never touched. The rename's source is the project folder's name relative to the build folder's checked descriptor (`renameat2` with that descriptor, or `rename` with `src_dir_fd`); the cleanup removes the build folder only when it is still the one made (one put in its place is named, never removed); and the export hashes the placed file only when it is the one written (`read_placed`, through a descriptor opened without following a link). On Windows, which has no `O_NOFOLLOW` or `dir_fd`, the same identities are checked on the paths (`lstat`, never a link or junction) and modes follow the share's. **The shared staging folder** is still removed when the last export leaves it empty; another export that checked it just before then meets it gone when it makes its lock, and makes it again and retries (at most 8 times, a few milliseconds apart; any missing-folder error on that path counts, since a third export may have made it again meanwhile, and on Windows also a refused access, which a folder being removed answers until it is gone), so exports of different names never fail each other over it (tested with 60 rounds of 4 concurrent exports started a little apart, with the window between the check and the lock widened: the code before the fix failed 96 of the 240). Recreating it was chosen over keeping it, because a kept staging folder, now refused when another user owns it, would block every other user of a shared library for good. Not covered: a folder above the build folder (`Resolve Projects`, the staging folder) swapped by someone with write access to it between the last check and the rename (the rename's source is anchored on the build folder's descriptor, the destination is still a path; the no-replace rename still cannot overwrite a project); SQLite opens the staged file by its name, so a swap and a swap back within one step that reads it (the checks bracket each step) is not seen, though the modes, owners, rename and hash act only on the file recorded; where a file system reports no inode numbers (some Windows shares) the identity check is only as strong as the path check; the folding is Unicode's and Windows' upper case, not a given share's own table.

**The export** (`aar plan export PLAN --profile P --format library --library FOLDER --seed PROJECT.db --facts FACTS.jsonl [--templates PROJECT.db ...] --project-name NAME [--media-map MAP.json] [--allow-unverified-media] [--allow-unopened-operations] [--seed-resolution WxH] [--library-user U] [--report FILE] [--json]`, with the library reading budgets of `import-timeline`). It lints (`lint_errors`), lays the plan out with the FCPXML export's `layout_for`, and refuses (`unsupported_plan_feature`, each with its location) what would change the cut and the project cannot carry yet: transitions other than the supported sound crossfades (S25e: the head's dissolve, the outro's, every picture transition, and a transition the layout could not place on a join), titles and the sting, clips off V1, audio fades, and sound a muted track without a bus silences. Each source's edit-PC path must have facts (`facts_missing`), and the facts must be of the file the plan cuts: a picture at the plan's rate holding every frame read, and the stated start timecode when the plan has one (`facts_mismatch`; a sound file or still is refused there too: the timeline import carries only pictures with their own sound). One clip is authored per file (`aar.drp.mediapool.author`, a template clip from `--templates` or the seed, one whose own facts are of the file's kind first; its refusals pass as `media_refused` with the media code, and an unverified result needs `--allow-unverified-media`, named in the report). Each layout clip becomes a picture and, when the file has sound, its linked sound on the seed's two tracks; the timeline is renamed to the plan's. Exit 0 written and placed, 2 refused (nothing placed; anything left in the library named), 130 interrupted (what was left, or the placed project, named). Without `--format library`, `--out` or `--verify` is required as before: the usage error is argparse's own for the FCPXML arguments, byte for byte what the command printed before the library format (a test builds that parser and compares). The report (printed, and with `--report` also written, never over a file): the project (name, folder, path, id, sha256), plan, timeline (rate, start, frames, resolution and what it was checked against), seed, the operations with their status and those not yet opened, each file's media kind, status, unverified reasons, template and notes, item counts, `not_carried` in the FCPXML report's vocabulary (`feature`, `location`, `detail`, `action`: a segment's gain, its framing (reframe, transform, fill), a label or note, markers, captions, and the layout's own `not_expressible` items; none changes the cut list, and the timeline import keeps the plan's values for all of them), the placement's modes and leftovers, lint warnings and the self-check.

**Staging for the human check** (`scripts/stage_library_projects.py --out NEW_FOLDER --seed --facts --templates`): builds, with the product code, a library of its own in a folder that must not exist yet (so never the real one) holding one small project per operation not yet opened, each self-checked, and `STAGING.md` with one line per project saying what a person should see in Resolve if it worked: (a) two clips of a verified kind authored from facts and cut together (the export; at the one-clip seed's 29.97 the verified picture kinds have no sound, so these are picture-only items too), (b) the seed's own clip in linked cuts with the timeline renamed, (c1) picture-only, (c2) sound-only items, (d1) gaps, (d2) a split edit (the sound leading by 10 frames); since S25e (e1) three linked cuts with a 2-frame Cross Fade 0 dB centred on each of the two joins (the ccn profile's crossfade: audible as no click at either cut, the picture cutting hard) and (e2) two linked cuts with a 16-frame Cross Fade +3 dB centred on the join (a short audible blend). The transition template comes from `--templates`, and the seed timeline must run at 29.97.

**Not carried, not verified.** Not verified: that Resolve opens a project holding an authored clip, a renamed timeline, picture-only or sound-only items, gaps or a split edit (staged, waiting for a person); seeds other than empty or plainly cut timelines (only one real seed shape, the one-clip save, was available); a seed in another bin layout; media rates other than the timeline's (refused); other project versions and Resolve versions. Not written: picture transitions and sound transitions of other kinds (S25e writes the supported sound crossfades), titles, fades, other tracks, gain, framing, markers; the timeline's thumbnail in its sequence row stays the seed's (Resolve redraws it, assumed), and so do the timeline clip's own extents (they did not follow the content on the one real save). A plan cannot express a split edit without an audio crossfade, so the export never makes one; the writer can (staged). Removing a seed's media is not done.

#### Library hand-off and pickup (S25d)

S25d puts library projects into the recipe: the edit PC measures the facts, the export step writes the cut into the library beside the FCPXML, and the cold worker picks up each save. The writer is unchanged: what a library project cannot carry is still refused.

**Facts from the edit PC (`aar.media.facts`, `aar media facts PATH... --out FACTS.jsonl [--pc-folder LOCAL=PC] [--timeout S] [--max-files N] [--max-bytes N]`, also `python -m aar.media.facts` from a copy of `src`, standard library only).** For each file, the S25c1 record: the path as the PC names it (the absolute path on Windows; `--pc-folder` names a folder when it runs elsewhere), size, the modification time on the PC's wall clock (C `ctime` form, English names whatever the locale) and in UTC (seven fractional digits), the creation time in UTC where the system keeps one (`st_birthtime_ns`: Windows and the BSDs; none on Linux), and `ffprobe -show_format -show_streams` as JSON. Read-only: the files are only stat'ed and handed to ffprobe (argument list, `file:` URL); their identity (device, inode, size, modification time) must be the same after the probe (`changed_while_measured`). Bounded: at most 256 files a run (refused before any probe, `too_many_files`; exactly the limit is fine), each probe killed after `--timeout` (60 s), the whole run at most `--deadline` (1,800 s: each probe gets the smaller of its timeout and the time left, and a file not reached is listed `deadline`), each line at most 1 MiB (the hub's own limit), the output at most `--max-bytes` (64 MiB) with error lines counted too (the file that would pass it and every later one are listed `output_cap`, and an error line that does not fit either is only printed, `"in_file": false`, counted in the summary's `not_in_file`). A file that is missing, not a regular file (a FIFO is never opened), empty, refused by ffprobe, timed out, changed (device, inode, size or modification time differ after the probe, so an edit in place to the same size is caught), whose name is not valid Unicode (`unrepresentable_name`: a POSIX name of non-UTF-8 bytes or a lone surrogate on Windows, shown with `\udcff` escapes) or whose modification time the system cannot write as a date (`bad_time`: Windows' `localtime` refuses times before 1970 and after the year 3000; nothing past 9999 fits the form) is written as an error line `{"path", "exists", "error": {"code", "message"}}`, printed, and makes the run exit 2. The creation time is read where each system keeps it: `st_birthtime_ns` (Windows on Python 3.12+, the BSDs), `st_birthtime` (macOS), `st_ctime_ns` on Windows before 3.12 only (everywhere else it is the last status change, never used); 0 means unknown, and one that cannot be written is left out and said in the file's printed summary (the hub treats a missing creation time as not kept). In a folder, what is not measured is listed in the summary with its reason and count (`hidden`, `not_a_media_suffix:.mkv`, `subfolder`, `dangling_link`, `not_a_regular_file`, `unreadable`; the first 20 named); a folder that cannot be listed is the refusal `folder_unreadable`, and when nothing is left to measure the run is refused `no_media` (exit 2, nothing written). Everything printed is ASCII JSON (`ensure_ascii`), so no console encoding can fail on a name; the facts file is always UTF-8. On Windows ffprobe (and an `AAR_FFPROBE` given as a name) is looked for only in absolute `PATH` folders as `<name>.exe`, never in the current folder, which `shutil.which` searches first there, so a program left in a media folder the command runs from is never run; an `AAR_FFPROBE` relative path is refused. Ctrl+C stops the run: the file being measured and every later one are listed `interrupted`, what was measured is written, exit 130. Files are written in the order of their PC paths (case folded), every object with sorted keys, so the same files give the same bytes. The output is written under a temporary name and given its name without replacing anything (`output_exists`): a hard link on POSIX, a rename on Windows (which refuses an existing name), and on a POSIX file system without hard links the name itself created exclusively (`O_EXCL`) and written, so a run racing another can never replace its output (a run killed meanwhile can leave that file short; the hub refuses a cut line); the temporary file is removed on every path. The hub's loader (`aar.drp.mediapool.gate.load_facts`) refuses a facts file that is not a regular file without blocking on it, reads each line with a bound (never more than 1 MiB + 1 into memory, even from a file that keeps growing), refuses a line nested deeper than 16 levels (`MAX_FACTS_DEPTH`, checked without recursion; a line too deep for the JSON parser is the same `bad_facts`, never a `RecursionError`), and reads an error line as "not measured" (recorded for the caller, never facts; an error line of any other shape is `bad_facts`). `facts_from_json` applies the same depth bound.

**The hand-off (`aar.recipes.ccn.library_handoff`).** `CcnLongformParams.library` (`LibraryParam`, strict, `extra="forbid"`): `folder` (the library), `seed` (a `.db`), `facts`, `templates` (at most 8 `.db`), `user`, `label` (how the owner knows the library in the Project Manager; default the folder's name), `seed_resolution` (`WxH`), `allow_unopened_operations` and `allow_unverified_media` (both default false). The paths are checked by their text at the boundary (absolute, no `.`, `..` or empty component, no control character, at most 1,024 characters, lexically under `AAR_MEDIA_ROOT` when set), never by what they are: the params are re-validated on every step, and a library gone or moved must not fail the run's other steps. When the export step uses them, each must lead (`realpath`) inside the media root's `realpath` (`path_outside_media_root`). The export step, after the FCPXML is exported and before the notes are written, calls `aar.plan.export.library.export_library` (the one implementation of `aar plan export --format library`) with the run's plan, profile, media map, transcript and laughs, the library snapshots in `<AAR_WORK_DIR>/aar-library-snapshots` (never the system temporary folder). The project folder is named `<show> - <timeline> r<round>` (`safe_name`), `-2`... up to 20 when the name is taken (a retry or a reopen in the same round). Any refusal is a record `{"status": "refused", "error": {code, message, hint}}`: the step still publishes the FCPXML, review video and notes exactly as before, and its result carries the record as `library_handoff` and a warning `library_<code>` under `warnings`.

**One guarded region.** Everything the library route does in the export step runs inside one `try` (`aar.recipes.ccn.steps.library_route`): the stop check, reading the run's plan, profile, transcript and laughs, every path check and file read of the params (the facts file, the seed, the templates), the snapshot folder, the export, storing the library export report, the record, the notes' library section (`handoff.library_lines`) and a JSON check of the record. No `Exception` leaves it, a `StepFailure` included: anything that is not the export's typed refusal becomes the refusal `library_failed`, whose message names the stage, the error's type and message (`safe_str`: an exception whose own text fails is still named by its type) and, when the project was already placed, its folder ("not recorded, so its saves are not picked up"). The guard's own fallback uses plain string operations only, and fixed text naming both errors' types if even that fails. The export step reads only the route's finished, plain results (`LibraryRoute`: record, notes lines, warnings, artifacts), so nothing it does with them can fail for the library. A test runs the real export step again with a failure injected at each of the 42 calls the route's own code makes (enumerated by tracing a dry run, so a call added later is injected too) and checks that the FCPXML, video and notes are published each time; another checks that the export step's own calls are the same with and without a library, so a library call added outside the guard fails it. `KeyboardInterrupt` and `SystemExit` (the worker stopping: `StepInterrupted` is a `KeyboardInterrupt`) are deliberately not caught: the step records no result, its claim lapses and the step is claimed and run again from the start, FCPXML included; a project the interrupted attempt had already placed stays in the library unrecorded, and the re-run places the cut under the next free name (`-2`). A facts file that cannot be read is `facts_unreadable` or `bad_facts`; a `facts_missing` refusal names the files the facts file lists as not measured, with their errors. A placed record holds the library, label, user, the project folder's path below the library (`parts`), the project id and name, the timeline, the plan artifact (`plan_sha256`), the SHA-256 of the placed `Project.db`, the operations not yet opened, the media not verified, the count of plan details not carried, and the library export report as an artifact (`report`). The notes gain one section: placed, "OR OPEN IT AS A LIBRARY PROJECT (NEW ROUTE, STILL BEING CONFIRMED)" (which library, user, project and timeline; edit and save, "Saving is all that is needed"; the FCPXML stays the dependable route; the unopened operations and unverified media named); refused, "LIBRARY PROJECT: NOT WRITTEN" with the message, code and hint, and that the FCPXML is unaffected. Every value is one quoted line.

**What a ccn cut can be today.** The `ccn` profile puts a 2-frame "Cross Fade 0 dB" on every join that is not continuous (`rules.audio-crossfade.require_on_cuts`); since S25e the library writer writes them (below), so a multi-range cut is placed too (before, it was refused `unsupported_plan_feature` and went by FCPXML only). And until the owner has opened the staging projects, every real cut needs both opt-ins (`add_media` is not yet opened; the show's media are usually outside a verified kind's envelope). Found while building this: `export_library` compared a plan source's `start_timecode` (frames) with the facts' timecode text, so every plan that states a start (every stub-made plan) was refused `facts_mismatch`; it now compares frames at the source's timecode rate.

**The pickup (`aar.recipes.library_returns.scan_library_returns`).** The cold worker runs it after the `.drt` sweep, once a minute, in its own `try` (a failure is logged, never stops the worker). It reads only runner-written `recipe.result` events whose `library_handoff` is placed with a hash, validated again (`Handoff`), and acts only while the hand-off's review is open: the run neither done nor cancelled, the hand-off's round the current one, its export op done (not superseded by a reopen or a rollback), and no decision on a gate op of that round. For each: the library folder must still lead (`realpath`) inside the media root, and is then opened from the media root's descriptor one component of that resolved path at a time with `O_NOFOLLOW | O_DIRECTORY`, so a link swapped in after the check is refused (`path_refused`, cause `library_relinked`) instead of followed out of the root; the project folder is opened from the library's descriptor the same way (a link anywhere below the library is `path_refused`, classified by `lstat` since Linux answers `ENOTDIR` for a no-follow directory open of a link); a journal or WAL beside `Project.db` is `busy`; a file over 256 MiB is `too_large` before it is read; a file changed less than 2 s ago waits silently for a later sweep (or counts as settled once this worker has seen its identity unchanged for 2 s, for a share whose clock runs ahead), and one this worker has found not settled in 10 sweeps in a row (`Limits.busy_after`: a file rewritten all the time) is reported `busy` (cause `never_settles`; the count is the worker process's own and starts again when the file settles or the worker restarts); then `copy_settled` copies it, by descriptor relative to the project folder, to `<AAR_WORK_DIR>/aar-library-snapshots/pickup/` (the reader refuses to take its own snapshot into the folder of the file it reads, so the pickup's copies sit one folder below the reader's), and a change during the copy or a journal after it is `busy`. A copy whose SHA-256 is that of the newest state recorded for the hand-off (the placed file's, or since S25e the newest return's) is unchanged (nothing); one already reported as a content condition is skipped without being read again (the S25e rule below). The copy is read with `read_timeline(..., project_id=recorded id)` (new: `project_mismatch` refuses a file of any other project before its timeline is read, so a different project saved under the same folder name is `project_replaced`, never imported); no timeline of the recorded name (or several) is `timeline_missing`; a damaged or unreadable file `damaged`. Then the saved `Project.db` is stored as an artifact (`project_db`, role `returned-library-project`) and `desktop_returns.record_import` (factored out of the `.drt` pickup, behaviour unchanged) imports it against the plan it was written from and journals the same `recipe.timeline_return` with `needs_review`, plan, diff, `not_carried`, `limits`, plus `source: "library_save"`, the hand-off's op, library, project folder, project id and timeline. The idempotency key is the project, run, round, plan, hand-off op, the state the save follows (S25e) and the snapshot hash: a second save is a second return, an unchanged file none, and two workers record one (the one that finds the other's record inside its transaction counts the save as repeated, not returned).

**Conditions** are `recipe.library_pickup` events (runner, global key): `library_missing`, `not_a_library`, `project_missing` (deleted or renamed), `path_refused`, `path_outside_media_root`, `busy`, `unsupported_platform` (no POSIX no-follow descriptors) and `pickup_failed` (an `OSError`, `ValueError` or `ExportError` of the hub's own) once per cause between two returns of the hand-off (every place a condition is raised names a fixed `cause`, recorded in the event and its key: a link below the library and a `Project.db` that is not a regular file are two `path_refused` events, a journal beside the file and a file that never settles two `busy` ones; `pickup_failed`'s cause is the error's type); `project_replaced`, `damaged`, `timeline_missing` and `too_large` once per content hash. Each has a message and a fix hint and shows in `recipe_status` as `library_pickup` (the newest 20); a later sweep looks again (a file whose content gave a condition is not read again). Returns show where `.drt` returns show: `recipe_status`'s `returned_edits` (CLI `aar recipe status`, MCP `recipe_status`), labelled by `source`; the console shows no `.drt` return today, so it shows none of these either (the review card shows the notes, which name the project).

**Bounds per sweep** (`Limits`): 20 open hand-offs checked, 1 GiB copied (a copy refused after it was made, because the file changed or a journal appeared, counts its bytes too), 60 s (checked between projects and handed to the reader as `stop_at`), 256 MiB per project file; a project larger than the bytes left waits; the order the hand-offs are taken in turns every minute (`now // 60` modulo their number), so one large or slow project cannot keep the others waiting for good. At the start of each sweep, snapshots older than an hour in the snapshot folder and its `pickup` folder (`.aar-pickup-*`, the reader's `.aar-library-*`: a killed worker's) are removed; anything else there is named in the sweep's result, never removed.

**Verified** (synthetic seed, facts and library; tests/hub): through the recipe runner, a one-range cut is placed beside its FCPXML, the notes name it, nothing is returned before a save, a 12-frame tail trim comes back as `trimmed` (tail 12), the same file again stores nothing, a save that cuts 60 frames from the middle comes back as `split` into the two pieces, and one that swaps them as the pieces swapped, each a return with its own `Project.db`; a three-range cut (crossfades) is refused with the FCPXML intact; the opt-ins off give `media_refused`, then `operation_not_opened`, in the notes. At sweep time: a project renamed away, a journal, another project under the folder name, a renamed timeline, a damaged file, a file over the bound, a file written during the copy, a link below the library, no `Users` folder, the library gone, the library path a link out of the media root, a read-only library (still returned), the review decided, the byte, time and project bounds, a save not settled yet, stale snapshots swept, no POSIX descriptors; each a typed condition once, no snapshot left. A fuzz of 60 damaged saves (bytes overwritten, cut short, grown, pages swapped) gives only returns or content conditions. At export time (unit): the library missing, not a library, read-only, a link out of the media root; the facts missing, malformed, of other files, error lines only, a FIFO; the seed missing or not SQLite; each a typed refusal and nothing placed. Params: 28 path tricks refused (a folder beside the media root whose name starts with the root's among them) and a 3,000-case fuzz that only ever refuses with a validation error. The facts command on media made with ffmpeg: parses with the hub's model, a bad file listed, the caps, the same bytes on every run, read-only, standard library only under `python -S`. #### Transitions and the latest save (S25e)

S25e makes real cuts placeable and the pickup faithful: the library writer writes the sound crossfades the `ccn` profile puts on every join, and the newest save of a hand-off is always what the hub has on record.

**What a transition is in a library** (checked on the two private 21.1 saves, 2026-11-25). An `Sm2TiItem` row of type `Sm2TiTransition` with an `Items` join row on its track, like a clip. It names no media (`MediaRef`, `In` and every media column NULL) and its id occurs nowhere else in the project (all 920, every table, every blob layer; all 920 are in one of the two saves, the other holds none, so nothing about transitions is shown across two projects): its neighbours' rows hold nothing about it, and it holds nothing about them. In the track's `Items` vector it sits between the clip that ends on its cut and the clip that starts there, in record order; at an equal start (a transition starting on the cut) the transition comes first (all 5 such). Every one of the 920 sits between two clips: none is at a clip's head or tail, so the saves hold no fade written as a transition. Kinds: sound "Cross Fade +3DB" 850, "Cross Fade 0DB" 4, picture "Smooth Cut" 66; no dissolve. All sit on 29.97 timelines.

**Field map** (`aar.drp.items.transitions`; P placed, D derived, I identity, L later-edit state, C copied from a template, each a constant on every sound transition).

| column | class | rule |
|---|---|---|
| `Start` | P | the cut minus the frames before it, counted from frame 0 like a clip's; centred, Resolve puts `(length + 1) // 2` frames before the cut (an odd length's extra frame before it: all 3 plain odd ones) |
| `Duration` | P | the length |
| `Sm2TiTrack_id`, join row | P | the sound track; `DbIndex` its place in record order (above) |
| `AlignmentType`, `Position` | D | 2 centred (always equal to each other) |
| `PrettyType` | D | Resolve's stored name of the kind: "Cross Fade 0 dB" -> `Cross Fade 0DB`, "Cross Fade +3 dB" -> `Cross Fade +3DB`. The gain law is here and nowhere else: a transition authored from a template of the other kind equals Resolve's on every field |
| `Sm2TiItem_id` | I | fresh |
| `FieldsBlob` #1 (`#1.#21`, the record start) | L | on 520 of the 854 sound transitions, never on the other 334: left out, as on a transition Resolve has just made (excluded by the gate, tag `history`) |
| `FieldsBlob` #2 | C | qCompress of a 44-byte value, the same 18 bytes on all 854 (`SOUND_FIELD`); a template holding other bytes (a damaged zlib stream can inflate to the same value) or another framing than version 2 plain is refused |
| every other column | C | `Name` "Transition", the flags and lock ids as on every sound transition (`TRANSITION_CONSTANTS`, equal to the verifier's own table, a test compares them); a template with a media column, effects or any column outside `ITEM_COLUMNS` is refused, and one whose copied column holds another value (`RenderTextEnabled` `3\|0000000000000000`, say) is refused `bad_template` naming the column when it is read (S25e-f2) |

**Supported** (refused otherwise, `ItemError` `unsupported_item`, `bad_placement` or `bad_template`): sound, "Cross Fade 0 dB" and "Cross Fade +3 dB", centred on a join of two clips, 2 to 16 frames (the lengths compared: 2, 4 of +3 dB; 3, 16 of 0 dB), on a 29.97 timeline. Of the 854 sound transitions 844 are centred and ten are not: five start on the cut and five end on it, each five one cut repeated on the same five audio tracks (one in each of five timelines), so each alignment is one example seen five times. Not supported: picture transitions (Smooth Cut holds a value no rule derives in `FieldsBlob` #2, one per item, and its parameters in `EffectFiltersBA`; no dissolve was seen), starting on the cut (`AlignmentType` 1: its 5 examples sit next to clips stored in Resolve's `N|hex` form) and ending on it (3: its 5 examples are `N|hex` themselves), other kinds, lengths and rates, and fades (none seen).

**What a transition needs of its neighbours** (`aar.drp.libwrite.cut.author_cut`, refusal `bad_transition`, never shortened): the outgoing entry's sound ends exactly where exactly one other entry's sound starts (not a gap, not the timeline's end), neither entry is a split edit, the frames before the cut fit in the outgoing clip and those after it in the incoming clip, and the media it plays exist: `before` frames of the incoming clip's file ahead of its in point and `after` frames of the outgoing clip's sound past its out point (`ceil(Duration × rate / SampleRate)` of its first audio track, the item writer's bound); and the two crossfades on one clip fit in it together, the frames after the cut of the one into it plus those before the cut of the one out of it (`transitions_overlap`, the plan export's code for the same rule, S25e-f2; before, each side was checked against its clip alone, so a 10-frame clip between two 16-frame crossfades was placed with their windows overlapping by 6 frames). The verifier checks the same with the same code, so the rule does not depend on which door a cut comes in by. **What it changes in them: nothing.** Their ranges still abut at the cut (the transition overlaps them, it does not lengthen them), and their rows are exactly what the item writer makes without knowing of it (below).

**The gate** (`aar.drp.items.transition_gate`, in `tests/drp/test_items_gate.py` under `AAR_ITEM_PROJECTS`; `scripts/items_scoreboard.py [--other-kind]` prints it). Each transition's neighbours are found in its track's `Items` vector and must abut: their meeting frame is the cut; the transition is authored from that cut, its length, alignment, kind name, track and index alone (so `Start` is computed, not copied) with another real transition as the template (never itself: identity by project path and row id, each project read once), and compared with Resolve's rows by the media pool's total comparison. On the two saves: **112 transitions, 7,280 fields, all equal** (Cross Fade +3 dB centred 108: 2 frames 101, 4 frames 7; Cross Fade 0 dB centred 4: 3 frames 1, 16 frames 3; 6 with `#1.#21`, excluded), with a template of the same kind and, in a second run, of the other kind (all 112). The two runs use only four distinct templates, all plain, so the rule that leaves `#1.#21` out of a template is exercised by unit tests only. Not compared, by reason: 734 `N|hex` whole frames (as for items; the 729 of them that are centred, read with their fractions, follow the same placement rule, `Start` = the neighbours' meeting point minus `(length + 1) // 2`, at lengths 2, 3 and 4 frames: 5, 386 and 338 of them, as the S25e validation also found independently), 66 picture (Smooth Cut), 5 starting on the cut, 3 next to a clip not in whole frames. The neighbours of the compared transitions, authored by the item writer: 13 of a supported item shape, 876 fields, all equal; the other 111 play compound or multicam clips or are `N|hex` (not compared). Media margins could be measured on 3 transitions only (the others' neighbours play compound clips or are `N|hex`): the smallest margin ahead of the incoming clip's in point is 143 frames, past the outgoing clip's out point 377; no real transition reads past its neighbours' media, which shows the evidence never tested the bound, so the writer refuses rather than relies on Resolve's behaviour there.

**Writing** (`aar.drp.libwrite`): `CutTransition(after, frames, name, alignment)` entries beside the `Cut` list (`Authored.transitions`); the template is the first plain sound transition of the templates or the seed (`pick_item_templates`; none is `no_template`, an `item_refused` at export). The seed's timeline may now hold plain sound crossfades too (removed with its items; one with later-edit state is `bad_seed`). Operation `add_sound_transitions` (not yet opened). The read-back finds each as a `transition` item at its record range. **The verifier** (`verify.TRANSITION_RULES`, one rule per column of `ITEM_COLUMNS`, pinned by a test with the writer's list; it uses no authoring code): from the `Cut` and `CutTransition` entries it recomputes each transition's join (as above, the overlap rule included), `Start` with its own centring rule, `Duration`, `AlignmentType` and `Position` 2, `PrettyType` from its own name table, `FieldsBlob` byte for byte (version 2, plain, one field #2 holding `SOUND_FIELD`, which must inflate to the 44-byte value), its `DbIndex` in the merged order of its track, a fresh id, every constant column, and the media the transition plays from the clips' rows as written; the count of items is the clips' plus the transitions'. A test plants a change in each column of a written transition and in its place, length, kind and value: each is `self_check_failed` before placement.

**Export.** `aar plan export --format library` takes the layout's transitions (`Layout.transitions`, the FCPXML export's own: cut, length, `head_part`, alignment, form) and writes each audio-only crossfade on V1's joins (`form` `split`) whose kind, length and rate are supported, centred, when the layout's `head_part` equals Resolve's centring (`frames // 2` against `(frames + 1) // 2`: an odd length is refused, the two disagree); everything else is refused with the reason as its `feature`, with the old vocabulary (`unsupported_plan_feature`): a picture transition (join, head, outro), another kind, length or rate, a crossfade the layout aligns to start or end on the cut (its handles do not hold a centred one), a transition the layout could not place on a join (at a gap, off V1: the import would drop it), and fades (`head.audio_fade_frames`, `end_fade_frames`). The layout's `audio_transition_type` note is not listed for a crossfade the project carries with its own kind. The report's `exported` counts `sound_transitions`. A crossfade of 0 frames is a hard cut everywhere (the layout skips it, as do the render's compiler and the import), so no transition is written for it and it is listed under `not_carried` (`zero_length_transition`, S25e-f2; before, it vanished without a word), not refused: the export refuses only what would change the cut if left out, and lists under `not_carried` the plan entries the project does not hold that change nothing. The layout itself is unchanged, so the FCPXML export's output is too. The export's other transition rules and the writer's: the writer enforces each itself (kind, length, rate, centred, one per join, on a join of two clips, the handles, the overlap) except one, the odd length: the export refuses an odd centred length because the layout's `head_part` (`frames // 2`) and Resolve's centring disagree, while the writer writes an odd length with Resolve's own centring (the gate compared one 3-frame crossfade).

**The import** (`aar.plan.timeline_import`). A `TimelineFile` says what it was read from (`kind` `drt` or `library`). For a library project (`sound_transitions=True`, passed by the export's self-check, the pickup and `aar plan import-timeline`) each sound transition item on A1 is matched with the edited plan's audio-only crossfades on V1's joins: one containing the cut with the plan's length is that crossfade; any other is `transition_added`; a crossfade with none is `transition_missing`; and the diff's `audio_transitions` limit says what this cannot tell (S25e-f2, also in docs/DESKTOP-HANDOFF.md): a crossfade the owner moves along its cut while it still contains the cut reads as unchanged (the plan has no field for its alignment), one made longer or shorter reads as the plan's removed and another added, and a change of kind is not read. For a `.drt` nothing changes: the FCPXML route writes those crossfades as split edits with fades, so sound transitions stay uncompared there.

**The latest save always wins** (owner, 2026-11-25; `aar.recipes.library_returns`). The pickup records a return whenever the settled file differs from the **newest state the hub has recorded for that hand-off**: the placed project while nothing has been returned, else the newest return (its `snapshot_sha256`, the saved file's artifact id for older returns). So an edit undone and saved is a return (its diff what the file now holds; "unchanged" when it is back to the plan), A, B, A, B is four returns, and a save identical to the newest record records nothing. The idempotency key names the state the save follows (`placed`, or `return:<event id>`) and the snapshot hash, so the same save seen by two workers or by a restarted one is one return while the same content saved again after another return is a new one; each return carries `follows`. The recording transaction checks, after the key, that the state it follows is still the newest; when another worker recorded a different save meanwhile it records nothing (`deferred`) and the next sweep compares the file with the newest record (a save already replaced on disk by a later one is then not recorded: the later one wins). Content conditions are still recorded once per content hash and such content is not read again; place conditions once per cause between two returns; `.drt` returns are unchanged.

#### Lessons from review feedback (S23)

The owner reviews each cut in the console: approve or reject with a reason, and notes pinned to timeline frames. That feedback drives the retry loop inside one recipe run, and nothing carries it further. A **lesson** does: a one-line editing rule that a person accepted, which the ccn cut guide prints for the agent doing the cut in later runs (`aar.hub.lessons`, S23a).

**Scopes and precedence.** A lesson applies to every show (`global`), to one client (`client:<name>`, matched against the brief's `rule_profile`) or to one hub project (`project:<prj_id>`). `parse_scope` checks the syntax only: the client name with the hub's rule-profile name pattern (`NAME_RE`, so never a path), the project id with the hub's id check. The writers also check the target: a client must be a loadable built-in profile (through the hub's built-in-name-only loader), a project must be registered. Where two lessons disagree, the narrower one wins: the project over the client, the client over global. The guide says so; nothing in code merges or ranks them.

**Only a person makes a lesson count.** An agent may propose one (`propose`, by a human or an agent, with its `why` and optionally the `(project, review)` it was drawn from, both checked to exist), but accepting (the person may change the text and the scope; the lesson keeps the proposal as well), dropping, retiring and adding a rule by hand (accepted at once) are human-only (`require_human`). The guide is an instruction to the next agent, so an agent that could accept its own proposal could write instructions into every later cut. The fold enforces the same rules again, so an event appended straight to the log cannot get round the writers: a human-only event by anyone else, a proposal by a node or the runner, a lesson event with a `project_id`, a bad transition (deciding twice, retiring a proposal or a dropped lesson, anything after a retire, an event for an unknown lesson), a second event that creates an existing id, a payload that fails validation, and an event whose `ts` is not a timestamp (`is_ts`) or whose actor id is over 128 characters (the page and the CLI show both, so they stay bounded) are each skipped and listed, never applied. There is no CLI or MCP write path: `aar hub lessons list [--state S] [--scope SCOPE]` and `aar hub lessons show ID` only read (the database opened read-only), because a CLI actor is self-declared and would be a way round the console's human identity, and agents get no lesson tools; they meet lessons only in the guide.

**Events and bounds.** Lessons are global events (`project_id` null, like `control.stopped` and `node.enrolled`); the source project and review are in the payload. `lesson.proposed` (`lesson_id`, `text`, `scope`, `why`, `source`), `lesson.added` and `lesson.accepted` (`lesson_id`, `text`, `scope`), `lesson.dropped` and `lesson.retired` (`lesson_id`, `reason`). The states: `proposed` becomes `accepted` or `dropped`; `accepted` (by accept or add) becomes `retired`; `dropped` and `retired` are final. Ids are `les_` and 16 hex digits. Text is one line: stripped, every whitespace run (newlines included) one space, 1-500 characters after normalizing, and no character a reader cannot see (`hidden_character`): control, format (zero-width, bidirectional and tag characters, the soft hyphen, the byte order mark), surrogate, private-use and unassigned code points; every `Default_Ignorable_Code_Point` (the variation selectors, the combining grapheme joiner, the Hangul fillers U+115F, U+1160, U+3164 and U+FFA0, the Khmer inherent vowels U+17B4 and U+17B5 among them; Python's `unicodedata` has no lookup for the property, so the module embeds its ranges from `DerivedCoreProperties.txt` of Unicode 15.0.0); and the other characters that draw as blank space without being whitespace: the braille pattern blank U+2800, the Khitan small script filler U+16FE4 and the musical null notehead U+1D159. Whitespace is collapsed to one space, never refused. A person must see everything a lesson says before it reaches a guide: invisible characters could carry an instruction past them, and a lone surrogate would break the page and the guide. `why` 0-1000 and a drop or retire reason 0-500 characters, normalized and checked the same way; the fold checks the same, and the ids in a scope or a source too. At most 200 proposals wait at once (`too_many_proposals`), and a scope holds at most 50 accepted lessons (`too_many_lessons`, whose fix hint says to retire one). Each writer reads, checks and appends inside one `BEGIN IMMEDIATE` transaction, and takes an optional idempotency key as the review writers do: the same request replays (returning the lesson as it is now), another request under the key is refused. Refusals are `WriteError`s with a fix hint: `invalid_input`, `unknown_lesson`, `illegal_transition`, `unknown_profile`, `unknown_project`, `unknown_review`, `actor_not_allowed`, `too_many_proposals`, `too_many_lessons`, `idempotency_conflict` (a non-human's human-only write is `HumanRequired`).

**In the guide.** The `guide` step reads `lessons_for_guide(log, project_id=<the run's project>, client=<the brief's rule_profile>)`; without a brief, only global and project lessons apply. Accepted lessons only, each scope in acceptance order, at most 50 per scope on read too (the first 50, so a later flood cannot push an established lesson out). They print at the end of section 3, `House rules (the ccn profile)`, before section 4, under `### Lessons from past reviews`, grouped `Global`, ``Client `<name>` `` and `This project`; an empty group is left out, and no section is renumbered (later sections refer to each other by number). With no lesson that applies, the guide is byte-identical to one built before lessons existed. The guide is built once per run (a rejection goes back to `cut`, never to `guide`), so a lesson accepted while a run is past its guide step applies from the next run.

**In the console.** `/lessons`, after Reviews in the nav, which shows the number of proposals waiting on every page (`Lessons (3)`): that is how the owner learns that proposals exist. The page has the proposals (oldest first, at most 25 at once, since each card carries a scope select listing every project), each with its why, its source review linked, who proposed it and when, and a form with the text (editable), "Applies to" (global, each built-in profile, each registered project, labelled in words, a project by its name and its id (two names can look the same), and preselected to the suggestion; a suggestion that is no longer a choice stays selected and marked, so accepting never widens it quietly) and an optional reason, to accept or drop; the accepted lessons grouped global, each client, each project, each with a retire form; and a form to add one. The writes are `POST /lessons/{id}/decide`, `/lessons/{id}/retire` and `/lessons/add` through the console's one write path (Origin, identity, CSRF token, idempotency key); the form's text and scope go through the store's validators. Without an identity the page is read-only. Every console page renders its values through `esc` and `url`, which replace a lone surrogate with U+FFFD: UTF-8 cannot encode one, and stored text can hold one (a project name registered from a CLI argument byte that is not UTF-8 made `/control` and `/lessons` answer 500). Refusing them where text enters the hub is S23-f2.

**The proposer (S23b).** After a person decides a review, a cheap model drafts up to 3 lessons from it, and they wait in the console like any other proposal: a person accepts, rescopes or drops each one, and nothing a model writes reaches a guide until a person accepts it. `aar hub lessons propose --db DB [--limit N] [--model M] [--actor agent:ID]` runs one bounded pass (`aar.hub.lessons_proposer`); on the hub, `aar-hub-lessons.timer` runs it 10 minutes after boot and 10 minutes after each pass (`deploy/linux`). The proposer only proposes: its lesson writes go through `lessons.propose` as an agent (`agent:lessons-proposer` by default; any other kind is refused). Its other writes are its own bookkeeping, global events that the lessons fold never reads: `lessons.drafted` (a review's marker), `lessons.draft_failed` (a charged attempt) and `lessons.draft_strike` (an uncharged strike).

- *What the model gets, and through what.* The local model gateway (CLIProxyAPI, OpenAI-compatible `POST /v1/chat/completions` at `AAR_LLM_BASE_URL`, default `http://127.0.0.1:8317`, with the key in `AAR_LLM_API_KEY`; `aar.llm.gateway` keeps the key out of every error, log line and repr, raw and URL-encoded the ways Python writes it (`quote(key, safe="")`, `quote(key)`, `quote_plus(key)`, each `%XX` in either case), refuses a base URL that carries it, pins requests to the base origin, follows no redirect and caps the reply at 1 MiB). One chat per review (`aar.hub.lesson_drafts`): a system message with the rules (at most 3 durable editing preferences for future cuts, not instructions about this cut; one imperative sentence each; a suggested scope, narrower when unsure; JSON only), and the review as a JSON block marked as data: the title, the decision, the reason, the notes a person wrote with their timecodes (notes an agent added are left out), the show (the project's registered name), the client (the `rule_profile` every typed brief of the project shares, when it is a built-in profile; otherwise none, and only the global and project scopes are offered), and the lessons already accepted or waiting in global, that client and that project, labelled by scope so the model does not repeat them (never another project's or client's). The user message is at most 24,000 characters as sent: JSON-escaped and indented, each backtick counted as the six characters of `\u0060`. The review's own fields always fit; notes and existing lessons share the rest, each cut at its end behind a "(N more not shown)" marker.
- *The model.* `gpt-6-luna` by default; `AAR_LESSONS_MODEL` (in the unit's `lessons.env`) or `--model` overrides it. The reply is read strictly: a JSON object (bare or in one fenced block) with a `lessons` list; each draft's text and why go through the store's own validator (`clean_line`), and a draft with an unknown scope, too long, empty, or holding a character a reader cannot see is dropped and reported. Scopes map `global` to `global`, `client` to `client:<client>` and `project` to `project:<project_id>`; each draft is recorded with the model's why and the review as its source, under the idempotency key `lessons:proposal:<project_id>:<review_id>:<n>`, and a draft the store refuses is reported while the others are recorded.
- *Once per review.* Candidates are the reviews with a `review.decided` event that are neither done nor given up, the fewest strikes first, then the fewest charged attempts, then the oldest decision (so a review that keeps failing goes behind the others instead of holding them back), each confirmed with `reviews.get_review` (open, withdrawn and fold-rejected decisions are skipped). A review is done once the marker `lessons.drafted` exists (global, `{project_id, review_id, proposed, model, recovered}`, key `lessons:drafted:<project_id>:<review_id>`), written after the proposals: a later pass skips it without a model call. A pass that died between the proposals and the marker leaves proposals whose source is the review; the next pass writes the marker (`recovered`, model null) without calling the model again. Right before it records a reply, a pass checks the marker and the review's proposals again: a review another pass recorded meanwhile is `recovered` and the reply is dropped. A reply whose every draft the store refused only because its backlog filled while the model answered (`too_many_proposals`) gets no marker: the review is `deferred` and stays a candidate.
- *Failures.* A setup failure stops the pass at once and charges nothing, so the next pass retries: `not_configured`, `origin`, `redirect`, `network` (the gateway cannot be reached), HTTP 401, 403, 404 and 429 (429 and 503 are retried twice first), and a model the gateway does not serve (`unknown_model`: the gateway answers a chat for an unknown model with HTTP 400, so before its first chat a pass reads `GET /v1/models`). Every other failure of a review's chat is ambiguous, the review's own or the setup's: `timeout`, `too-large`, `bad-response`, 5xx, every other 4xx (400, 408, 413 and 422 among them) and a reply that is not the lessons JSON (`bad-output`). The pass carries on with the next review, and stops after 2 in a row. An ambiguous failure is charged to its review (`lessons.draft_failed`, `{project_id, review_id, code, attempt}`, key `lessons:draft-failed:<project_id>:<review_id>:<attempt>`) when any review of the same pass, before or after it, is drafted by the model (a pass has one model): a success anywhere in the pass shows the setup works. Otherwise it is an uncharged strike (`lessons.draft_strike`, `{project_id, review_id, code, strike}`, key `lessons:draft-strike:<project_id>:<review_id>:<strike>`). A review is given up after 3 charged attempts or 144 strikes: about a day of passes 10 minutes apart, so a review that fails alone, with no other review to show whose fault it is, cannot retry forever. Each report counts the given-up reviews and shows each failure's attempts and strikes. Markers, attempts and strikes are counted by their keys, whatever event holds them, so no event can make a review retry forever. An outage of the gateway or the model that fails every chat (the gateway's upstream answering 5xx or timing out, every chat HTTP 400) charges no review: each pass stops after 2 strikes and exits 1, and the strikes go to the waiting reviews with the fewest. So an outage of about 144 passes (a day at 10 minutes) gives up the reviews waiting through it: with one or two waiting, after those 144 passes; with more, the strikes spread over them, and giving them all up takes about 72 passes per waiting review. Nothing reopens a given-up review yet, so its lessons are never drafted (PLAN.md S23-f4). A gateway that cannot be reached at all, a wrong key and a rate limit are setup failures: they record nothing and give nothing up, however long they last. The command exits 0 when the pass ran (with nothing to do, another pass holding the lock, or a full backlog too), 1 when it failed (a setup failure or 2 failures in a row stopped it, or it recorded a strike), 2 when it could not start (no key, a refused gateway URL, a bad argument, no database).
- *One pass at a time.* A pass holds a non-blocking `fcntl.flock` on `<db>.lessons-propose.lock`, a file beside the database (mode 0600, left in place), for its whole run. A pass that finds it held does nothing, reports `busy` and exits 0; one that cannot take it stops with `lock_unavailable` and exits 1, with a hint at what is at fault: a lock file that is there but cannot be opened (named, with its owner and mode to check: it must be a regular file, not a symlink, that the service user can write), a folder where none can be made, or a file system without flock. Without `fcntl` (Windows) a pass runs without the lock.
- *Bounds.* At most `--limit` chats per pass (1-50, default 5), failed ones included, each with at most 4,000 reply tokens; at most 3 drafts per review; before each chat the pass stops if the proposals waiting plus 3 would pass the store's 200 (a full backlog is reported, not an error, and drafting resumes once a person decides some); at most 3 charged attempts and 144 strikes per review. In time: the gateway client bounds each socket operation by its 60 s timeout, and a reply body by a deadline 60 s after each try starts, but it reads the status line and the headers through `http.client`, bounded only per read, and no thread enforces a total. On the hub, the unit's `TimeoutStartSec=30min` is the outer bound for a whole pass. A pass run by hand has none: a server that sends its status line or headers a byte at a time can keep it waiting for as long as it goes on.

## 5. Safety rules (enforced in code, not just written here)

- Before every hot op, the node checks that the expected project is the one open. It refuses to switch project or database while a human is active, unless a human forces it from the console.
- Switching databases, creating or restoring cloud projects, and writing to a production project all need a human approval token, which is recorded in the event log.
- **Approvals in node jobs (F15 and the branch guard).** Every op of a job runs as the job's agent, behind the branch guard, in every project. An op the guard refuses (a human's timeline, or state every timeline shares) runs only with a `project.write` approval on target `<project id>#op:<op>#step:<n>`, consumed for that one op occurrence. A mutating op against a production project also needs the job's plain `project.write` approval on the project id, consumed once per job and then good for the job's later writes. The one exception is the overridden op itself: its own override counts for it, so one human grant covers that single op, but it licenses nothing after it. Every consume is audited on the hub as `agent:<agent id>#<job id>`, and a stored approval is trusted only when the hub shows that consume for that exact scope and target.
- **Render-job ownership.** The node's local job store is its trust root for render-job ownership: a job deletes or adopts only the render job whose Resolve `JobId` its own journal recorded there.
- Deliver settings are recorded before a render preset loads and restored afterwards. The recorded settings include the output size (`FormatWidth`/`FormatHeight`) and quality, so a render that sets its own size never leaves the human's size changed.
- Never change Input Color Space on BRAW clips, and never sweep a colour space across a whole bin.
- Never connect to the cloud library's database directly.
- DRP writes always go to new files. Originals are never overwritten.
- Real project files used for testing stay in a git-ignored corpus (`corpus/`, or `$AAR_DRP_CORPUS`) and are never committed.

## 6. Risks

| Risk | Mitigation |
| ---- | ---------- |
| DRP edits import but break silently (F6) | Whitelist of writes, sandbox round-trip validation, and a preference for build-and-export |
| A new Resolve version changes the DRP schema | Version-tagged templates, validation for each host version, a tolerant reader |
| The single Resolve instance is a bottleneck (R4) | Broker and batching; the S14 spike; a second machine as fallback |
| Humans and agents fight over the shared instance | Presence guard, leases, agent branch timelines |
| Cloud features need paid libraries and have no API | All cloud work goes through the node; the console replaces Presentations |
| The 60 s MCP cap, hangs and crash reporters | Node-side job runner with a watchdog, not run through the MCP bridge |
| 21.1 scripting needs Studio | The target is Studio only, as the requirement says |

## 7. Decisions (these defaults hold until the owner says otherwise)

1. A standalone app, which Command Center threads use as an MCP server. The alternative is to build it inside Command Center.
2. The hub is tailnet-only for v1. People outside the tailnet will need accounts later.
3. The edit PC's empty Local Database becomes the sandbox for DRP validation and spikes. **This needs approval**, because switching databases closes the open project. Until then, DRP work is offline only.
4. Run the multi-instance spike (S14) on the edit PC. **This needs approval** and an idle window.
5. A GitHub remote. There is none yet, and the PR and Prism gate needs one. Until it exists, slices merge locally into `dev` after independent review. `main` gets only the reviewed `dev` → `main` PR.
6. **Open: a real credential for the console and hub.** In v1, identity is network reachability. Whoever can reach the console acts as its `--operator`, and with `--trust-tailscale-headers` any process on the hub host can claim any Tailscale login over loopback. The MCP server has no auth at all, and with `--agent-writes` any caller can write briefs, recipes, plans, status and facts under any agent id it declares. That is acceptable only while both stay tailnet-only (D2). Before either is reachable from outside the tailnet, it needs a real per-person credential, for example a Tailscale identity checked through the local API or an auth proxy, and the trusted-header mode must go.
