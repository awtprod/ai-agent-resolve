# AI-Agent-Resolve: design

Draft v1, 2026-10-17. Slices and status are tracked in [`PLAN.md`](../PLAN.md).

## 1. What this is

AI-Agent-Resolve is a companion app for DaVinci Resolve Studio, built mainly for AI agents to use. Agents plan, measure, build and check edits. Humans supervise and review, and keep working in Resolve as usual.

It does not reimplement Resolve. Resolve remains the renderer, the timeline of record and the collaboration surface. This app adds the things Resolve lacks for agent work:

- A typed edit-plan layer that is checked against house rules before anything touches Resolve.
- A scheduler in front of the single Resolve instance.
- An offline toolchain for `.drp` files.
- A shared store of projects, events and artifacts that humans and agents both see.
- Recipes that take a job, such as a CCN long-form or a set of shorts, from brief to published files.

## 3. Architecture

```
 agents (Command Center threads, Codex, CLI)            humans
        │ MCP (streamable HTTP) / REST / CLI                │ web console: review, approve, override
        ▼                                                   ▼
 ┌──────────────────────────── aar-hub (tailnet) ─────────────────────────────┐
 │ project registry · append-only event log · work graph                      │
 │   (brief → plan → ops → artifacts → reviews)                               │
 │ leases + presence · review threads at timecode · artifact store (by hash)  │
 │ per-project facts (offsets, gains, traps) · rule profiles · recipe runner  │
 └──────────┬──────────────────────────────────────────────┬──────────────────┘
            │ hot jobs (node pulls)                        │ cold jobs (any host)
            ▼                                              ▼
 ┌──── aar-node (beside each Resolve Studio) ───┐   ┌──── workers ──────────────────┐
 │ session broker: leases, hot-op queue,        │   │ aar.drp: read / diff /        │
 │   context save + restore, presence guard     │   │   modify / create             │
 │ op library: verified ops with traps built in │   │ transcripts, laugh maps,      │
 │ job runner: checkpointed, no 60 s cap        │   │   face tracks, ffmpeg,        │
 │ path map, offline + proxy checks             │   │   captions, thumbnails        │
 └──────────┬───────────────────────────────────┘   └───────────────────────────────┘
            │ DaVinciResolveScript (local)
            ▼
   DaVinci Resolve Studio ─── Blackmagic Cloud library · Presentations · Cloud Store
```

The app is Python 3.11+ throughout, because the Resolve API and all the existing CCN tooling are Python. It is one repo with a single package, `aar`, split into `aar.drp`, `aar.node`, `aar.hub`, `aar.plan` and `aar.recipes`.

Work is either hot or cold:

- **Hot ops** need Resolve's current project or timeline: building, grading, submitting renders, exporting. They always go through the node's broker.
- **Cold ops** need nothing from Resolve: parsing DRPs, transcription, Gemini analysis, ffmpeg, planning and linting. They run in parallel on any host.

## 4. The six requirements

### R1. Read, modify and create `.drp` files

- **Read (S1).** A lossless container reader produces a typed model: project settings, bins, media clips, timelines, tracks, items, and markers where they can be decoded. It keeps the raw text spans so later edits can splice them. It uses a tolerant scanner rather than a stock XML parser, because tags like `ListMgt::LmVersionTable` break those parsers. The version header is exposed. `.drt` is covered fully. `.drb` is best effort because its internals are still unknown.
- **Diff (S2).** A semantic diff of two files shows what an agent or a human changed between versions. Objects are matched by DbId, and every byte the reader does not decode is compared raw and reported as `opaque-changed`. Its gate mode (`aar drp diff --gate`) is S8's post-write check: it passes only when every change is decoded and DbId-matched. The gate cannot see, by construction, changes that leave both the decoded model and the compared residue identical: (a) zstd framing that decompresses to the same bytes; (b) hex letter case inside a blob the reader decodes (`FrameRate`, `Resolution`, `MediaExtents`, `Time`, `Geometry`, `Clip`, marker and settings blobs); (c) whitespace between elements; and (d) XML-equivalent attribute spellings — attribute order, quote style (`'` vs `"`) and entity-versus-literal characters — which the tolerant scanner normalizes away. Limit (d) holds only for the attributes the scanner decodes, the first 4096 of an element. The attributes of an element past that cap are not decoded; they are compared as raw bytes, from the first unread attribute to the end of the start tag, so inside that truncated tail the comparison is **stricter** than in the kept part: quote style, whitespace, entity spelling, attribute order and `/>` versus `></X>` all count as changes. That fails closed (a harmless respelling there is reported, never missed), and the reader's `scan-attributes-truncated` warning already fails the gate for such an element. A repeated attribute resolves last-wins below the cap and **first-wins past it**, because nothing past the cap is decoded: a second `DbId` there is never read, so the semantic "DbId changed" line is not produced and the pair is reported as one opaque change instead. When a `DbId` appears in the unread tail the change detail says so (a byte search for the name; a false hit only adds wording). The `DbAppVer`/`DbPrjVer` stamp is compared by its raw spelling, so a spelling-only change (`17` vs `017`, or non-ASCII digits) fails the gate. A genuine stamp *value* change also **fails** the gate on a real file: the stamp sits in the header comment of every member, including ones the reader does not interpret (`Gallery.xml`, stills), whose bytes are then compared as opaque. Bumping the stamp in only `project.xml`, or only in the members the reader interprets, fails too, but as a `version-mismatch` warning (the members no longer agree and the gate refuses any file read with warnings), not as an opaque change. A file whose stamp lived only in the decoded `project.xml` would pass a stamp change; on real files the failure comes entirely from the raw members' bytes. A project `DbId` change, by contrast, is reported but **passes** the gate — it is a single decoded header field (the project is the file's singleton, paired whatever its DbId) with no opaque collateral, so it is only listed, not failed. Because a passing gate means every change was decoded and DbId-matched, not that the changes were the ones intended, S8 must additionally compare the full change list against its intended edit set before trusting a write.
- **Modify (S8).** Only a whitelist of round-trip-verified edits is allowed:
  - rename
  - relink and path mapping (Windows drive letters to Mac `/Volumes` and back)
  - markers (add, update, delete)

  Each edit is a text-span splice plus a blob re-encode. Anything outside the whitelist is refused. Two edits that were planned are **deferred, not built**:
  - **Metadata.** It cannot be verified. The reader decodes no user-editable clip metadata (comments, keywords, scene, shot, take and camera fields live in `BtMetadataLockableBlob`, which it does not decode), so the post-write gate could not vouch for an edit. A clip's name is a rename.
  - **Fader keyframes.** No keyframe writer exists. `drp_tools` has codecs and format notes only, and its notes leave the tick encoding, the track mapping and the `AdrDatabase` checksum open. The reader does not decode `FLStudioModelBA` either.

  Every write must pass the S2 gate, and its full change list must equal the plan's intended edits. Three rules bound what is edited and what is accepted:
  - **Inputs that read with warnings are refused** (`input-has-warnings`), because the gate can never pass for them. In the 64-file private corpus that is 16 files, all `blob-partial`; the other 48 can be edited.
  - **The round-trip allow-list** (`aar.drp.modify.roundtrip`) is used only to compare a file with Resolve's own re-export of it, never for the writer's output. It accepts exactly **11 opaque lines** that Resolve rewrites on every export: 3 playhead values, 3 pan/tilt preset DbIds, 2 `DbSavedTime` values, 1 project age, 1 save date inside the settings blob, and **1 save stamp in the root bin's fields blob**. The project's `LastModTimeInSecs` is accepted as a decoded header change on top of those. Each rule checks the bytes, not just the name.
  - **Files are labelled `unverified`** (`<out>.aar.json`) until the sandbox round trip exists. The label is a JSON file aar recognises as its own by the stamp it writes: a `tool` of `aar <version>`, a `label` and `status` of `unverified`, and an `output` block naming this file and this label. A `<out>.aar.json` that aar did not write is refused (`foreign-sidecar`) and both files are left untouched; a label aar wrote on Windows is recognised on POSIX when its stamp holds an absolute Windows path (drive, UNC or `\`-rooted); one with a relative Windows path is still refused there, since `sub\out.drp` is also a valid POSIX name. `--force` checks the label when the run starts and again on a snapshot (a hard link, else a copy) taken just before the label is replaced. A label that is not aar's by then is refused, nothing is written, and the snapshot is kept and named in `left_behind` (kind `label-snapshot`). A kept snapshot is renamed to `.<out>.aar.json.<8 chars>.label-snapshot.json`, a name the leftovers pattern never matches, so a later run never lists it as a stale temporary file or in an `orphan-sidecar` remove list. If that rename fails (no space, or a name past the filesystem's limit: the snapshot name is the output's name plus 39 characters), the run's result is unchanged and the snapshot is kept and reported under its temporary name, which a later run does list among the leftovers. A snapshot kept by an older aar (before S8e) still has a temporary-file name (`….tmp.json`) and is still listed among the leftovers; check it against the label before deleting it. This narrows the window but cannot close it, because rename has no compare-and-swap: a label another program writes as a new file between that last check and aar's `os.replace` (microseconds) is still replaced and lost. One written in place into the old label's file shows up in a hard-linked snapshot afterwards, which is then kept rather than deleted.
  - **Placement narrows, but does not close, the no-hard-link race.** The output and its label are written to temporary files, verified, then moved into place (the label first). Without `--force` the move hard-links onto the name — atomic, failing if the name is taken — or, on FAT/exFAT where there are no hard links, claims the name with `O_CREAT|O_EXCL` and `os.replace`s the verified temporary onto its own placeholder (`os.replace`, not `os.rename`, so it also works on Windows exFAT/FAT media, where `os.rename` fails when the destination exists). The `O_CREAT|O_EXCL` claim beats an exclusive creator or a check-then-create writer: once aar holds the name, that writer's create fails. It does **not** beat a plain non-exclusive writer (`open(dest,"wb")`, `cp`, Windows `CREATE_ALWAYS`): that writer opens and truncates aar's placeholder and writes into it, and the `os.replace` then discards those bytes. For that class of writer the window runs from the exclusive create through its close to the replace. On a failed replace aar removes the name only when it is aar's own output (same device and inode, by `lstat`). It deletes nothing else, not even an empty file: an empty file there may be another writer's (created after unlinking the placeholder, or the placeholder truncated and not yet written to), and no identity aar can record tells them apart. **A failed replace therefore leaves an empty file at the name, with no label** (the label is removed again). The same happens on Windows when a sharing violation makes the replace fail. The raised error, and the CLI's JSON (exit 74), name that file in `left_behind` (kind `placeholder`) so an agent can check and delete it. When placing the output fails, aar removes the label it just placed (or, with `--force`, restores the old one). If that cleanup fails too (for example a sharing violation on the label), the placement error is still the one raised, with the cleanup failure attached as a note and the same exit code, and aar's own label left at `<out>.aar.json` is named in `left_behind` (kind `own-label`); the next run reports it as `orphan-sidecar` (`out-exists` if a file is at the output name). When it was the `--force` restore that failed, the old output is still at `--out` and its correct label survives only in the snapshot: that snapshot is kept, never deleted, and named too (kind `label-snapshot`), to be moved back over the `own-label` file. A crash mid-move may leave aar's own partial labelled copy (an empty placeholder or the output), but never a file that was already there.

- **Create (S9).** There are two routes:
  1. Preferred: build the project with the scripting API in a sandbox, then call `ExportProject`. Resolve writes the file, so it is valid by construction.
  2. Offline: fill in a version-matched template that was exported from the target Resolve version.
- **Validation gates every write.** Each written file is imported into the sandbox library, read back through the API and compared with the intended model. If it is visual, a frame is rendered as well. A file that has not been validated is labelled `unverified` and never offered to humans.
- **Version gate.** A file is never stamped newer than the target host. Writing for an older DbPrjVer is refused unless a template for that version exists.
- **Prior art.** We port the codecs from the `drp-format` JavaScript library and from the owner's `drp_tools`. `drp_tools` supplies codecs and format notes only; it has no keyframe writer, so fader keyframes do not come from it. We do not reuse DRP-Toolkit, which is GPL.
  - **`drp-format` licence: unconfirmed.** The standalone repository `samuelgursky/drp-format` returns 404 (checked 2026-10-19). The library is vendored at `resolve-advanced/vendor/drp-format/` in `samuelgursky/davinci-resolve-mcp`. The repository's root `LICENSE` and the vendored `package.json` both say MIT, but the vendored directory has no licence file of its own and the copyright line names the repository's contributors, not the library's author. We therefore treat the licence as MIT per the host repository and unconfirmed for the directory; `tests/fixtures/drp/README.md` records the commit the four template files come from.
- **Blocked on approval.** S8 and S9 need permission to use the edit PC's empty Local Database as the sandbox. Switching databases closes the open project.

### R2. Blackmagic Cloud

- Cloud work happens only through the node (F1). The node can:
  - list cloud projects in the current library
  - load, create, import or restore a cloud project with `CloudSettings`
  - read each clip's Cloud Sync status
  - set `liveCollaborationMode`
  - check freshness with `RefreshFolders` and `GetIsFolderStale`
- **Media.** Before a build, the node checks the sync status of the project's media. It flags proxy-only sync, because in our setup proxies have no audio.
- **No direct database access.** The node never connects to the cloud library's database. That is unsupported and puts the shared library at risk.
- **Review.** Presentations have no API, so review happens in our console as a render plus timecoded notes. A human can still post a Presentation by hand. Its comments come back as timeline markers, which the node can read.
- **Limits.** The free tier allows 2 GB of storage and 20 presentations. Libraries are paid.

### R3. Collaboration between Resolve Studio users

Resolve already handles the hard parts on cloud libraries (locks, Live Save, chat, Compare Timelines). This app adds the layer above:

- **Presence and leases** across humans and agents. They are shown in the console and returned to agents in tool results, for example "bin X is held by a human since 14:02".
- **Agent branch timelines.** Agents never edit a human's timeline. An agent duplicates it to `<timeline> [agent:<id> v<n>]`, edits the copy, renders a review, and a human merges it with Compare Timelines (21.1). This rules out lock fights by design.
- **Review threads** anchored at timecode, plus approvals and handoff notes, all stored in the hub. They can be mirrored to timeline markers so humans see them inside Resolve.
- **Shared per-project facts:** sync and angle offsets, gains, template traps and path maps.
- **Remote collaborators**, Mac users included, need only Resolve Studio and access to the cloud library. The console is a web page.

### R4. Several projects at once on one machine, one user

Each Resolve instance has one current project (F3), and a second instance is unproven (F4). The plan follows from that:

- **Cold work** for any number of projects runs in parallel.
- **Hot work** is time-sliced by the broker:
  - per-project queues, batched so Resolve switches projects less often
  - leases
  - context saved and restored around every switch: project, timeline, page, playhead, Deliver settings and bin
  - a presence guard that refuses to switch while a human is working. "Working" is a heuristic: recent input, or the page or playhead has moved.
  - **Resolve 21.1 traps: never poll Deliver state.** `Project.GetCurrentRenderMode()` raises a "Main view page is changed to 11" signal on every call. Read with the rest of the context on every 0.25 s worker tick, it crashed Resolve 21.1 after about 270 reads (live 2026-11-07). `GetCurrentRenderFormatAndCodec` was not tested, so it is treated the same way. The presence poll therefore reads only the working position (`get_position`: project, timeline, page, playhead, bin, Project Manager folder and whether a render is running), at most once per `context_poll_seconds` (default 2 s, `aar node run --context-poll-seconds`, at least 0.5 s and below the presence guard's configured maximum observation age, `max_observation_age`, default 30 s). Deliver state is read only off the poll path: by the snapshot when the broker borrows the human's context, by one check before the restore and by the restore's final check (three reads per borrowed context), inside `render.build`, and once after an op in the human's project that reports changing them (`note_deliver_changed`: the gateway's Deliver setters report themselves, and `render.build`, which drives the API directly, reports a failed restore of its own). **A human's Deliver edit is kept, unless an op in the same project then reports its own Deliver change** (today only `render.build` when its own restore fails, and its snapshot preset keeps the human's edit): the poll cannot see one, so the check before the restore compares the Deliver settings with what the broker last left there (the snapshot's, unless an op reported changing them). If they differ, a human changed them while the broker held the context: the broker keeps them, restores only the position, and records `deliver_restore_skipped: human_change` with the fields (in the restore report, the `restored` event and a node-log warning).
  - **Input idle is read only in the console session.** On Windows the guard reads keyboard and mouse idle time with `GetLastInputInfo`, which sees only the calling process's session. So the node checks first that it runs in the active console session (`ProcessIdToSessionId` against `WTSGetActiveConsoleSessionId`). In session 0 (a Windows service), in any other session, with no one attached to the console, or when either call fails, it reports `input_idle_error` and refuses to switch: fail closed, because there the idle would read as huge while a human types. The node must run in the interactive user's session, as a logon task, not a service. **Known limit:** a human working over Remote Desktop has a session that is not the console session, so the node refuses to switch while they are connected. That is the safe direction; revisit it in S15b, where `aar node run` is decided.
- **Renders.** Render jobs queue per project. S14 tests whether a `-rr` render node or a `-nogui` instance can run beside the GUI on the same PC. If neither can, renders are time-sliced too.
- **Fallback.** Truly parallel hot work needs a second Resolve instance. If S14 fails on Windows, that means a second machine or VM using Studio's second activation.
- **Collisions.** The broker also fixes today's thread collisions (F10).

### R5. UI and UX designed for agents

Agents are the primary users. Humans get a thin supervision console.

- **Task-level, typed tools** rather than mirrors of the Resolve API:
  - finding and describing: `project.find`; `timeline.describe`, which returns text a model can read (tracks, items with source timecode, gaps, markers)
  - analysis: `analyze.transcript`, `analyze.laughs`, `analyze.faces`, `analyze.loudness`
  - planning: `plan.lint`, `plan.apply(dry_run)`
  - looking: `frame.grab`, `frame.contact_sheet`
  - output and checks: `render.review`, `qa.check`, `review.request`
- **One EditPlan JSON for every build.** It holds source ranges with exclusive ends, tracks, transitions, audio gains, titles and a rule profile. The plan is linted against house rules before any Resolve call. A dry run returns a diff of what would change.
- **Every result carries measured values** from deterministic tools (frame counts, LUFS, durations). Errors are structured and include a fix hint and the known trap that caused them.
- **Everything resumes.** Jobs have ids and checkpoints, and the event log lets an agent replay its state after losing context.
- **Humans get four things:** a review queue (render plus timecoded notes), approve or reject, a board of who holds what, and an emergency stop.

**Analysis workers (S13c1).** `aar.analyze` holds the cold workers behind `analyze.*`, as a library and the `aar analyze` CLI; they register no node ops yet (the job wiring comes later, per F9). `aar analyze transcript` runs faster-whisper (extra `whisper`; the CCN preset is medium.en, int8 on the CPU, beam 5, VAD with a 400 ms minimum silence, no conditioning on previous text) and writes a `Transcript` in recording time, `file time + recording_origin / fps`. It checkpoints every segment, resumes with `--resume`, drops hallucinated segments by faster-whisper's own thresholds and lists each drop in its report. Models are never downloaded: a name is looked up in the shared model directory `$AAR_MODEL_DIR` (outside the worktrees), and a missing model is an error. `aar analyze sync` (extra `analyze`, numpy) measures each file's offset against a reference with GCC-PHAT anchor windows, a consensus, and a drift fit over the overlap, and returns one status per pair: `ok`, `drift`, `low-confidence` (candidates, never a number), `no-overlap` or `failed`. `offset_s` is where the other file's first sample falls on the reference's clock, so `other.recording_origin = reference.recording_origin + offset_s × fps`. Both follow the `aar qa check` exit codes, and `aar qa check --whisper-model` uses the same adapter for `join-retranscribe`.

**Analysis workers, part 2 (S13c2).** `aar analyze faces` writes `aar.faces/1`: OpenCV's YuNet face detector (extra `faces`, never in `dev`) on frames sampled at `--sample-fps` (default 2). The model is `--model` or `$AAR_YUNET_MODEL`, an existing file that is never downloaded; its sha256 and size go in the header with the settings, the input's size and mtime, the source and sample frame rates and the frame size. ffmpeg emits each sample at the display size, so a 90 or 270 degree rotation swaps width and height and the long side is at most `--max-side`. Sample i is the frame on screen at `i / sample_fps` (within one source frame, `time_tolerance_s`). Boxes and five landmarks are normalised to [0, 1], clamped, sorted largest first and rounded to 4 decimals. Non-finite and zero-area detections are dropped and counted, and a short final read is reported as `truncated_tail`, never parsed. It checkpoints every frame like the transcript, and a resumed run gives byte-identical output. `aar analyze laughs` writes `aar.laughs/1` and optionally a `LaughMap`. It extracts the whole file's audio to a 16 kHz FLAC, asks Gemini with the versioned prompt `LAUGH_PROMPT_V1`, saves the raw reply, and checks every laugh against the audio. **The credential** is a Gemini API key, read only from the environment (`AAR_GEMINI_API_KEY`), sent only in a request header, and never written anywhere: not argv, a URL, a log, a report, the work dir or an error message. **The paid call** needs `--allow-paid`; without it the command exits 2 before any network use, and `--from-raw` re-parses a saved reply offline. **No redirects** are followed, because urllib would copy the key to the new host, and every request must go to the API's own host. **The parser** is strict. Every dropped item is reported with its index, its reason (`bad-item`, `bare-number`, `bad-time`, `bad-level`, `unknown-kind`, `reversed` or `out-of-range`) and an excerpt. **The envelope cross-check** compares a 10 Hz RMS envelope over [start − 1, end + 2] with the median of the 8 s before it. A laugh is `confirmed` when `bump90 ≥ 6.0` dB and `frac6 ≥ 0.10`; both thresholds are tunable starting values, to be set on real material. With too little baseline or digital silence a laugh is `unchecked`, otherwise `unconfirmed`. **The onset is refined** on a 50 Hz envelope: the first 20 ms frame more than 6 dB above the baseline that stays more than 3 dB above it for 200 ms, within 1 s before to 1.5 s after Gemini's start. End-on-laugh lands on this onset. Laughs within 0.25 s merge. The map holds confirmed laughs (all of them with `--include-unconfirmed`). **Applause never enters a laugh map**; it is listed separately. A whisper model name looked up in `$AAR_MODEL_DIR` must resolve inside that directory, symlinks and `refs/main` included (`model-outside-dir`), while an explicit model path is taken as given.

#### The EditPlan (version 2)

`aar plan schema` prints the JSON Schema; `src/aar/plan/model.py` is the reference. Positions and lengths are integer frames at the plan's `fps`, and every range is half-open, `[in, out)`. The published schema is an approximate contract, and the model is authoritative at the numeric edges: a JSON number such as `24.0` as the frame rate or `1.0` as the version passes the schema's `integer` test, but the model refuses it. The same goes for the frame rate's text form: fps text padded with non-ASCII whitespace (a no-break space, say) is refused by the model but accepted by the schema, so the schema errs on the safe side.

- **Version 1 fields** (S5): `project`, `timeline`, `kind` (`longform` or `short`), `fps`, `resolution`, `profile`; `sources` (id, media, camera, shot size, recording id and origin, duration); `segments` (track, source, `src_in`/`src_out`, `record_in`, keyframed `reframe`, `gain_db`); `transitions` between neighbouring segments (video type and length, audio transition); `titles` (lower thirds are `kind: "lower-third"` with a template name, lines and a record in/out); `captions` and `caption_style`; `markers`.
- **Version 2 adds** what the S13 producers and the `plan.apply` compiler need:
  - `template`: the timeline the build starts from. The compiler branches it with `timeline.branch`, never `timeline.duplicate`, so the copy is a registered agent branch.
  - `head`: how the first segment comes in from black (video type and frames, audio fade-in frames).
  - `outro`: the clip appended where the content ends (source id, optional source range, video track, the name of the audio track that carries it, the transition into it, and optional `sting` text over its start). The outro is not a content segment. Content rules (chronological, dialogue splice, end on the laugh, cut density) see the last content segment as the end. The outro does count towards the timeline length, so `short-max-duration` includes it.
  - `audio_tracks`: per-track name, `gain_db`, `mute` and optional `bus`, in track order (A1 first), so the CCN topology can be stated: A1–A4 muted, A5 the bus, A6 the bounce. Names are unique.
  - `Source.color`: input colour space, an optional CDL (slope, offset and power as three numbers each, plus saturation) and an optional LUT name. The safety rule still holds: never set the input colour space on BRAW. The linter's `no-braw-input-color-space` rule reads the `media` text alone: it is BRAW when the path ends in `.braw`, in any case, with surrounding whitespace trimmed. A URI (`scheme://...`) loses its query and fragment first; anything else is a local path and is tested whole, so a name such as `take #3.braw` still counts. The real clip is checked at apply time.
  - `Source.frame_size` (S18): the media's **display** size `[width, height]` (after pixel aspect and rotation, not the stored pixel size), two whole numbers above zero (or any size with the display aspect, such as a face track's sampled size). Reframe `x`/`y` are shares of the source picture, and `zoom` 1.0 is the source filling the frame (the tallest crop the timeline's aspect allows). `aar plan produce` sets it (see Plan producers, framing). `plan_hash` leaves it out while unset, so older plans keep their hash.
  - `Segment.transform`: a static zoom, pan, tilt, rotation and flips, separate from the keyframed `reframe`. The effective zoom is the transform's zoom times the reframe zoom; `no-same-camera-jump` uses it.
  - `end_fade_frames`: the audio fade-out at the very end of the timeline.
- **Versioning rule.** `version` is 1 or 2, and a plan that leaves it out is version 2. Version 2 only adds fields, so every valid version 1 plan is valid, and lints the same, as version 2. A plan that says version 1 and gives a version 2 field a value is a validation error (`plan_version`) naming the field, for example `segments[1].transform`. Null, or an empty `audio_tracks`, is not a use, so a full dump of a version 1 plan reads back as version 1. `tests/plan/fixtures/v1_compat` pins the pre-v2 profile and the reports the pre-v2 code wrote for the plan fixtures; linting them today must give the same bytes.
- **Where problems are reported.** Version 2 cross-references are validation errors (exit 2), each with the field's location: an outro source that is not a plan source, an outro that plays to the end of a source with no duration, an outro range outside its source, a sting longer than the outro, an outro audio track not in `audio_tracks`, duplicate track names, a blank template or name, a CDL triple that is not three finite numbers in range, and a head or outro transition whose type and length disagree (a cut has no length; anything else needs one). The version 1 checks stay lint findings in `ranges-valid` (exit 1), so version 1 plans lint exactly as before.

**Rules.** The `ccn` profile runs these; the thresholds are in `profiles/ccn.toml`, not in code.

| Rule | Severity | What it checks (ccn values) |
| ---- | -------- | --------------------------- |
| `ranges-valid` | error | Ranges positive and inside the media, no overlap on a track, unique source ids, transitions that follow a join |
| `chronological` | error | Each recording plays forward only |
| `no-dialogue-splice` | error, warn | No cut inside a word (error); a cut sits in a pause of at least 250 ms (warn). Needs a transcript |
| `no-same-camera-jump` | error | Same camera across a time jump needs a zoom change of at least 0.2 (static transform included) |
| `timejump-close-to-wide` | warn | A time jump cuts to a wider shot |
| `no-dissolve` | error | Cuts between content segments. **New:** the head and the outro transitions are allowed when the profile says so (`allow_head`, `allow_outro`), up to `max_head_frames` / `max_outro_frames` (30, which admits the 15-frame start dissolve). Without those keys only cuts pass |
| `audio-crossfade` | error | Non-continuous joins get a "Cross Fade 0 dB" of at most 30 frames with enough handle |
| `cut-density` | warn | **New.** No more than `max_cuts` (2) cuts in any `window_s` (10 s) of record time. Overlapping offending windows merge into one finding with the burst's span and cut count |

A rule's thresholds are either required (every profile listing the rule sets them) or optional with a code default. A rule can also check its threshold values, and a bad value is a profile error (exit 2) before anything is linted.

The join-based cut rules (`cut-density`, `no-same-camera-jump`, `timejump-close-to-wide`, `audio-crossfade`, and the neighbour hint of `min-shot`) consider same-track joins only, meaning neighbouring segments on one track, so an overlay entry on another track and the cut into the outro are not counted as cuts. `no-dialogue-splice` (`src/aar/plan/rules/speech.py`) also uses same-track joins, to spot unbroken continuations, but it does not count cuts.

### R6. CCN work end to end

Recipes turn the existing, proven pipeline (the CCN shorts and long-form workflow, thumbpipe, the supoclip runner) into a work graph. The steps are:

1. Brief.
2. Locate sources (cloud project, offline media).
3. Flatten multicam and apply offsets.
4. Transcript and laugh map.
5. Cut plan, rule-checked.
6. Resolve build from the template: lower third, sting, outro, A5 bus.
7. Camera match.
8. Crossfades and loudness.
9. Review render: `render.build` sets the output size and quality, then `aar.deliver` fits it under the review cap.
10. QA: re-transcribe the joins, LUFS, offline frames, colour.
11. Human review loop: the review render is stored, QA'd and sent for a human decision.
12. Master render: `aar.deliver` pulls it, hashes and stores it, and records its QA facts.
13. Shorts, then captions.
14. Thumbnails (thumbpipe).
15. Publish: YouTube through Command Center, Instagram through ccn-web-app.
16. Archive and update the project facts.

House rules ship as a rule profile, `ccn`:

- Never splice dialogue, and keep ranges chronological.
- No whip-pans, and no same-camera jump cuts.
- End hard on the laugh.
- Cut close to wide at time jumps, with no dissolves.
- Audio crossfades are at most 30 frames and sit in room tone.
- Loudness: about -22 LUFS for long-form, about -14 to -15 LUFS for shorts.
- Shorts run under 37 s.
- Captions: at most 16 characters, Montserrat, active word in yellow.
- Review MP4s stay under 20 MB.

Other shows get their own profiles.

#### R6 decisions for S13 (2026-10-19)

These are defaults taken from the owner's recorded feedback on real CCN cuts. Each one is a profile value or a recipe parameter, so it can change without code.

- **End on the laugh means its onset.** The last frame lands between the laugh's onset and 400 ms after it: "end hard right after the punchline word or at the first hint of laugh, no dragging laugh, never fade to silence". A short's audio fade-out is a de-click (at most 1 frame), never a fade to silence. Long-forms end on the laugh, then the outro.
- **Dissolves.** None between content segments. A transition in from black on the first segment and the transition into the outro are allowed (the real long-form build uses a 15-frame start dissolve).
- **Cut density.** Warn when any 10 s window holds more than 2 cuts ("8 cuts in 13 s" was "extremely choppy"; 5 cuts in 50 s was accepted).
- **Shortest shot.** Warn under 1.0 s; fold slivers into a neighbour.
- **Pause trimming is a planner parameter, not a lint rule.** Trim pauses of at least 0.9 s down to a beat of about 0.45 s. The silence threshold is per venue: -42 dB by default, -36 dB where room laughs sit at -36 to -40 dB. QA reports the longest silence left in the output.
- **Joins sit in source-audio quiet.** Transcript word gaps are not enough, because Whisper word times are off by 0.1–0.2 s at joins. The in-side of a join needs at least 60 ms below -40 dBFS in the source audio. After the render, 2–3 overlapping short-window transcriptions around each join must agree with each other and with the plan's words.
- **Loudness.** Shorts get gain plus a limiter, not two-pass loudnorm, which flattened the laugh-to-voice range and padded the tail. Targets: -14.5 ± 0.5 LUFS for shorts, -22 ± 0.5 for long-forms. True peak at most -1.0 dBTP, no clipped samples, and the duration is unchanged.
- **Captions.** Every kept word is captioned (words snapped equals words captioned).
- **Where work runs.** Cold work (analysis, planning, QA, shorts compose) runs on the hub host. Resolve, its renders and the masters stay on the edit PC. Files move through one transport module that checks size and sha256.
- **Builds start from the template with `timeline.branch`,** so the copy is a registered agent branch. A human merges it.
- **Shorts compose with ffmpeg first** (a port of the proven runner). The Resolve template route comes later through the `plan.apply` compiler.
- **Publishing.** aar's last step emits a publish packet (final file and its hash, metadata, thumbnail) and waits on a human approval. Command Center and ccn-web-app do the upload; aar holds no YouTube or Instagram credentials.
- **Hub writes.** Agents create brief, plan and recipe nodes through hub write tools. Deciding a review stays human-only.

#### Media QA (S13b)

`aar.qa.check(file, kind=..., profile=..., plan=..., transcript=..., transcriber=...)` and `aar qa check FILE --kind short|longform|review` measure a render with ffmpeg and return one entry per check: id, status (pass, warn, fail or skipped), measured values, the target, and a one-line message saying what to do. Thresholds live in the profile's `[qa]` block (`QATargets`). Every key added after `review_mp4_max_mb` has a default, so an older profile still loads. `aar.media` runs ffmpeg and ffprobe from `AAR_FFMPEG`/`AAR_FFPROBE` or `PATH`. It passes argument lists only (the path goes in as `file:<absolute path>`), gives every call a timeout that kills the process group, keeps a bounded stderr tail, and raises `MediaError` with the exit code and that tail. The CLI exits 0 when no check failed and 1 when the checks ran and one failed, including media that exists but does not decode (a failed decode check). It exits 2 when the input or a tool cannot be located or opened, or the profile is invalid.

| Check | Definition | Parameters |
| ----- | ---------- | ---------- |
| decode | ffprobe reads the file, and a full `-xerror` decode of every video and audio stream prints no error and exits 0. A file ffprobe cannot read fails here, and the render checks below are skipped as `render-unreadable`. | none |
| loudness | ebur128 on the first audio stream: integrated I within the kind's target ± tolerance (inclusive), and true peak (4x oversampled) at most the maximum. LRA is reported only. `review` uses the long-form target. A render without audio fails. | `short_lufs` -14.5, `longform_lufs` -22, `lufs_tolerance` 0.5, `true_peak_max_dbtp` -1.0 |
| clipping | A clipped sample is a decoded 32-bit float sample, in any channel, whose magnitude is at or above the clip level. When the astats sample peak is below the level, the count is 0 without a scan. Otherwise every sample is counted in pure Python, so a long master that reaches the level can run into the call's timeout (which then fails the check). NaN or infinite samples also fail. A clipped square fails and a -6 dBFS sine passes. | `clip_level_dbfs` -0.01 |
| longest-silence | ffmpeg silencedetect: a silence is every sample of every channel below the threshold for at least `silence_min_s`. The check reports the longest silence and where it starts. It passes unless `longest_silence_warn_s` is set and the longest silence is longer, which gives warn. | `silence_db` -42 (the CLI `--silence-db` or the `silence_db=` argument sets a venue value such as -36), `silence_min_s` 0.2, `longest_silence_warn_s` off |
| size-cap | `review` renders only: at most `review_mp4_max_mb` decimal MB (1 MB = 1,000,000 bytes). Other kinds are skipped as `not-applicable`. | `review_mp4_max_mb` 20 |
| duration | The render's video stream (else its audio stream, else the container) lasts the plan's record duration (`total_frames()` at the plan fps), within the tolerance in frames, inclusive. | `duration_tolerance_frames` 1 |
| join-quiet | Applies to every cut, meaning a join that does not continue the same recording within `join_continuity_tolerance_frames`. The check decodes the incoming source's first audio stream over [src_in − S, src_in + S], clipped to the start and end of the source, at 48 kHz. A window of `join_quiet_window_ms`, starting at any sample, is quiet when the RMS of its loudest channel is below `join_quiet_db`. A quiet run is the union of overlapping quiet windows, so its length is exact to the sample. The cut passes only when a run of at least `join_quiet_min_ms` contains src_in, allowing `join_quiet_slack_ms` at either end of the run: the incoming clip must start in the pause, not near it. When a cut fails, the scan becomes the fix hint. The nearest run of at least the minimum inside the window (the longer one on a tie) is reported with a suggested src_in, the frame at the plan fps nearest that run's middle ("move src_in of join N to frame F"). If there is no such run, the hint says there is no pause within ±S. Each join reports the run at the cut, the nearest pause, the longest run and the quietest window. S must cover the minimum plus the slack, so the window never shortens a run that contains src_in. With the default S, a pause whose qualifying part ends more than 40 ms before src_in is outside the window and gets no suggestion. | `join_quiet_db` -40, `join_quiet_min_ms` 60, `join_quiet_slack_ms` 10, S = `join_quiet_search_s` 0.10, `join_quiet_window_ms` 10, `join_continuity_tolerance_frames` 1 |
| join-retranscribe | Applies to every cut. An injected `Transcriber` (`aar.qa.Transcriber`) transcribes `join_windows` windows of the render, each `join_window_s` long, centred on the join and offset by `join_window_step_s`. The windows are compared on their overlap less `join_window_edge_s` at each end. A word is in that region when its midpoint is. Every pair of windows, and every window against the plan's expected words, must reach a difflib ratio of `join_agreement_min`. The expected words are the source transcript words, mapped through the plan. A source word that the cut slices by more than `word_straddle_s` on both sides fails the join, and so does a transcriber exception. | `join_windows` 3, `join_window_s` 4.0, `join_window_step_s` 0.5, `join_window_edge_s` 0.25, `join_agreement_min` 0.8, `word_straddle_s` 0.03 |
| caption-coverage | Every kept word is covered by a plan caption in record time. A kept word is a transcript word whose midpoint lies inside a kept segment's recording range, and it is covered when its record midpoint lies inside a caption's [record_in, record_out). The check lists the uncovered words. A short with no captions fails. A long-form or review plan with no captions is skipped. | none |

Skipped never means passed. A check is `skipped` only when the caller chose not to give an input (`no-plan`, `no-transcript`, `no-transcriber`, `no-captions` for a long-form or review plan), when the render could not be read or has no audio (`render-unreadable`, `no-audio`, which always come with a failed decode or loudness check), or for the size cap on a render that is not a review (`not-applicable`). Every skip carries a `skip_reason` and a message that says what was missing. A check that ran but could not check everything sets `incomplete` and puts the cause in `measured["unchecked_reason"]` and in its details. This covers a join check whose plan sources cannot be read (`source-unreadable`: the file is missing, the path is not local, or the source has no audio), a transcript that does not cover the recordings on both sides of a cut or under every segment (`transcript-does-not-cover`), and a truncated silence log (`log-truncated`). Such a check warns, or fails if something it did check failed. When nothing could be checked it warns, so it never looks better than a check that ran. The report's status is the worst status among the checks, and a skip counts as neither pass nor fail. The report's `unchecked` list names every check that was skipped or incomplete, so a runner can tell an all-clear (pass with an empty list) from "not checked" without parsing messages. The CLI prints that list under its head line. QA targets must be finite numbers: TOML allows `nan` and `inf`, and the profile refuses them. Any measurement that fails, including an ffmpeg error or a timeout, is a fail that carries the tool's message. Missing ffmpeg or ffprobe raises an error rather than producing a report in which every check is skipped. Source media paths in a plan are local hub paths. A relative path resolves against the plan file's folder in the CLI, or against `media_root` when the library is called. S13f adds the map from edit-PC paths to hub paths. Plan version 2 (S13a) works as is: `duration` measures against `total_frames()`, which includes the outro, and the step into the outro is the outro's transition, not a content cut. A v2 plan still does not say which audio track carries each segment, so every content join on a video track is treated as an audio cut.

#### Plan producers (S13d)

`aar.plan.produce` and `aar plan produce STUB --transcript T --keep K --out PLAN` turn analysis outputs and a keep list into an EditPlan v2 that lints clean. They are cold and deterministic: the only media access is ffmpeg decoding the source audio for pauses and joins. Every parameter is in the profile's `[produce]` block (defaults in code, so a profile without the block still loads); the cut-in-quiet test reuses `[qa]` `join_quiet_*`, so the planner and QA cannot drift apart. **The governing rule: the producer never plays material the human excluded, and never removes a word.** No edge, nudge, fold or ending moves outside a keep range.

- **Inputs**, each validated at the boundary with a typed `ProduceInputError` (exit 2): a **plan stub**, an EditPlan with no segments or transitions, whose `sources` are the source list and whose other fields (template, head, outro, audio tracks) pass through; the **transcript** (`aar analyze transcript`), which must name its recording (`transcript-unnamed`), and that must be the cut's recording; a **keep list**, `{"recording"?, "ranges": [{start_s, end_s, label?}]}` in recording time, chronological; optionally **sync** (`aar analyze sync`: each `ok` pair sets its source's origin; any other status is refused), **face tracks** (`aar.faces/1`, bound to the source whose media is the measured file; faces are sorted by size here, never trusted in file order), a **laugh map**, and a **camera schedule** `{"spans": [{start_s, end_s, camera}]}`, a camera being a `Source.camera` label or a source id. Without a schedule, `default_camera` is on screen throughout. **Automatic speaker-driven camera switching is out of scope:** the cameras come from the schedule. All cameras of one cut share one recording.
- **Keep edges move inward only.** Touching ranges merge first (they play unbroken, so a word across the seam stays), and edges round inward to whole frames. An edge inside a word (the `no-dialogue-splice` test, `word_at`) moves inward past it, the in point to the word's end and the out point to its start: the partial word goes with the material the human excluded, and the range never grows. Each word an edge cuts through is named in a `keep-edge-cuts-word` warning (its text, time and edge). Where transcript words touch, the frame nearest the shared boundary is allowed, so a boundary with no frame inside the tolerance does not pass whole words. Where they overlap, a whole word can go with it, and a `keep-edge-drops-word` warning says so. A range this empties is dropped with a `keep-dropped` warning; one that falls under `min_shot_s` is refused (`keep-too-short`).
- **1. Pause trim.** A pause is a quiet run of the scheduled camera's audio (10 ms RMS of the loudest channel, `aar.media.quiet_runs`, below `silence_db`: −42 dB, or a venue's, e.g. `[produce.venues.loud]` −36 dB), never a transcript gap. Runs that meet at a scan chunk's edge or a camera change join. A pause strictly inside a keep range and at least `min_pause_s` (0.9 s) long keeps `beat_s` (0.45 s): `beat_lead_s` (0.25 s) after the outgoing speech, the rest before the incoming. A transcribed word inside a quiet run splits it, so no trim removes a word; every word occupies at least `min_word_ms` (40 ms) around its middle, so zero-length and 15 ms words count too. A source longer than `no_pause_warn_s` (60 s) whose kept parts hold no quiet stretch at all, not even between words (silent audio, or the wrong venue threshold), gets a `no-pauses` warning.
- **2. Joins in quiet.** Every cut's in point must pass QA's join-quiet test (`aar.qa.scan_join_quiet`: a run of at least 60 ms below −40 dBFS containing src_in). A human cut (between keep ranges) also needs the crossfade's incoming handle inside that run, and its out side checked on the outgoing audio envelope: one quiet run from `out_quiet_preroll_ms` (20 ms) before src_out to the end of the outgoing handle, so the kept tail holds no real word tail that Whisper ended early, and the fade-out holds no onset of the next removed word. A failing point moves up to `join_nudge_ms` (150 ms, in whole frames rounded down), nearest first, to a passing frame that adds or drops no word, keeps the cut a cut and leaves the shot foldable: at a human cut inward only (the in point later, the out point earlier), inside a keep range either way. Otherwise it stays and a warning names the join (`join-not-quiet`, `join-out-not-quiet`). When the media has no frame for the crossfade's handle, the point moves to the first frame that has one if that frame passes, else `ProduceError("no-handle")` names the cut.
- **3. Sliver fold.** A shot under `min_shot_s` (1.0 s) folds within its own keep range, never across a human cut. Across a camera change it merges into the neighbour; across a trimmed pause the trim is re-run: the sliver grows into the pause just far enough to last `min_shot_s` and the rest stays trimmed, and only a pause too short for that comes back whole. The option that brings back the least removed audio wins, the previous side on a tie. A sliver with no option is an error.
- **4. End on the laugh.** With a laugh map, the content ends `end_after_ms` (200 ms) after the onset of the latest laugh in the final keep range (at least the end-on-laugh rule's `min_strength`). Content after it is dropped, with an `end-dropped-speech` warning saying how much when it held words. The out point stays inside the final keep range and the piece ending there must belong to it, so a laugh at the range's first frame never stretches the previous range across the human's cut. A frame inside a word moves to the nearest clean frame inside the rule's window; with none, the ending stays and a warning says so. `end_after_ms` must lie inside that window.
- **5. Framing.** A same-camera cut steps the framing: a long-form toggles `Segment.transform.zoom` 1.0 ↔ `punch_in_zoom` (1.25); a short cycles the `[[produce.framing]]` presets (A zoom 1.0, B zoom 1.22 with y 0.45, the house limit for a shorts punch-in), which must differ by `no-same-camera-jump`'s 0.2. A short's reframe follows the face track's largest face with the supoclip `steady()` path (`[produce.steady]`: dead zone 0.25 crop widths, Gaussian glide σ 0.7 s, the edge-safety passes), then a clamp into the picture and a slew limit at `speed_headroom` (0.9; at most 0.95, because keyframe x is rounded to 4 decimals) × `no-whip-pan`'s 0.3 frame widths/s; zoom and height are static per segment. Keyframes every `key_step_s` (0.5 s). A face that still nears the crop edge is a warning. A face track over a source with camera cuts inside it smooths across them; split the keep list at those cuts. **Source size (S18).** Each source gets `frame_size` for the FCPXML export's framing: the stub's own, else the display size of the video stream the producer's probe reads from the same file (`aar.media.probe`: pixel aspect applied, then a 90/270 rotation swaps it; the cut's sources reuse the audio probe, other readable sources are probed, an unreadable one is a `frame-size-unread` warning), else the face track's sampled size. An audio-only source gets none. Sizes whose aspects differ by more than 1 % are a `frame-size-mismatch` warning; the stub's size still wins, and the probe wins over the face track.
- **Every cut** gets a `crossfade_frames` (2) audio crossfade of `audio-crossfade`'s type; its handle is `ceil(crossfade_frames × handle_fraction)` frames each side.
- **Invariants.** Chronological order and no edit point inside a word are checked on the result (`InvariantError`). The plan is then linted under the profile; a lint error is `LintGateError` and nothing is written (exit 1). Warnings are allowed and listed in the report with the planner's own warnings and a log of snaps, trims, nudges, folds and the ending.

#### Edit-PC transport (S13f)

Cold work runs on the hub; Resolve, its renders and the masters stay on the edit PC. One module (`aar.host`) moves files between them and runs PowerShell there. It is security-sensitive: it builds remote commands and moves files, so every path and string is treated as hostile.

- **Config, not code, names the host.** The edit PC is an ssh alias plus an ssh config file (`ssh -F <config>`), given by `AAR_EDIT_*` environment variables or an explicit `EditHostConfig`. There is no default host anywhere in code, and the ssh config and key material are never read. The alias must be a plain ssh host/alias (`^[A-Za-z0-9][A-Za-z0-9._@-]*$`): `/`, `[`, `:`, spaces and a leading `-` are refused, because they change how scp splits `host:path`.
- **Roots bound every transfer.** The config lists allowed remote (Windows) roots and allowed local (hub) roots. A source or destination outside them is refused before any command runs. Local paths are resolved with `realpath`, so a symlink that escapes its root is refused.
- **Runner seam.** All argv go through a `Runner` (argv list, optional stdin, timeout). The real one uses `subprocess` with an argument list and never a shell, and always passes `-F <config>`, `-o BatchMode=yes` and `-o ConnectTimeout=<n>`. Tests use a fake runner; nothing in the module or its tests contacts a real host.
- **PowerShell.** Scripts run as `powershell -NoProfile -NonInteractive -EncodedCommand <base64 of UTF-16LE>`. The command-line cap is a config value (`AAR_EDIT_CMDLINE_MAX`), not a fixed constant: Win32-OpenSSH runs the command through the sshd DefaultShell, and the default DefaultShell is `cmd.exe` (~8191 characters), far below the 32767 a PowerShell DefaultShell allows. The default cap is sized for `cmd.exe` and the refusal says so and how to raise it. Output CRLF is normalised to LF and CLIXML progress is stripped from stderr (error text is kept). Values embedded in scripts use one quoting helper (single-quoted literals), which doubles every character PowerShell treats as a single quote -- `'` and the smart quotes U+2018, U+2019, U+201A, U+201B -- so a filename like `Don’t Tell Mom.mp4` cannot break out of its literal. Parent paths inside scripts are taken with `[System.IO.Path]::GetDirectoryName`, never `Split-Path -LiteralPath ... -Parent` (an invalid parameter-set combination).
- **Transfers.** `pull`/`push` use scp in SFTP mode (the OpenSSH 9 default; `-O` is never passed). Remote size and SHA-256 come from `Get-Item`/`Get-FileHash`, local from `os`/`hashlib`. The file lands under a temporary name beside the destination and is moved into place only when both size and hash match; a mismatch or failure removes the partial and raises a typed error. The local move prefers an atomic hard link and falls back to an `O_EXCL` claim-then-replace on filesystems without hard links (FAT/exFAT, some SMB/CIFS and FUSE mounts); a local I/O failure surfaces as a typed error with the partial removed. An existing destination (file or directory) is never overwritten unless the caller asks; `--overwrite` still refuses a directory destination and a destination whose parent is a reparse point (the move fails closed).
- **Path forms and globbing.** A Windows path becomes one of `alias:E:/...` (default) or `alias:/E:/...`, selected by config, because it is unsettled which Windows OpenSSH needs. The spec is rebuilt from validated components, so no raw separators or alternate spellings leak through. scp in SFTP mode globs a remote *source* client-side, so glob metacharacters (`[ ] * ? \`) in a download source are backslash-escaped; a remote *destination* is not globbed and is sent literally. scp is always run with `-s` to force SFTP mode rather than rely on the client default; there is no toggle. The hub needs OpenSSH >= 8.7. Legacy SCP is unsupported because it is unsafe: in legacy mode scp sends the remote path unquoted through the remote shell (`cmd.exe` by default on Windows), so a data-controlled filename containing `&`, `^`, `%VAR%` or `$( )` would run a command (the round-2 HIGH-1 class of bug). A client older than 8.7 rejects `-s` and so fails closed with a typed transport error; a client of 8.7-8.9 defaults to legacy SCP, which `-s` overrides. The hub is OpenSSH 9.6p1. If the removed `AAR_EDIT_SCP_SFTP` env var is still set, config load refuses with a typed error rather than silently ignoring it.
- **Timeouts.** `connect_timeout` (ssh `ConnectTimeout`, default 10 s) bounds the handshake. `command_timeout` (default 300 s) is the wall-clock for each runner call, so it also bounds the scp of a large master and the `Get-FileHash` of one; callers pass `--timeout` (or a larger `command_timeout`) for big files.
- **What is refused.** Relative and drive-relative paths (`E:Show`), `.`/`..`/empty components, verbatim and device namespaces (`\\?\`, `\\.\`), reserved device names (`CON`, `COM1`, …), illegal or control characters (including an alternate-data-stream `:`), trailing dots or spaces, UNC paths unless a UNC root is configured, and anything that does not resolve inside an allowed root. Path parsing, NTFS upcasing and the edit-PC↔hub map reuse `aar.drp.modify.paths`.
- **Root confinement folds ASCII case only.** A path is inside a root when its leading components match the root's, compared with an ASCII-only upper-case fold. ASCII case differences fold (`E:\Show` == `E:\SHOW`), but a non-ASCII character must match exactly: the full NTFS upcase over-folds 246+ pairs NTFS keeps distinct (long s vs `S`, dotless i vs `I`, Kelvin sign vs `K`), so e.g. `E:\ſhow` or `E:\CAFÉ` under root `E:\Café` is refused as `outside-allowed-roots`. Under-folding is the safe direction: at worst it refuses a path that NTFS would place inside the root, never the reverse.
- **Known limit.** Root validation is lexical, so a junction or symlink (reparse point) under an allowed root could still redirect a transfer outside it on the edit PC. The push move refuses when the destination's immediate parent is a reparse point, but a reparse point higher in the tree is not caught. This is acceptable for a trusted, single-tenant edit PC on a tailnet; a complete fix needs an atomic remote resolve-and-move that SFTP does not offer (any check-then-move still races).
- **Residuals for a live Windows test** (the hub has no PowerShell or Windows, so these are reasoned, not confirmed):
  - the generated move script on Windows PowerShell 5.1 (the `GetDirectoryName` parent for a drive-root and a UNC-share-root destination, HIGH-2); `Move-Item -LiteralPath ... -Destination` with `[ ]` in the name on 5.1; the no-`-Force` move refusing an existing file; and the container and reparse-point guards against a real junction;
  - the real command-line budget for a cmd.exe DefaultShell (the `cmd.exe /c` wrapper and full path);
  - which path form (`E:/...` vs `/E:/...`) Win32-OpenSSH's sftp-server accepts for stat, glob, download and upload;
  - UNC over SFTP in both forms (slash form is `///server/share/...`), including the second-hop credential, and `Get-Item -LiteralPath '\\server\share' -Force` on a share root;
  - smart-quote (`Don’t ...`, with U+2019) and non-ASCII names end to end (UTF-8 over SFTP to UTF-16);
  - `scp -s` acceptance on the client actually used (a client older than OpenSSH 8.7 rejects it and fails closed);
  - stdin handling (ssh/scp get `/dev/null`), CLIXML noise on a first-run module load, and hidden files (`Get-Item` without `-Force` fails closed);
  - paths of 260+ characters through `GetDirectoryName`/`Get-Item` on .NET Framework (5.1);
  - whether the cleanup `Remove-Item` after an interrupted upload races the sftp-server's still-open handle and silently leaves the `.aarpart-*`;
  - legacy SCP (toggle-off) mode is unsupported because it is unsafe (see the transfers note): the remote shell parses the path, so it is never exercised and never allowed.

#### Hub write surface (S13g1)

How agents write to the hub (`aar.hub.writes`, `aar.hub.facts`). The MCP tools and `aar hub write` are thin wrappers over the same functions.

- **Opt-in.** `aar hub serve` stays read-only and lists exactly its 13 read tools (12 from S13g1 plus `recipe_status`, added in S13g2: it is always listed, even without agent writes, because an agent needs it to drive a recipe run). `--agent-writes` opens the existing database writable and adds six write tools (`brief_create`, `recipe_create`, `plan_submit`, `node_set_status`, `facts_record`, `facts_retract`), the S13g2 recipe write tools (`recipe_start`, `step_complete`, `recipe_retry`, `recipe_cancel`) and three reads (`facts_get`, `brief_get`, `plan_get`). Human-only actions (deciding a review, granting or revoking an approval, resuming after a stop) are never tools. Agents without MCP use `aar hub write {brief,recipe,plan,status,fact,retract}` and `aar hub facts show`: one JSON request in (a file or stdin, with the tool's arguments), JSON out, a refusal as `{"error": {code, message, fix_hint, details}}` on stderr with exit 2. A plan stored as `blocked` exits 1, as `aar plan lint` does.
- **Identity is self-declared.** A write tool records the caller's `agent_id` as `Actor("agent", agent_id)`, checked only against the agent-id rule. That is attribution, not authentication (decision 6): any caller that reaches the server can claim any agent id. The CLI's `--actor` is the same.
- **Node kinds and schemas.** The graph gains a `recipe` kind; logs written before still fold to the same state (pinned by a fixture generated on the old code). Node data is typed with strict models (unknown keys refused, every string and list bounded, no NaN or infinity), each with a `schema` literal:
  - `aar.brief/1`: hub `project_id`, `show`, `kind` (longform, short, thumbnail), `recipe`, `rule_profile` (a built-in profile name), `sources` (at most 64 cloud-project, timeline-by-unique-id or media refs), `deliverables` (1 to 32, unique names, typed kinds) and optional `hook`, `handle`, `title`, `notes`.
  - `aar.recipe/1`: `recipe`, `brief_id`, `params` (a JSON object of at most 64 KiB, nested at most 8 deep), `max_review_rounds` (1 to 10, default 3). The recipe's own validator checks the params (a hook for S13g2; the default accepts any bounded object). The brief must be typed and ask for that recipe.
  - `aar.plan-node/1`: the EditPlan is stored as a content-addressed artifact (its canonical JSON, at most 1 MiB); the node holds its sha256, the plan version, the rule profile, the parent, the brief it resolves to, and a lint summary (counts, the first 20 findings errors first, and the rules that could not run). A plan derives from a brief, recipe, earlier plan or review, never an op or artifact. A plan that fails validation is refused with each field location; one with lint errors is stored `blocked`, one without `pending`. The hub lints without a transcript or laugh map, so the rules that need one are listed as skipped, not passed.
- **Profiles by name only.** The hub accepts built-in profile names, never paths, so a tool caller cannot make the hub read a file on its host. A plan whose parent resolves to a typed brief must use that brief's `rule_profile`, so an agent cannot dodge the house rules by naming another profile.
- **Who may change what.** An agent (or node) may move the status of a brief, recipe, plan or op node that it created (the actor on the node's creation event), through the graph's transition table. A human may move any node except a review. Reviews close only through a human decision or the requester's withdrawal. **Runner-managed nodes are the exception:** a recipe step's op node (`aar.step/1`) and a recipe node once its run has started are refused for every actor (`runner_managed`) — they mirror runner evidence, so a human acts on a running recipe through `recipe_cancel` and review decisions, never a status move.
- **Actor kinds** are `human`, `agent`, `node` and `runner`. `runner` is the recipe engine's own identity (`aar.recipes.RUNNER`); it is the only writer the scheduler trusts for `recipe.*` evidence and op nodes. No string surface can produce it (the actor parsers and MCP refuse `runner:*`). The runner may request reviews, but may never decide one (human-only) and may not move a node through `set_own_status`; local trust still applies (a direct event-log writer on the host is trusted, as everywhere).
- **Idempotency.** Every write needs a caller-chosen `idempotency_key`, namespaced per actor. The same key with the same (normalised) request returns the first result again, marked `replayed`; the same key with a different request (another project, op or content) is `idempotency_conflict`. A write that takes several events appends them in one transaction with a `hub.write` record (the op and a sha256 of the request) last, so a crash before the commit leaves nothing and a retry writes it whole. `plan_submit` stores its artifact first; it is content-addressed, so a retry reuses it.
- **Errors** are `{code, message, fix_hint, details}`. Codes include `unknown_project`, `unknown_parent`, `wrong_parent_kind`, `untyped_parent`, `unknown_node`, `not_creator`, `kind_not_allowed`, `protected_review`, `illegal_transition`, `idempotency_conflict`, `invalid_brief`, `invalid_recipe`, `invalid_plan`, `invalid_params`, `unknown_profile`, `profile_mismatch`, `recipe_mismatch`, `unknown_namespace`, `invalid_fact`, `unknown_fact`, `unknown_source` and `too_many_facts`.
- **Facts** (`facts.recorded`, `facts.retracted`, scoped to the project). Keys come from a closed set of namespaces, each with its own value model; every `<...>` part is 1 to 64 of `A-Z a-z 0-9 _ -`:
  - `sync.offset.<angle>`: whole frames, the frame rate as a rational, and what the offset is relative to.
  - `audio.gain.<track>`: dB, -96 to +24.
  - `template.trap.<id>`: text, up to 2000 characters.
  - `template.id.<name>`: a Resolve unique id.
  - `path.map.<name>`: `from` and `to` paths.
  - `render.hash.<deliverable>`: sha256 and byte size. An optional leading role segment, only `review` or `master` (`render.hash.review.<deliverable>`, `render.hash.master.<deliverable>`), lets a review and a master of one deliverable coexist; any other role word is refused.
  - `qa.<metric>.<deliverable>`: a finite number and its unit.

  The projection gives each key's current value (the last event in log order wins), who set it and when, an optional source (a recipe node and/or a stored artifact) and its last 10 changes. A retraction keeps the history. Malformed or forged events are skipped and listed. Any actor kind may record; a project holds at most 1000 keys.

#### Recipe runner (S13g2)

`aar.recipes` drives a recipe node through its steps on the hub. Every piece of run state lives in the event log (the op nodes, the `recipe.*` event family, and the reviews), so a killed process resumes from the log alone. This slice ships the engine, the gate library and a test-only recipe; the CCN recipes are a later slice.

- **Recipes are defined in code**, in `aar.recipes.registry`. A `RecipeDef` has a name (the hub's `NAME_RE`), a version, a pydantic params model and an ordered tuple of `StepDef` (at most 64). A `StepDef` has an id (`[a-z][a-z0-9_]{0,31}`), a kind (`cold`, `hot`, `agent`, `gate`), the ids of earlier steps it `needs` (a DAG, validated at registration), `max_attempts` (1–5, default 3), a finite `timeout_s` (≤ 24 h) and per-kind fields. Registering a recipe installs its params model into the recipe-params validator hook (the `ParamsValidator` seam from S13g1): the running surfaces (`aar hub serve`, the recipe engine) plug in `registry_params_validator`, so `recipe_create` then refuses an unregistered recipe name with `unknown_recipe` (a new error code) and validates params against the registered model (`invalid_params`). `build_server`, `aar hub serve` and `aar hub write recipe` all default to `registry_params_validator`; a caller opts out of the registry with `accept_any_params`. `recipe_start` (and the worker) re-validate the stored params, so a recipe slipped in through the generic graph API with bad params is refused `invalid_params` rather than crashing a step.
- **Each step attempt is an op node** with typed data `aar.step/1` (`recipe_node`, `step_id`, `attempt` from 1, `round` from 1, `step_kind`), created by RUNNER. It links to the recipe node with `derives_from` and to any artifact it produces with `produces` (also by RUNNER). **The op's and the recipe's graph status are mirrors the engine writes; they are never read as truth.** The scheduler derives every status from runner evidence: an attempt is done/failed from a runner `recipe.result`; a gate is done from a human decision on the runner-linked review; cancelled from a runner `recipe.cancelled`. So an agent that owns an op node and moves its graph status changes nothing the scheduler reads (it is also refused `runner_managed`). A round rollback supersedes attempts with a `recipe.cancelled` event.
- **The `recipe.*` event family** (typed payloads, each written with S13g1's atomicity pattern — one transaction, the `hub.write` record last): every one is **attributed to RUNNER**, with the real caller recorded (`caller` in the `hub.write` record, `worker` on a claim, `by` on a result). Their idempotency keys are **global under the single runner identity** (not per-actor), which is what makes op creation unique across concurrent callers. The family: `recipe.started`, `recipe.claimed` (a lease, with `worker` and `claim_index`), `recipe.heartbeat` (keyed per claim), `recipe.hot_intent`, `recipe.hot_submitted`, `recipe.result` (`done`/`failed`, canonical-JSON outputs enforced ≤ 64 KiB — over it the step fails `outputs_too_large`; artifact ids; an error `{code, message, fix_hint}`), `recipe.review_linked`, `recipe.cancelled`, `recipe.run_cancelled`. The fold ignores any `recipe.*` event or `aar.step/1` op node not authored by RUNNER (listed in `ignored`).
- **Scheduling is a pure function over runner evidence**: `advance(log, recipe_node, *, actor, dispatcher=None, clock)` does one pass. It creates the op node for each ready step (one per attempt — the op-creating event uses a global idempotency key under RUNNER, so two concurrent callers produce exactly one op), submits and polls hot steps through the port, opens gate reviews and reads their decisions, advances review rounds, and reconciles the recipe node's graph status to the evidence status each pass (so a block that clears, e.g. after a legitimate retry, never sticks). It never runs a cold step itself. `actor` is the real caller, recorded on every write; the writes are RUNNER's. Every recipe write tool and the worker loop call `advance`.
- **Cold steps run in a worker** (`aar recipe worker`, the D6 cold worker on the Linux hub host). It claims a pending cold op with a 60 s lease (heartbeat every 15 s; both config), runs the registered callable with a `StepContext` (the recipe params and brief, the needed steps' outputs, an artifact `put`/`get`, a facts writer attributed to the op, a deadline, `cancelled()`), records the result and calls `advance`. A claim whose lease has lapsed is re-claimed only for steps registered `idempotent=True`; a non-idempotent lapsed claim fails `lease_lost` and needs an explicit retry; a live lease is never stolen. **Timeouts are cooperative: an in-process step cannot be killed.** The context carries a deadline and a callable that overruns it is recorded as `timeout`, but it could not be interrupted. SIGINT/SIGTERM stop claiming new work and let the current step finish.
- **Hot steps go through a port**, the `HotDispatcher` protocol (`submit`/`poll`). Before `submit`, `advance` records the intent with a deterministic `request_id` (the op id); the dispatcher is idempotent on that id, so a crash between the intent and the submitted record re-submits the same id. **The port's `request_id` idempotency is load-bearing** (F11): two concurrent `advance` callers may both call `submit` for the same op, which is safe only because the port dedupes on `request_id`; the fake is strict about it, and the real S15b job store keys its jobs on the request id. A port call that raises is caught per op inside `advance` (it never escapes or fails the step): a submit error leaves the recorded intent so the next pass re-submits, a poll error shows `waiting:dispatcher_error`. With no dispatcher the op stays `pending` and the status view shows `waiting:no_node_dispatcher` — "the Linux hub works with the PC off". `waiting_for_node` and `node_offline` show through unchanged. The real port (hub jobs plus a remote node) is S15b; this slice ships the protocol and a fake.
- **Agent steps** hand work to an agent, which completes them explicitly with `step_complete`. The step declares an `instruction` and an `expects` contract: a `plan` node that derives from the recipe node (round 1) or this recipe's gate review for the previous round (round > 1) and passes `plan_gate`; an `artifact` of a stated media kind, stored in this recipe's project; or `json` for a pydantic model. Outputs are canonical-JSON ≤ 64 KiB (`outputs_too_large` otherwise). The runner validates against the contract; on failure the call is refused (`expects_unmet`) and the step stays open. Any agent or a human may complete it; the completion is a runner write with the caller recorded as `by`. `step_complete` and `recipe_retry` honour the caller's `idempotency_key` (replay the first result marked `replayed`, or `idempotency_conflict`); an optional `round` guard on `step_complete` stops a replayed earlier-round call completing a later round.
- **Gate steps are human review gates.** On activation the runner opens a review (a review node and `reviews` edge written by RUNNER, so **the requester is the runner identity**: no agent can withdraw it, a human can) whose subject is a prior step's output. Approve finishes the step. Reject, while `round < max_review_rounds` (the S13g1 bound, 1–10, default 3), starts the next round and supersedes every live-or-done attempt from the step named by `on_reject` onward. At the limit the step fails `review_rounds_exhausted` and the recipe blocks; that gate is **terminal** — `recipe_retry` on it is refused `rounds_exhausted`, and the only exit is `recipe_cancel`. A review withdrawn by a human (no decision) fails the gate `review_withdrawn` and blocks the recipe; `recipe_retry` then opens a fresh review **in the same round** (a withdrawal does not use a round). **Nothing in this slice decides a review — that stays a human action in the console.**
- **The gate library reads evidence, never node status** (`aar.recipes.gates`). `plan_gate` passes only when the stored lint summary has no errors and every required rule actually ran; it ignores the plan node's graph status, so an agent that moves its own lint-`blocked` plan to `active` (a legal transition — S13g1 F2) still cannot pass it. `qa_gate` reads a `QAReport`: a required check passes on `pass`, on `warn` only when allowed, and fails on `fail`, on `incomplete`, or on `skipped` unless its `skip_reason` is `not-applicable`. Exit 0 from `aar qa check` is not a pass.
- **REPORT.md (step 16).** A built-in last step `recipe.report` (cold, idempotent) writes a deterministic `REPORT.md` artifact: every step's attempts, rounds, durations, outcomes and error codes; the gate decisions with the deciding human; the QA summaries; the facts recorded; and every produced artifact with its sha256. For now "archiving" is that report plus the recipe node going `done`; files move in S16b.

#### Delivery (S13i)

R6 steps 9 to 12 turn a finished render into a stored, hashed, QA'd and (for review) sent artifact. Two parts carry it.

- **Render output size (`render.build`, `render` job).** The build op takes an optional output size (`width`/`height`, both or neither, even, 16 to 8192), `video_quality` (a bit rate in kbit/s from 100 to 400000, or one of Least/Low/Medium/High/Best; 0 is refused, so None means automatic), `export_audio` and `audio_codec`. `_configure` writes them through `SetRenderSettings` **after** the delivery preset loads, so they override it, and the §5 Deliver snapshot carries the human's own size and quality back on restore. After `AddRenderJob` the op reads the size back off the queued job: a size the queue reports but that does not match is `render_size_ignored` (the just-added job is cleaned up), while a queue that reports no size keys is recorded as `size_verified: false` rather than failing. A resumed build adopts its journaled job and never re-applies or re-verifies the size.

- **`aar.deliver` (hub-side library, `aar deliver review|master`).** Dependencies are injected (an `EditHostLike` for the verified transport, a `Transcoder` with a default two-pass `FfmpegTranscoder`, a QA callable defaulting to `aar.qa.check`, and the hub's `EventLog`, `ArtifactStore` and `Actor`). Each delivery works in `<workdir>/<project>/<deliverable>/<render_job_id>/`; the `workdir` is required, absolute and durable (never a scratch directory — the library creates none of its own), and every file it writes, including the ffmpeg two-pass logs, stays inside it.
    The `workdir` must be absolute and durable: a path that resolves under a fixed system scratch root (`/tmp`, `/var/tmp`, `/dev/shm`) is refused (`invalid_workdir`). Each delivery takes an exclusive per-work-dir `flock` for its whole run: a second concurrent delivery of the same render job gets `delivery_in_progress`, and because the lock is an `flock` a crashed delivery releases it so a later resume is never blocked.
  - **Review.** Pull the render (skipping the pull when the local copy already matches the remote sha256; a different sha256 is `deliver_local_mismatch`, never overwritten). The review box is 1280×720 or 720×1280, chosen by the **source aspect, not by kind**; the fit keeps the aspect, uses even dimensions and never upscales. A render is used as is only when it already fits the box and the cap (`review_mp4_max_mb`, decimal MB) **and** is already a browser-playable file: H.264 video at `pix_fmt` yuv420p (8-bit 4:2:0 — so High 4:2:2, High 4:4:4 and 10-bit are excluded), AAC or no audio, in an `.mp4`/`.mov` container (its stored mime then follows the container, e.g. `.mov` → `video/quicktime`); anything else — ProRes, 10-bit, a non-yuv420p profile, a `.mkv` — is transcoded. The transcode is two-pass H.264 (`yuv420p`, High profile, so every browser plays it) + AAC 128 kbit/s + `+faststart` at `floor((cap·0.92·8/duration − 128000)/1000)` kbit/s (capped at 4000, refused below 250 as `review_cannot_fit`), retried once at 85% of that rate, and `review_over_cap` if it is still over. A partial transcode goes to a `.part` and is renamed only after ffmpeg exits 0, the output decodes, and its size is checked against the cap; the two-pass logs are deleted on success and failure, and the per-pass ffmpeg timeout is `max(120 s, 4×duration)`. A review.mp4 left by a prior attempt is reused only if it fits the cap and still decodes — an over-cap or undecodable (or unprobeable) leftover is rebuilt, never reused. Each delivery takes an exclusive `flock` on the work dir; a second concurrent delivery of the same render gets `delivery_in_progress` (exit 3), while an flock errno other than EWOULDBLOCK/EAGAIN (an NFS `nolock`, FUSE or SMB mount) is `lock_unsupported` (exit 2) and names the errno. QA holds the review to the **content kind's** loudness and duration targets (short or longform) plus the review checks (decode and the size cap), composed in the delivery library without changing what `qa.check(kind="review")` means for other callers; a failing report is `review_qa_failed` and nothing is stored or sent. The review MP4 is stored (`ArtifactStore.put`, deduped by content); its sha256 and size go to `render.hash.review.<deliverable>` and its size in MB to `qa.size.<deliverable>`; then a human review is requested, and any still-open review previously requested for the same project, deliverable and review role is withdrawn ("superseded by delivery <id>", via the requester-withdraw path, same actor), so a human can never approve a stale proxy. The facts and the review carry deterministic idempotency keys derived by hashing `(project, deliverable, render job id, role, content sha256)` (well under the hub's 128-char key limit for any input), so an unchanged re-run writes nothing new and does not transcode again, while a re-delivery whose bytes changed (a lowered cap, an ffmpeg upgrade, an F5 rebuild) is a new delivery that supersedes the previous `render.hash` fact through the facts store's last-writer-wins path — never a hub idempotency conflict.
  - **Master.** Pull (same resume rules), store with role `master`, and QA with the source kind. The hash fact (`render.hash.master.<deliverable>`) is always written; a `qa.<metric>.<deliverable>` fact is written for each numeric value a check measured (integrated loudness in LUFS, true peak in dBTP), never guessed. Duration is not written as a pass/fail fact without a plan (the master QA runs without one); the measured duration stays on the `RenderOutput`. There is no transcode and no review request: the master is stored whether QA passes or fails, because the publish gate (step 13) is a human. Masters can be several gigabytes, so every hash and copy is streamed; `command_timeout` on the edit host has to be raised for a large master. Review and master write distinct `render.hash.<role>.<deliverable>` keys, so they never clobber each other for one deliverable name.
  - **Errors** are a typed `DeliverError(code, message, fix_hint, **detail)`; any hub, media, environment (a locked or read-only event log, an unwritable artifact store) or value error after the first write is wrapped into one, carrying the truthful `completed_steps` already done — a `sqlite3` error becomes `hub_unavailable`, an `OSError`/`PermissionError` from the artifact store becomes `store_unavailable`, and a local-filesystem read/write error elsewhere (an unreadable source, a broken work dir) becomes `local_io_error`. Opening the hub db with a bad `--db` (not a sqlite file, or a missing directory) is caught by the CLI and reported as `hub_unavailable` (exit 2, no traceback). The stable codes are `invalid_render_output`, `invalid_workdir`, `invalid_name`, `invalid_input`, `deliver_local_mismatch`, `delivery_in_progress`, `lock_unsupported`, `review_cannot_fit`, `review_over_cap`, `transcode_failed`, `review_qa_failed`, `media_unreadable`, `unknown_subject`, `hub_write_failed`, `hub_unavailable`, `store_unavailable`, `local_io_error` and `unsupported_platform`. The CLI exits 0 (done), 1 (QA failed), 2 (bad input, a missing tool, an unavailable hub/store, or running on Windows), or 3 (a transport error or `delivery_in_progress`). `fcntl` (POSIX-only) is imported lazily inside the lock, and delivery refuses on Windows with `unsupported_platform` before any lock, so `aar` — which imports the deliver CLI to register its commands — still loads on the Windows node. Recipe wiring is a later slice.

#### Remote node link (S15a)

How a node on the Windows edit PC does everything `LocalHubLink` and `EventLogTransport` do in process, against a hub on the Linux host in another process. This slice adds the link only; hub-side jobs and the run loop are S15b.

- **Direction.** The node dials out to the hub; the hub never connects to the PC for job work (decision 1). This works with the PC off and behind NAT.
- **Auth.** Identity is an enrolled bearer token, not reachability (decision 3; a default Andrew may change). The hub stays tailnet-only, so the token is a *second* factor, not the only gate. `aar hub node enroll <id> --actor human:<id>` mints a `secrets.token_urlsafe(32)` token, stores only its `sha256` in `node.enrolled`, and prints the token once. `aar hub node revoke` writes `node.revoked`; `--rotate` revokes and re-enrols in one transaction. Lookups fold the enrolment events fresh on every request (no cache outlives a revocation) and compare hashes with `hmac.compare_digest`, so a revoked or rotated token stops working on the very next call. The node reads the token from a file (`token_file`), never an env var; on POSIX a group- or other-readable file is refused, as ssh does (skipped on Windows). The token never appears in a repr, a log line, an exception or the event log.
- **Transport.** `aar hub nodeapi --db [--host <loopback>] [--port 8789] [--allow-remote]` is a Starlette app run by uvicorn with `proxy_headers=False`, opening the existing DB read-write. A non-loopback bind needs `--allow-remote`. Routes: `POST /node/v1/<op>` only (anything else 404, a non-POST 405). `Authorization: Bearer <token>`; a missing, unknown or revoked token is 401 with no detail. The authenticated node id comes from the token; a body `node_id` that differs is 403 `node_mismatch`. `Content-Type: application/json` is required, the body cap is 1 MiB (over it 413), a bad shape is 400 `invalid_request`. Every request carries a validated `request_id` (≤64 chars), echoed back. Responses: `200 {ok, result, replayed, request_id}`; `4xx {ok:false, error:{type, message}, request_id}`. A traceback never appears; an unexpected error is a generic 500. The node side (`aar.node.remote`, stdlib only) caps responses at 4 MiB.
- **Ops** are thin calls into the same hub functions `LocalHubLink`/`EventLogTransport` use: `assert_running` (always checks `node:<token node>` plus `all` and the project), `control_status`, `approval`, `consume_approval` (see idempotent consume), `record_branch`, `branches` (a new `HubLink` read for S15b's branch rebuild), and `feed_deliver` (runs `deliver_feed_event`, keeping the spec's idempotency key so a resend is a no-op). For `consume_approval` and `record_branch` the body `actor` is the job's on-behalf-of actor; it must be `agent`, or `node` with the token's id; a human actor is refused 403 `actor_not_allowed`.
- **Error table** (same contract as `HubLink` and the feed; each row is tested):

  | Node sees | Raised (an `OSError` = unreachable, a `ValueError` = refused) |
  | --- | --- |
  | connection refused/reset, DNS failure, timeout, TLS failure | `HubUnreachable` |
  | 5xx, 429, 503, over-cap response, non-JSON 200 | `HubUnreachable` |
  | typed 4xx: an approval code | the matching `ApprovalError` subclass |
  | 423 `stopped` | `Stopped` |
  | 409 `feed_conflict` | `FeedConflict` |
  | typed 4xx: `unknown_hub_project` / `invalid_input` | `UnknownHubProject` / `InvalidInput` |
  | 4xx with an unknown type | `HubRefused` (generic `ValueError`, carries the code) |
  | 401 or 403 | `NodeNotEnrolled` (a refusal: the runtime stops dispatching and stops the feed, no retry; a human re-enrols) |

  `HubUnreachable` is fail-closed and temporary: the job waits `hub_unreachable` and the feed backs off; a stop issued while the link was down still bites on reconnect, because `assert_running` is a live call before every hot op (decision 5, no cached "running"). A `stopped` is 423 Locked, because an emergency stop is a deliberate hold a human must lift.
- **Idempotent consume across a lost ack.** A retried consume after a dropped response must not park the job. `approvals.consume_for_node` records the authenticated node as `via_node` in the `approval.consumed` payload, in the same transaction as the consume. A retry whose token, scope, target and on-behalf-of actor match the recorded consume, through the same node, returns the first result with `replayed: true` and writes nothing; any other second consume is still refused and audited (`ApprovalAlreadyConsumed`). The local `approvals.consume` is unchanged, so its existing callers keep single-use semantics. The runner's existing write-ahead `approval_pending` intent and `_verify_approval`/`approval` read already heal a lost ack on reconnect (it re-reads the token rather than re-consuming); the hub-side replay is kept as defence in depth for a genuine re-consume.
- **`via_node`.** The node id is recorded with every write the API makes: as the explicit `via_node` payload field on `approval.consumed` (whose event actor is the on-behalf-of *agent*), and as the event actor `node:<id>` on `record_branch` and the feed events (the hub functions already require it). Logs written before S15a fold unchanged, because `via_node` is a new optional payload key no projection reads.
- **Residuals for S15b.** S15a does not yet check that the agent actor on a consume or branch record belongs to a job this node has claimed (there are no hub-side jobs until S15b). `NodeRuntime.remote(...)` exists and is wired, but `aar node run` and the run loop that reacts to `NodeNotEnrolled` (stop claiming, stop the feed) are S15b, as is the Windows job-store lock (decision 11): until then `aar.node.runtime` still transitively imports `fcntl` through the job store, though `aar.node.remote` and the feed/link modules themselves do not. A live gateway against a real Resolve is not exercised here; the tests inject a fake gateway.

#### Resolve build ops (S13h1)

The `plan.apply` compiler (S13h2) compiles an EditPlan v2 into hot ops. `aar.node.ops.build` adds the six it was missing; there is no compiler yet.

- **The ops.** `media.import` (edit-PC files into a media-pool bin), `track.ensure` (append tracks; set name, enabled, locked), `transition.add` (a transition at an item's start or end), `item.set_color` (a CDL and/or a LUT on an existing node), `item.set_transform` (zoom, pan, tilt, rotation, flips) and `title.place` (a Text+ title template at an exact record range, with its text).
- **Idempotent by read-back,** like the other write ops: the current state is read first and a match is `present` with no call; every write is read back, and a write that returned True but reads back differently is an `OpError` with a stable code. Lists hold 1 to 50 entries, a target may not repeat, every number is finite and every string is non-blank and bounded.
- **Never destructive.** No op deletes or replaces a track, clip, transition, node or media-pool item it did not create in the same call, moves or relinks media, or changes the project or database. The one deletion is `transition.add` undoing the transition it has just made when its read-back is wrong (`transition_short`, `transition_misplaced`; `transition_left_behind` if the delete fails). An AST scan of `build.py` pins this. Tracks are only appended; there is no `DeleteTrack` op. A title never overwrites: an occupied range is `track_occupied`, and the same template exactly there is reused.
- **Branch guard.** Five ops edit a `timeline` named by unique id, so R3 applies unchanged. `media.import` names no timeline; its guard exemption reads "additive: only adds media-pool items to the named bin and, with create_bins, the missing bins on its path; never alters, moves, relinks or deletes existing items or any timeline". It matches existing items by their `File Path` (separators normalised, ASCII case folded), never re-imports one, and matches what `ImportMedia` returns by `File Path`, never by position; strays and duplicates are reported (`import_unexpected`), never deleted. The bin is made current only for the import, and the folder that was current is put back.
- **No Fairlight mute, solo, bus or bounce in 21.1.** The API has none of these. `AudioTrack.mute` can only be approximated by a disabled track (`track.ensure` with `enabled: false`), which neither plays nor renders (inferred) but is not a Fairlight mute; S13h2 reports bus assignment and bounce as manual steps. A track's channel format cannot be changed by script: an existing audio track of another format is `track_format_mismatch`.
- **Colour.** 21.1 has no CDL getter, so a CDL is sent but never claimed: the result says `verified: false, reason: "no-cdl-getter-21.1"` and lists what was sent. `SetCDL` sets absolute values, so a rerun sends it again. `GetLUT` returns a path relative to the LUT folder, so LUTs compare by normalised trailing components. There is no add-node call: a node that does not exist is `node_out_of_range`. Set colour after `grades.copy`, which replaces the node graph.
- **Titles.** `InsertTitleIntoTimeline` and `InsertFusionTitleIntoTimeline` land at the playhead with a default length that nothing can change afterwards, so `title.place` appends a template media-pool item (a Fusion composition holding a Text+) with `AppendToTimeline`, through the `timeline.append_ranges` machinery, then sets `StyledText` on the comp's `TextPlus` tool and reads it back. Captions and subtitle tracks are not part of S13h1.
- **Transitions.** The handle check before `AddTransition` is advisory (`center` needs `frames // 2` each side, `left`/`right` all of it on one side; the rules are inferred); the read-back of the new transition's type, length and position is the real check. The R6 rule that allows only the head and outro transitions is enforced by `plan.lint` and the compiler, not by the op.
- **Inferred, to confirm in a live smoke** (gated live tests in `tests/node/test_ops_live.py`, on a scratch timeline they create, deleting nothing): `ImportMedia` skips an unreadable path silently and can import a file twice; `StartIndex`/`EndIndex` may be left out; the audio format names; what `AddTransition` does with short handles (the op handles both a shorter transition and `None`); that `DeleteClips` deletes a transition item; the alignment meanings; the `TextPlus` id, the `StyledText` input and its `"\n"` line breaks, and that `SetInput` without a time sets a constant; that `FlipX`/`FlipY` read back as booleans; and that `SetCDL`, like the other setters, can jam after the Color page (the op bounces and retries once).

#### FCPXML export (S18)

The owner's decision (2026-11-08): the app makes edits and saves them in a file Resolve opens, with no running Resolve. `aar.plan.export` is a pure, cold, deterministic library on the hub that writes an EditPlan v2 as one FCPXML 1.10 timeline (`fcpxml > resources > library > event > project > sequence > spine`), imported in Resolve with File > Import > Timeline. It is a sibling of the `plan.apply` compiler, which stays as it is, and reuses its plan-walking helpers (first and last content segment, title track, audio track index, handle arithmetic). It uses only the stdlib (`xml.etree`).

```console
aar plan export PLAN --profile ccn --format fcpxml --out cut.fcpxml [--media-map map.json] [--overwrite] [--json]
aar plan export PLAN --verify cut.fcpxml [--media-map map.json]
```

The export lints first and refuses a plan with lint errors (exit 2); warnings are printed. It writes the file and `cut.report.json` beside it as one pair (both are written to fsynced temporary files, then placed; a failure puts the previous pair back, byte-identical, or leaves nothing for a fresh export, with no temporary file left), never over an existing file unless `--overwrite`, and prints the report. The report's `import` section says how to bring it in: File > Import > Timeline, with "Use sizing information" and "Automatically set project settings" ticked for a non-16:9 or custom size (the scripted import ignores the FCPXML format size: a 9:16 short came in at 1920x1080); "import source clips" can stay on in the dialog. **Round 3 (Resolve 21.1 import test, 2026-11-08)** set the layout below: what Resolve mishandled is never written. Before handing out a file it reads it back with its own reader and refuses (`self_check_failed`) unless it reproduces the plan exactly. `--verify FILE` runs the same check on any file: exit 0 when it matches, 1 on a mismatch, 2 on unreadable input. Element and attribute names follow Apple's FCPXML reference; the URLs, and the DTD content models the reader checks against, are recorded in aar-evidence/s18/PROGRESS.md.

| Plan concept | FCPXML |
| ------------ | ------ |
| `fps` | `format frameDuration`: 1001/24000s for 23.976, 1001/30000s for 29.97, 1/24s, 1/25s, 1/30s, and the 47.952, 48, 50, 59.94 and 60 rates. Any other rate is refused (`fps_not_representable`), so 23976/1000 never drifts |
| Positions and lengths | Exact rational seconds, `frames * den / num` over the frame duration's denominator (`86486400/24000s`), whole seconds when exact. No floats |
| Timeline start | `sequence tcStart`, non-drop: 01:00:00:00, or the profile's `[export] timeline_start`. Spine offsets count from it |
| `resolution` | `format width height`, named (`FFVideoFormat1080p2398` etc.) only for 720p, 1080p and 2160p at 23.976, 24, 25, 29.97, 30, 50, 59.94 and 60, where Final Cut Pro has a standard name; otherwise no name (it is optional) |
| Segments on V1 | `asset-clip` on the primary spine (`offset`, `start` = source in, `duration`) at its plan record range, abutting its neighbours exactly (Resolve "trimmed" overlapping spine clips and duplicated the outro), with `gap` elements for holes. The spine runs from 0 to the plan's total length |
| Segments on V2+ | `asset-clip` anchored to the spine element under its start, `offset` in that element's local time, at a dense lane: the used tracks other than V1 in plan order (V3 with no V2 is lane 1), because Resolve creates no empty track for a missing lane. The report maps each plan track to the track it lands on |
| `Segment.gain_db`, `AudioTrack.gain_db` | `adjust-volume amount`: the segment's gain plus its audio track's gain (FCPXML has no track gain) |
| Audio tracks | Every clip carries its own linked sound; nothing uses `srcEnable` (Resolve 21.1 ignores it and imports the sound anyway, which doubled the outro). By the compiler's positional convention V`N` content sound is plan A`N`; it lands on the audio track of its lane (spine A1, dense after that). The report and the sequence `note` map each planned track to the imported one ("plan A5 -> imported A1"). A muted track is exported audible and flagged; bus routing and empty tracks are reported |
| `head` | A `transition` (Cross Dissolve) at the first clip's start (offset = its first frame), opening the spine or following a gap; the audio fade-in is `fadeIn` in the first clip's volume `param` |
| `transitions` (V1 joins) | A video dissolve is a `transition` at the edit between the two abutting clips, carrying an audio crossfade of the same length (`filter-video` + `filter-audio`). An audio-only crossfade is a J/L split edit: the picture cuts at the plan's cut, each clip's sound runs on under the other's (`audioStart`/`audioDuration`, the DTD's "J/L cuts (i.e., split edits)") with `fadeOut`/`fadeIn` over the crossfade. (A spine transition holding only `filter-audio` moved the picture cut by 6 frames in Resolve, so that form was removed.) |
| `outro` | One `asset-clip` with its own linked sound after the content, at the gain of its planned audio track; its transition is a video-only `transition` starting on the cut (or centred/ending on it, from the handles). When the plan puts its sound on another track, the report says "outro sound is on the clip's own track; move it to the A5 bus by hand" |
| `end_fade_frames` | `fadeOut` in the last clip's volume `param` (the outro's sound when there is an outro) |
| Framing | A clip whose `Source.frame_size` aspect differs from the timeline's, or that has a reframe or transform, gets `adjust-conform type="fill"`; a moved clip needs `frame_size` (`source_size_required`). Without a size an unmoved clip keeps Resolve's default (fit), reported |
| `Segment.transform`, `reframe` | `adjust-transform` computed from the source size and the fill scale (never the timeline width for a source value): scale = reframe zoom × transform zoom (negative for a flip), rotation, position = (pan, tilt) − R·scale·c in percent of the frame height (y up), where c is the crop centre `(x, y)` in filled-source pixels; reframe keys become `position` and `scale` keyframes (`interp`/`curve` linear) at clip-local times |
| `markers` | Not written: Resolve imported no clip-level `marker`. Each is in the report under "not imported: add by hand" with its timecode, colour and note |
| `titles`, `outro.sting` | A Basic Title (`title` with `text`/`text-style-def`) at the lane above the top content track; a title that overlaps another in time (a lower third under the sting) goes on the first free lane above, since Resolve trims overlapping items on one track. The report's `titles` lists each title's lane and imported track. Reported: "replace it with template X" |
| `Segment.label`, `notes` | The clip's `name` and `note` |
| Reported, not expressible | `template`, audio `mute` and `bus` (and, per feeding track, that the bus track's gain is not applied to it), empty audio tracks, `Source.color` (input colour space, CDL, LUT, per source), markers, `captions` and `caption_style` (S13e burns captions in), transition types other than dissolve (written as a dissolve), audio crossfade lengths or types that differ from the dissolve, transitions off V1 or across a gap, the outro's audio transition, reframe paths where zoom and centre change together between keys |

**Transitions.** Spine clips keep their plan record ranges and abut; a `transition` sits at the edit and plays over the media beyond the outgoing clip's out and the incoming clip's in (handles), so neither clip is lengthened. Its `offset` is the cut minus its frames before the cut: the cut for one that starts on it, the cut − `d // 2` when centred, the cut − `d` when it ends on it. Apple's reference supports this: the spine "contains elements ordered sequentially in time", "only one story element is active at a given time, except when a transition is present" (DTD), and the transition's "offset and duration attributes define the position and extent of the transition effect" (https://developer.apple.com/documentation/professional-video-applications/transition, .../spine); the Resolve read-back is the ground truth. The alignment is the compiler's own rule, `aar.plan.apply.compile.transition_alignment`: centred when the handles hold all its media (`d // 2` frames before the cut on the incoming head, the rest after it on the outgoing tail), else starting on the cut, else ending on it; an unknown source duration counts as no handle (`no_handle_for_transition`). A split-edit crossfade uses the same windows for the sound. Two transitions on one clip may not overlap (`transitions_overlap`). A clip's sound plays its plan range, widened only by a split edit. Final Cut Pro ignores a transition's audio crossfade on a clip with split timing; the report flags each case.

**Media paths.** `src` must be a path Resolve on the edit PC can open. An absolute edit-PC path (`E:\...`, `\\host\share\...`, checked with the build ops' own rule) becomes a percent-encoded `file:` URL. A `file:` URL of a drive or UNC path is used as is. A hub (Linux) path, or a `file:` URL of one, needs `--media-map` (a JSON object of `linux_root -> windows_root`, the S13f path map); without one, or outside it, it is refused as `media_not_on_edit_pc`. A media-pool name (a multicam clip) is refused as `pool_source_not_exportable`, with a hint to give the underlying camera file. Also refused as `media_not_on_edit_pc`, each with a `reason`: a `file:` URL with a drive letter in the host (`file://E:/...`), with userinfo, or with any `%` in the host (an encoded separator would move the host and share); a map root (a directory, not a file); a path component ending in a space or a dot; and a relative name. `aar plan produce` keeps a stub's media names as given, so a stub for export must give absolute edit-PC paths, or hub paths with `--media-map`. Each asset starts at 0s, so source frames count from each file's first frame; its duration is the source's, or the furthest frame used (reported).

**Refusals** are typed `ExportError`s: `lint_errors`, `fps_not_representable`, `bad_timeline_start`, `empty_timeline`, `unknown_source`, `zero_length_segment`, `media_not_on_edit_pc`, `source_size_required`, `pool_source_not_exportable`, `bad_media_map`, `outro_audio_track_missing`, `duplicate_transition`, `no_handle_for_transition`, `transitions_overlap`, `duplicate_keyframe_time`, `non_finite_value`, `unsafe_text` (text XML 1.0 cannot carry exactly), `fade_too_long`, `item_outside_timeline`, `self_check_failed` and `output_exists`.

**The self-check** parses the file with the stdlib, refuses entity declarations and DOCTYPE internal subsets before parsing, checks every element, attribute and child order it meets against the FCPXML 1.10 content models of the elements aar writes, every id and `ref`, and every time (an exact rational on a frame boundary). It fails anything the writer never emits, as an allowlist: an element (a `marker`), an attribute (`enabled`, `anchor`, `srcEnable`, ...), a value of a fixed attribute (`tcFormat`, `audioRate`, `kind`, fade and keyframe types, asset `start`, `hasAudio`, ...), or a second `media-rep`, so a hand-edited or foreign file cannot pass. It then rebuilds the timeline (each segment's track, record in and out, source in and out and media, each transition's cut, length (its window's frames before the cut decoded from its offset) and effect name and uid, split crossfades from the clips' sound ranges and fades, sound ranges, volumes, fades, conform, transforms and keyframes, titles, markers and assets with their start and duration) and requires it to equal the plan; spine clips must abut and never overlap; it checks that every clip, with the handles its transitions play, reads inside its asset and its plan source, and recomputes each filled clip's crop window from the XML (conform, scale, rotation, position, source size) against the plan's reframe within 0.5 source pixels.

**Confirmed by the 2026-11-08 import test:** source frames count from each file's first frame; cut lengths, order and record positions; the 01:00:00:00 start; the head dissolve; static zoom; clip gains; titles at their frames; the split crossfade keeps the picture cut (Resolve puts the overlapping sound on a second audio track). **Still to confirm in the rerun:** the handle-model transitions (no duplicate outro), the one-clip outro, dense lanes; that `adjust-conform fill` fills a 16:9 source in a 9:16 timeline and that position is a percentage of the timeline's height (Apple: "the original frame height", "the project's height"); that a centred or left-aligned transition plays the handles as written; the audio track each lane's sound lands on; `fadeIn`/`fadeOut` and keyframed `adjust-transform` (not readable by script); negative scale as a flip and the pan, tilt and rotation signs; that asset-clip `start` is read relative to the asset's `start="0s"` rather than the file's embedded timecode; the Basic Title and the effect uids (`FxPlug:4731E73A-8DAC-4113-9A30-AE85B1761265` for Cross Dissolve, `FFAudioTransition` for the audio crossfade), which come from Final Cut Pro's own exports.

## 5. Safety rules (enforced in code, not just written here)

- Before every hot op, the node checks that the expected project is the one open. It refuses to switch project or database while a human is active, unless a human forces it from the console.
- Switching databases, creating or restoring cloud projects, and writing to a production project all need a human approval token, which is recorded in the event log.
- **Approvals in node jobs (F15 and the branch guard).** Every op of a job runs as the job's agent, behind the branch guard, in every project. An op the guard refuses (a human's timeline, or state every timeline shares) runs only with a `project.write` approval on target `<project id>#op:<op>#step:<n>`, consumed for that one op occurrence. A mutating op against a production project also needs the job's plain `project.write` approval on the project id, consumed once per job and then good for the job's later writes. The one exception is the overridden op itself: its own override counts for it, so one human grant covers that single op, but it licenses nothing after it. Every consume is audited on the hub as `agent:<agent id>#<job id>`, and a stored approval is trusted only when the hub shows that consume for that exact scope and target.
- **Render-job ownership.** The node's local job store is its trust root for render-job ownership: a job deletes or adopts only the render job whose Resolve `JobId` its own journal recorded there.
- Deliver settings are recorded before a render preset loads and restored afterwards. The recorded settings include the output size (`FormatWidth`/`FormatHeight`) and quality, so a render that sets its own size never leaves the human's size changed.
- Never change Input Color Space on BRAW clips, and never sweep a colour space across a whole bin.
- Never connect to the cloud library's database directly.
- DRP writes always go to new files. Originals are never overwritten.
- Real project files used for testing stay in a git-ignored corpus (`corpus/`, or `$AAR_DRP_CORPUS`) and are never committed.

| Risk | Mitigation |
| ---- | ---------- |

## 7. Decisions (these defaults hold until the owner says otherwise)

1. A standalone app, which Command Center threads use as an MCP server. The alternative is to build it inside Command Center.
2. The hub is tailnet-only for v1. People outside the tailnet will need accounts later.
3. The edit PC's empty Local Database becomes the sandbox for DRP validation and spikes. **This needs approval**, because switching databases closes the open project. Until then, DRP work is offline only.
4. Run the multi-instance spike (S14) on the edit PC. **This needs approval** and an idle window.
5. A GitHub remote. There is none yet, and the PR and Prism gate needs one. Until it exists, slices merge locally into `dev` after independent review. `main` gets only the reviewed `dev` → `main` PR.
6. **Open: a real credential for the console and hub.** In v1, identity is network reachability. Whoever can reach the console acts as its `--operator`, and with `--trust-tailscale-headers` any process on the hub host can claim any Tailscale login over loopback. The MCP server has no auth at all, and with `--agent-writes` any caller can write briefs, recipes, plans, status and facts under any agent id it declares. That is acceptable only while both stay tailnet-only (D2). Before either is reachable from outside the tailnet, it needs a real per-person credential, for example a Tailscale identity checked through the local API or an auth proxy, and the trusted-header mode must go.
